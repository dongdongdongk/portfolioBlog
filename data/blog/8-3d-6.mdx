# { 🎮 State Machine으로 애니메이션 전환 관리하기 }

## 🎯 이번 강의 목표

기존에 사용하던 "Blend Poses by bool/enum" 노드 대신, **State Machine(상태 머신)**을 활용해 더 체계적으로 애니메이션을 관리합니다.

- 이동(Locomotion)과 비행(Flying) 애니메이션을 하나의 State Machine으로 통합
- 전환 규칙(Transition Rule)을 사용해 상태 간 자연스러운 전환
- 애니메이션 그래프를 깔끔하게 정리

---

## 💡 핵심 개념

### State Machine이란?

```
상태 머신(State Machine)
  ↓
캐릭터의 "상태"를 관리하는 시스템
  ├─ 상태: "걷기", "달리기", "점프", "비행" 등
  ├─ 전환: 상태 A → 상태 B로 언제 바뀔지 규칙 설정
  └─ 장점: 복잡한 애니메이션을 체계적으로 관리
```

**왜 State Machine을 사용하나요?**

- "Blend Poses" 노드는 간단하지만, 애니메이션이 많아지면 그래프가 복잡해짐
- State Machine은 각 상태를 독립적으로 관리하고, 전환 규칙을 시각적으로 확인 가능
- 유지보수와 확장이 훨씬 쉬움

- 확장 시 그래프가 복잡해질 가능성

## ⚙️ 전환 규칙 설정

### Inactive → Active 전환 (일반 이동 → 비행)

```
Movement State Machine에서
  ├─ Thruster Inactive 상태 드래그
  └─ Thruster Active 상태에 연결
       ↓
     전환 화살표 생성
```

![image.png](https://res.cloudinary.com/du1acdhxq/image/upload/v1788380764/notion-blog/_/_/_5_/_8_-_3D_-_6/image_3.png)

**전환 규칙 더블클릭:**

```
노드 구성:
  Movement Mode (변수)
    ↓
  Equal (Enum) 노드
    ├─ 입력: Movement Mode 값
    ├─ 비교 대상: Flying
    └─ 출력: Bool (참/거짓)
         ↓
       Result (Can Enter Transition)
```

**Equal (Enum) 노드란?**

- 두 개의 열거형(Enum) 값을 비교하는 노드
- 입력값 == 비교값이면 `True` 반환
- 이동 모드가 "Flying"과 같으면 전환 허용

**동작 원리:**

```
Movement Mode == Flying?
  ├─ Yes → True → 비행 상태로 전환
  └─ No → False → 전환 안 함
```

![image.png](https://res.cloudinary.com/du1acdhxq/image/upload/v1788380764/notion-blog/_/_/_5_/_8_-_3D_-_6/image_4.png)

### Active → Inactive 전환 (비행 → 일반 이동)

```
Movement State Machine에서
  ├─ Thruster Active 상태 드래그
  └─ Thruster Inactive 상태에 연결
       ↓
     반대 방향 전환 화살표 생성
```

**전환 규칙 더블클릭:**

```
노드 구성 1: 걷는 중인지 확인
  Movement Mode
    ↓
  Equal (Enum)
    ├─ 비교 대상: Walking
    └─ 출력: Bool

노드 구성 2: 떨어지는 중인지 확인
  Movement Mode
    ↓
  Equal (Enum)
    ├─ 비교 대상: Falling
    └─ 출력: Bool

두 결과를 OR 노드로 결합
  Bool 1 (Walking 확인)
    ↓
  OR Bool 노드
    ├─ 입력 A: Walking 확인 결과
    ├─ 입력 B: Falling 확인 결과
    └─ 출력: Bool
         ↓
       Result
```

**OR Bool 노드란?**

```
논리 OR 연산자
  ├─ A 또는 B 중 하나라도 True면 → True
  ├─ A와 B 모두 False일 때만 → False
  └─ 예: 걷기(True) 또는 떨어지기(False) = True
```

**AND Bool 노드와의 차이:**

```
AND (그리고)
  └─ A와 B 모두 True일 때만 → True

OR (또는)
  └─ A 또는 B 중 하나만 True여도 → True
```

**동작 원리:**

```
Walking == True 또는 Falling == True?
  ├─ Yes → True → 일반 이동 상태로 전환
  └─ No → False → 비행 상태 유지
```

## 📊 최종 구조

### Anim Graph 전체 흐름

```
Movement State Machine
  ├─ Thruster Inactive
  │    └─ Use Cached Pose: Locomotion
  │
  └─ Thruster Active
       └─ Use Cached Pose: Flying

전환 규칙:
  Inactive → Active
    └─ Movement Mode == Flying

  Active → Inactive
    └─ Movement Mode == Walking OR Falling
```

### State Machine 계층 구조

```
Movement (최상위 State Machine)
  ├─ State: Thruster Inactive
  │    └─ Contains: Locomotion State Machine (cached)
  │
  └─ State: Thruster Active
       └─ Contains: Flying State Machine (cached)
```

## 📝 핵심 정리

### State Machine vs Blend Poses 비교

| 항목          | Blend Poses   | State Machine    |
| ------------- | ------------- | ---------------- |
| **복잡도**    | 간단          | 초기 설정 복잡   |
| **가독성**    | 많아지면 복잡 | 체계적           |
| **확장성**    | 어려움        | 쉬움             |
| **사용 시기** | 단순 블렌딩   | 복잡한 상태 관리 |

### 언제 무엇을 사용할까?

```
Blend Poses 사용:
  ├─ 2-3개의 간단한 애니메이션 블렌딩
  ├─ Bool 값에 따른 단순 전환
  └─ 추가 확장 계획 없음

State Machine 사용:
  ├─ 여러 상태가 복잡하게 연결됨
  ├─ 전환 조건이 다양함
  ├─ 향후 상태 추가 가능성
  └─ 체계적 관리 필요
```

### 주요 노드 정리

```
Equal (Enum)
  ├─ 기능: 열거형 값 비교
  ├─ 입력: Enum 변수
  ├─ 출력: Bool (같으면 True)
  └─ 용도: 전환 조건 판단

OR Bool
  ├─ 기능: 논리 OR 연산
  ├─ 입력: Bool A, Bool B
  ├─ 출력: Bool (하나라도 True면 True)
  └─ 용도: 여러 조건 중 하나만 만족해도 전환

AND Bool
  ├─ 기능: 논리 AND 연산
  ├─ 입력: Bool A, Bool B
  ├─ 출력: Bool (모두 True일 때만 True)
  └─ 용도: 모든 조건을 만족해야 전환

Save Cached Pose
  ├─ 기능: 애니메이션 결과 저장
  ├─ 용도: 한 번 계산한 애니메이션 재사용
  └─ 장점: 성능 최적화

Use Cached Pose
  ├─ 기능: 저장된 애니메이션 불러오기
  ├─ 용도: 캐시된 포즈 사용
  └─ 연결: Save Cached Pose와 짝
```

## ⚠️ 주의사항

```
1. 캐싱 주의
   ├─ Save와 Use는 반드시 짝으로 사용
   ├─ 캐시 이름을 명확하게 설정
   └─ 불필요한 캐싱은 메모리 낭비

2. 전환 규칙 검증
   ├─ 양방향 전환 모두 설정했는지 확인
   ├─ 전환 조건이 명확한지 검토
   └─ 무한 루프 방지

3. State Machine 네이밍
   ├─ 상태 이름은 명확하게 (Idle, Walking, Flying 등)
   ├─ 전환 규칙도 이름 지정 가능
   └─ 유지보수를 위해 일관된 네이밍 규칙

4. 탭 관리
   ├─ 작업 후 불필요한 탭 정리
   ├─ Anim Graph/Event Graph는 유지
   └─ 필요할 때 다시 열기 가능

5. 테스트 필수
   ├─ 구조 변경 후 반드시 테스트
   ├─ 모든 전환 경로 확인
   └─ 키보드/컨트롤러 모두 테스트
```

## 🎯 이번 강의 목표

캐릭터의 움직임에 생동감을 더하기 위해 **발자국 소리**를 구현합니다.

- 걷기/달리기 애니메이션에 발소리 추가
- 점프 시작/착지 소리 추가
- Animation Notify 시스템 활용

## 💡 핵심 개념: Animation Notify

### Animation Notify(애니메이션 노티파이)란?

```
Animation Notify
  ↓
애니메이션의 특정 시점에 "이벤트"를 발생시키는 마커
  ├─ 용도: 사운드 재생, 파티클 생성, 함수 호출 등
  ├─ 위치: 애니메이션 타임라인에 배치
  └─ 동작: 애니메이션이 해당 지점에 도달하면 자동 실행
```

**왜 필요한가요?**

- 애니메이션과 사운드를 정확히 동기화
- 발이 땅에 닿는 순간에만 소리 재생
- 코드 없이 애니메이션 에디터에서 직접 설정 가능

---

## 📋 준비물 확인

### 사운드 에셋 위치

```
Assets → Sounds
  ├─ Footsteps 폴더
  │    ├─ 개별 발자국 사운드들
  │    └─ MS_Footsteps (메타 사운드)
  │
  └─ Jump 폴더
       └─ MS_Jump (점프 사운드)
```

**메타 사운드(Meta Sound)란?**

- 여러 사운드를 조합한 시스템
- 랜덤하게 사운드 선택 + 음높이 변화
- 같은 소리가 반복되어도 자연스러움

**Notify Track이란?**

```
Notify Track (알림 트랙)
  ↓
애니메이션에 노티파이를 배치하는 레이어
  ├─ 기본: 1개 트랙 제공
  ├─ 추가 가능: 트랙 드롭다운 → "Insert Notify Track"
  └─ 삭제: 트랙 선택 → "Remove Notify Track"
```

**여러 트랙을 사용하는 이유:**

- 소리, 파티클, 커스텀 이벤트 등을 구분해서 관리
- 가독성 향상
- 편집 용이

### 3단계: 첫 번째 발자국 노티파이 추가

```
1. 타임라인에서 발이 땅에 닿는 순간 찾기
   Shift + 드래그로 재생 헤드 이동
     ↓
   왼발이 땅에 닿는 지점 확인

2. Notify Track에서 우클릭
     ↓
   Add Notify → Play Sound
     ↓
   깃발 모양 마커 생성

3. 마커 위치 조정
   ├─ 클릭 + 드래그로 이동
   └─ Shift + 드래그로 정밀 조정
```

**Play Sound Notify란?**

- 엔진에 내장된 노티파이
- 사운드 재생 전용
- 가장 자주 사용되는 노티파이

```
Details 패널 (마커 선택 시)
  ├─ Sound 항목 클릭
  │    ↓
  │  MS_Footsteps 검색
  │    ↓
  │  선택 후 왼쪽 화살표(←) 클릭
  │
  └─ 사운드 자동 할당 완료
```

### 5단계: 두 번째 발자국 추가

```
1. 오른발이 땅에 닿는 지점으로 스크럽
   (애니메이션 중간쯤)

2. 우클릭 → Add Notify → Play Sound
   ├─ 이전에 선택한 MS_Footsteps 자동 할당
   └─ 다른 사운드로 변경 가능

3. 재생(▶) 버튼으로 확인
   두 발자국 소리가 정확한 타이밍에 재생되는지 체크
```

```
  ├─ 너무 빠르거나 느리면 마커 이동
```

```
   └─ 너무 느리면: 소리가 늦게 남

   ├─ 블렌드되는 모든 애니메이션에 노티파이 필요
   ├─ 걷기만 추가하면 달릴 때 소리 안 남
   └─ 사용되는 모든 애니메이션 확인

4. 메타 사운드 활용
   ├─ 단일 사운드보다 메타 사운드 권장
   ├─ 랜덤 요소로 자연스러움 증가
   └─ 반복되는 소리의 단조로움 방지

5. 성능 고려
   ├─ 너무 많은 노티파이는 성능 저하
   ├─ 필수적인 것만 추가
   └─ 멀티플레이어에서는 최적화 더 중요
```

## 📊 주요 노드 설명

### Get World Delta Seconds

```
Get World Delta Seconds
  ↓
이전 프레임과 현재 프레임 사이의 시간 (초)
  ├─ 60 FPS: 약 0.0166초
  ├─ 30 FPS: 약 0.0333초
  └─ 가변적: 프레임마다 다름
```

**왜 필요한가?**

```
프레임 독립성 (Frame Independence)

Delta Time 사용 안 함:
  ├─ 60 FPS: 연료가 빠르게 소모
  └─ 30 FPS: 연료가 느리게 소모
       ↓
     프레임레이트에 따라 게임이 달라짐!

Delta Time 사용:
  ├─ 소모율 × Delta Time = 실제 소모량
  └─ 모든 프레임레이트에서 동일한 속도
       ↓
     일관된 게임 경험!
```

**계산 예시:**

```
Drain Rate = 5.0 (초당 5씩 감소)

60 FPS (Delta = 0.0166):
  5.0 × 0.0166 = 0.083 (한 프레임당)
  60프레임 = 약 5.0 (1초당)

30 FPS (Delta = 0.0333):
  5.0 × 0.0333 = 0.1665 (한 프레임당)
  30프레임 = 약 5.0 (1초당)

결과: 프레임레이트와 무관하게 초당 5씩 감소!
```

### Clamp (Float)

```
Clamp (Float) 노드
  ├─ Value: 제한할 값
  ├─ Min: 최소값
  └─ Max: 최대값
       ↓
     Min ≤ 결과값 ≤ Max
```

**동작 원리:**

```
Value = -10, Min = 0, Max = 50
  ↓ Value가 Min보다 작음
  Result = 0

Value = 25, Min = 0, Max = 50
  ↓ Value가 범위 내
  Result = 25

Value = 100, Min = 0, Max = 50
  ↓ Value가 Max보다 큼
  Result = 50
```

**연료 시스템에서의 역할:**

```
문제 상황:
  Jet Fuel = 2.0
  소모량 = 3.0
    ↓
  2.0 - 3.0 = -1.0 (음수!)

Clamp 적용:
  Clamp(-1.0, Min=0, Max=50)
    ↓
  Result = 0.0 (음수 방지)

추가 보호:
  연료 회복 시 최대값 초과 방지
  Clamp(60, Min=0, Max=50)
    ↓
  Result = 50.0
```

```
  ↓
```

```
    ↓
  정지 사운드가 매 프레임마다 재생
    ↓
  소리 spam!
```

### Do Once 노드란?

```
Do Once 노드
  ↓
여러 번 호출되어도 한 번만 실행
  ├─ 첫 실행: 통과
  ├─ 이후 실행: 차단
  └─ Reset 전까지 계속 차단
```

**핀 구성:**

```
Do Once
  ├─ Enter (입력)
  ├─ Completed (출력 - 첫 실행만)
  └─ Reset (리셋 입력)
       ↓
     Reset 실행 시 다시 사용 가능
```

### Do Once 적용

```
Triggered → Has Fuel False 경로
  ↓
Do Once
  ├─ Enter: False 경로에서 진입
  └─ Completed: Stop Jetpack
       ↓
     첫 번째만 실행, 이후 차단
```

**동작 흐름:**

```
프레임 1: 연료 0 도달
  → Do Once 통과 → Stop Jetpack 실행 ✅

프레임 2~N: 여전히 연료 0
  → Do Once 차단 → Stop Jetpack 실행 안 됨 ✅

결과: 정지는 한 번만!
```

## ⚙️ Collision Settings 상세 설명

### Collision Complexity (충돌 복잡도)

```
Project Default (Use Simple Collision As Complex)
  ├─ Simple Collision을 사용
  └─ 권장 설정
```

### Collision Enabled (충돌 활성화)

```
Query Only (쿼리 전용)
  ├─ 용도: Overlap 이벤트, Trace (레이캐스트)
  ├─ 물리: 적용 안 됨 (중력, 힘 등)
  └─ 픽업 아이템에 적합!

Physics Only (물리 전용)
  ├─ 용도: 물리 시뮬레이션
  ├─ Overlap: 이벤트 안 발생
  └─ 물리 객체에 적합

Query and Physics (둘 다)
  ├─ 용도: 둘 다 필요한 경우
  └─ 예: 상자를 밀 수도, 감지도 가능

No Collision (충돌 없음)
  └─ 장식용, 완전히 통과
```

**픽업 아이템:**

```
Query Only 선택 이유:
  ├─ Overlap 이벤트만 필요
  ├─ 물리 계산 불필요 (중력, 힘 등)
  └─ 성능 최적화
```

## 🔄 충돌 상호작용 원리

### Overlap이 발생하는 조건

```
두 오브젝트가 Overlap하려면:

Object A와 Object B의 관계:
  ├─ 둘 다 Generate Overlap Events: True
  │
  └─ 서로의 채널에 대한 Response:
       최소 하나는 Overlap이어야 함

예시:
  BP_JetFuel (FuelMesh)
    ├─ Pawn 채널: Overlap
    └─ Generate Overlap: True

  BP_Kix (Capsule)
    ├─ WorldStatic 채널: Block
    └─ Generate Overlap: True

  결과:
    └─ Block과 Overlap 중 "낮은 것" 적용
         → Overlap 발생! ✅
```

**우선순위:**

```
Block > Overlap > Ignore

충돌 결정:
  ├─ 둘 다 Block → Block
  ├─ 하나는 Block, 하나는 Overlap → Overlap
  └─ 하나라도 Ignore → Ignore
```

### Interface Segregation (인터페이스 분리)

```
BPI_Jetpack의 함수들:
  ├─ Apply Thrust Input (입력 처리)
  ├─ Drain Jet Fuel (연료 소모)
  ├─ Has Fuel (상태 확인)
  └─ Handle Refill Fuel (연료 보충)

각 함수는 명확한 단일 책임
  ├─ 이해하기 쉬움
  ├─ 재사용 가능
  └─ 테스트 용이
```

### Dependency Injection (의존성 주입)

```
Fuel Amount를 파라미터로 전달
  ↓
픽업이 보충량 결정
  ↓
캐릭터는 받은 값만 처리
  ↓
책임 분리, 유연성 증가
```

## 💡 핵심 요약

```
연료 보충 시스템
  ↓
인터페이스 함수: Handle Refill Fuel
  ├─ 파라미터: Fuel Amount
  └─ 반환: 없음

구현:
  Current + Amount → Clamp → Set Jet Fuel

픽업 로직:
  Overlap → Check Interface → Refill → Destroy

안전 장치:
  ├─ Does Implement Interface (타입 체크)
  ├─ Clamp (범위 제한)
  └─ Branch (조건 분기)
```

**이번 강의의 핵심:**

- 인터페이스로 느슨한 결합 유지
- 파라미터로 유연성 제공
- Clamp로 항상 유효한 값 보장
- Does Implement Interface로 안전성 확보
- Destroy Actor로 픽업 후 정리
- Instance Editable로 디자이너 친화적 설계

**설계 원칙:**

- 단일 책임: 각 함수는 하나의 역할만
- 개방-폐쇄: 새 픽업 추가 시 기존 코드 수정 불필요
- 의존성 역전: 구체적인 클래스가 아닌 인터페이스에 의존
