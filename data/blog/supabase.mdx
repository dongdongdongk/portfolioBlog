# 문제 상황: 뭐가 문제였을까?

```jsx
관리자가 시스템에 로그인하는 건 잘 됐지만, 새로운 테스트를 만들려고 할 때 오류가 발생했어요. 오류 메시지는 다음과 같았죠:
```

```jsx
PrismaClientInitializationError: Can't reach database server at aws-0-ap-northeast-2.pooler.supabase.com:5432
```

```jsx
쉽게 말하면, 프로그램이 데이터베이스(데이터를 저장하는 곳)에 연결하려고 했지만, 연결이 안 됐다는 거예요. 이 오류의 코드는 P1001인데, 이건 "데이터베이스 연결이 실패했다"는 뜻이에요.
```

# 왜 이런 일이 일어났을까? (원인 분석)

## 1. 데이터베이스와 연결 풀(Connection Pool)

```jsx
데이터베이스는 데이터를 저장하고 꺼내오는 시스템이에요. 프로그램(여기서는 테스트 생성 앱)이 데이터베이스에 데이터를 저장하거나 읽으려면,

데이터베이스와 "연결"을 만들어야 해요. 이 연결은 마치 전화선을 연결하는 것과 비슷해요. 전화선을 너무 많이 사용하면 더 이상 연결을 못 하죠.

**연결 풀(Connection Pool)**은 프로그램이 데이터베이스와 연결할 때 사용하는

"전화선"의 개수를 관리하는 시스템이에요. 연결 풀은 제한된 개수의 연결만 허용해요. 예를 들어, Supabase라는 데이터베이스 서비스의 무료 플랜은 최대 60개의 동시 연결만 허용해요
```

## 2. 트랜잭션(Transaction)이란?

```jsx
트랜잭션은 데이터베이스 작업을 하나로 묶어서 처리하는 방법이에요. 예를 들어, 테스트를 만들 때:

1. 테스트 정보(Test 테이블)를 저장하고,

2. 질문(Question 테이블)을 저장하고,

3. 답변 옵션(AnswerOption 테이블)을 저장하고,

4. 결과 유형(ResultType 테이블)을 저장해야 한다고 해볼게요.

이 모든 작업이 성공해야 테스트가 제대로 만들어져요. 만약 질문은 저장됐는데 답변 옵션이 저장 안 되면,

테스트가 망가지겠죠? 그래서 트랜잭션은 "모두 성공하거나, 아니면 모두 취소"되는 방식으로 동작해요.

하지만 트랜잭션은 여러 연결을 한 번에 사용하기 때문에, 연결 풀의 "전화선"을 많이 잡아먹어요.
```

## 3. 문제의 원인

```jsx
이제 왜 오류가 났는지 정리해볼게요:

복잡한 트랜잭션:

		테스트를 만들 때, 프로그램은 트랜잭션을 사용해서 여러 테이블에 데이터를 한꺼번에 넣으려고 했어요.

		이 과정에서 많은 연결(전화선)을 사용했어요.

Supabase 무료 플랜의 한계:

		Supabase 무료 플랜은 최대 60개의 연결만 허용해요.

		그런데 복잡한 트랜잭션이 너무 많은 연결을 요청해서, 연결 풀이 고갈됐어요.

		즉, 더 이상 전화선을 빌릴 수 없어서 데이터베이스에 연결하지 못한 거예요.

로그인 vs 테스트 생성:

		로그인할 때는 단순히 사용자 정보를 확인하는 쿼리(데이터를 읽는 간단한 요청)를 보내니까 연결을 적게 사용해요.

		하지만 테스트 생성은 여러 테이블에 데이터를 쓰는 복잡한 작업이라 연결을 많이 필요로 했어요.

네트워크 불안정:

		가끔 네트워크가 불안정해서 연결이 끊어질 수도 있어요. 하지만 이건 주요 원인은 아니었어요.
```

# 해결 방법: 어떻게 고쳤을까?

## 1. 트랜잭션 제거

```jsx
// `const`로 `createdTest` 변수를 선언해서, 생성된 테스트 데이터를 저장할 준비를 해요.
const createdTest = await prisma.$transaction(async (tx) => {
  // `prisma.$transaction`은 여러 데이터베이스 작업을 한꺼번에 처리하는 트랜잭션을 시작해요.
  // `tx`는 트랜잭션 안에서 사용할 수 있는 Prisma 도구예요.
  // `async`는 비동기 작업(시간이 걸리는 작업)을 처리한다고 알려줘요.
  // `await`는 작업이 끝날 때까지 기다리라는 뜻이에요.

  // 1. Test 테이블에 새로운 테스트를 추가해요.
  const test = await tx.test.create({
    data: {
      title: '새로운 테스트', // 테스트 제목
      description: '테스트 설명', // 테스트 설명
    },
  })

  // 2. Question 테이블에 질문을 추가해요. `test.id`를 사용해서 테스트와 연결해요.
  const question = await tx.question.create({
    data: {
      testId: test.id, // 위에서 만든 테스트의 ID
      content: '질문 1', // 질문 내용
    },
  })

  // 3. AnswerOption 테이블에 답변 옵션을 추가해요. `question.id`로 질문과 연결해요.
  const answerOption = await tx.answerOption.create({
    data: {
      questionId: question.id, // 위에서 만든 질문의 ID
      content: '옵션 1', // 답변 옵션 내용
    },
  })

  // 트랜잭션의 결과로 생성된 테스트를 반환해요.
  return test
})
```

```jsx
트랜잭션은 안전하지만, 연결을 많이 사용해요. 그래서 이걸 순차적 처리로 바꿨어요:
```

```jsx
// `const`로 `test` 변수를 선언해서, 생성된 테스트 데이터를 저장할 준비를 해요.
// `await`는 데이터베이스 작업이 끝날 때까지 기다리라는 뜻이에요.

const test = await prisma.test.create({
  data: {
    title: '새로운 테스트', // 테스트 제목
    description: '테스트 설명', // 테스트 설명
  },
}) // 테스트 먼저 저장

// `questions` 배열에 있는 질문들을 하나씩 처리하기 위해 `for` 루프를 사용해요.
// `let i = 0`: 루프를 시작할 때 인덱스 `i`를 0으로 설정.
// `i < questions.length`: 질문 배열의 길이만큼 반복.
// `i++`: 한 번 반복할 때마다 `i`를 1씩 증가.
for (let i = 0; i < questions.length; i++) {
  // `const`로 `createdQuestion` 변수를 선언해서, 생성된 질문 데이터를 저장해요.
  // `prisma.question.create`는 `Question` 테이블에 새로운 질문을 추가해요.
  const createdQuestion = await prisma.question.create({
    data: {
      testId: test.id, // 위에서 만든 테스트의 ID와 연결
      content: questions[i].content, // 질문 내용 (배열에서 가져옴)
    },
  }) // 질문 하나씩 저장

  // 답변 옵션도 비슷한 방식으로 저장 (예시로 주석 처리)
  // `prisma.answerOption.create`로 `AnswerOption` 테이블에 답변 옵션을 추가.

  //   }
  // });
}
```

# 교훈과 권장사항: 앞으로 어떻게 해야 할까?

```jsx
이 문제에서 배운 점과 앞으로 주의할 점을 정리해봤어요.

1. 트랜잭션 사용 주의

		트랜잭션은 안전하지만 연결을 많이 사용해요.

		꼭 필요할 때만 사용하고, 가능하면 순차적으로 처리하는 게 좋아요.

		예를 들어, 테스트 생성처럼 데이터가 조금 덜 엄격해도 괜찮은 경우에는 트랜잭션 대신 하나씩 처리해도 돼요.

2. Supabase 연결 최적화

		연결 풀 모니터링: Supabase 대시보드에서 연결 풀 사용량을 확인해서 문제가 생기기 전에 미리 대처하세요.

		유료 플랜 고려: 무료 플랜의 60개 연결 제한이 문제라면,

		더 많은 연결을 허용하는 유료 플랜으로 업그레이드하는 것도 방법이에요.

		연결 풀 설정 추가: 데이터베이스 연결 문자열에 연결 풀 크기나 타임아웃 설정을 추가해서 안정성을 높일 수 있어요.

3. 에러 처리 개선

		재시도 로직: 데이터베이스 연결이 실패하면 자동으로 몇 번 재시도하도록 프로그램을 설정하면 좋아요.

		명확한 에러 메시지: 사용자에게 "서버에 연결할 수 없습니다" 같은 이해하기 쉬운 메시지를 보여주세요.

		로그 개선: 문제가 생겼을 때 어떤 작업에서 오류가 났는지 쉽게 알 수 있도록 로그를 자세히 남기세요.
```

# 왜 중요한가요?

```jsx
이 사례는 클라우드 데이터베이스(예: Supabase)를 사용할 때 연결 관리가 얼마나 중요한지 보여줘요.

무료 플랜은 저렴하지만 제한이 많아서,

프로그램이 복잡해지면 연결이 부족할 수 있어요.

이런 문제를 미리 이해하고 코드를 최적화하면, 더 안정적인 앱을 만들 수 있어요.
```

```jsx
● 테스트 생성 실패 문제 해결 보고서

  문제 상황

  증상: 관리자 로그인은 성공하지만 새로운 테스트 생성 시 다음 오류 발생
  PrismaClientInitializationError: Can't reach database server at
  `aws-0-ap-northeast-2.pooler.supabase.com:5432`

  에러 코드: P1001 (Database connection failed)

  원인 분석

  1. 복잡한 트랜잭션 처리

  - 테스트 생성 API에서 prisma.$transaction() 사용
  - 하나의 트랜잭션 내에서 여러 테이블에 순차적으로 데이터 삽입
    - Test 테이블 → Question 테이블 → AnswerOption 테이블 → ResultType
  테이블
  - 트랜잭션은 더 많은 데이터베이스 연결을 필요로 함

  2. Supabase 무료 플랜의 연결 제한

  - Supabase 무료 플랜: 최대 60개의 동시 연결
  - 복잡한 트랜잭션은 여러 연결을 동시에 점유
  - 연결 풀이 고갈되면 새로운 연결 요청 실패

  3. 간단한 쿼리 vs 복잡한 트랜잭션

  - 로그인: 단순한 SELECT 쿼리 → 적은 연결 사용
  - 테스트 생성: 복잡한 트랜잭션 → 많은 연결 사용

  해결 방법

  1. 트랜잭션 제거

    // 복잡한 트랜잭션 로직
  })

  // 변경 후: 순차적 처리
  const test = await prisma.test.create({ ... })
  for (let i = 0; i < questions.length; i++) {
    const createdQuestion = await prisma.question.create({ ... })
    // 순차적으로 처리
  }

  2. Prisma 클라이언트 설정 최적화

  const prisma = new PrismaClient({
    datasources: {
      db: {
        url: process.env.DATABASE_URL,
      },
    },
  })

  근본적인 원인

  1. 연결 풀 관리: 트랜잭션은 더 많은 데이터베이스 연결을 점유
  2. Supabase 제한: 무료 플랜의 연결 수 제한
  3. 네트워크 불안정: 일시적인 연결 불안정성

  교훈 및 권장사항

  1. 트랜잭션 사용 시 주의사항

  - 복잡한 트랜잭션은 연결 풀을 많이 사용
  - 가능하면 단순한 순차 처리로 대체
  - 트랜잭션이 꼭 필요한 경우에만 사용

  2. Supabase 연결 최적화

  - 연결 풀 크기 모니터링
  - 필요시 유료 플랜으로 업그레이드
  - 연결 문자열에 연결 풀 설정 추가

  3. 에러 처리 개선

  - 데이터베이스 연결 실패 시 재시도 로직
  - 사용자에게 명확한 에러 메시지 제공
  - 로그 개선으로 문제 진단 용이성 향상

  결론

  문제: 복잡한 트랜잭션이 Supabase 무료 플랜의 연결 제한을 초과해결:
  트랜잭션을 순차적 처리로 변경하여 연결 사용량 최적화결과: 테스트 생성
   성공

  이는 클라우드 데이터베이스 서비스의 연결 제한을 고려한 코드 최적화의
  중요성을 보여주는 사례입니다.
```
