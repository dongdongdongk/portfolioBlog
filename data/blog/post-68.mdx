# 관심사의 분리

```java
* 애플리케이션을 하나의 공연이라 생각해보자. 각각의 인터페이스를 배역(배우 역할)이라 생각하자. 그런데! 실제 배역 맞는 배우를 선택하는 것은 누가 하는가?

* 로미오와 줄리엣 공연을 하면 로미오 역할을 누가 할지 줄리엣 역할을 누가 할지는 배우들이 정하는게 아니다. 이전 코드는 마치 로미오 역할(인터페이스)을 하는 레오나르도 디카프리오(구현체, 배우)가 줄리엣 역할(인터페이스)을 하는 여자 주인공(구현체, 배우)을 직접 초빙하는 것과 같다. 디카프리오는 공연도

해야하고 동시에 여자 주인공도 공연에 직접 초빙해야 하는 다양한 책임을 가지고 있다.
```

![Untitled](https://res.cloudinary.com/du1acdhxq/image/upload/v1788381135/notion-blog/_/_/_-_/_/Untitled.png)

![Untitled](https://res.cloudinary.com/du1acdhxq/image/upload/v1788381133/notion-blog/_/_/_-_/_/Untitled_1.png)

```java
OrderServiceImpl 과 MemberServiceImpl 을 보면 DiscountPolicy discountPolicy = new FixDiscountPolicy(); 처럼 배우의 역할인 클라이언트 클래스가 배우(FixDiscountPolicy) 까지 결정하고 있다

이 역할 클래스 에서 배우를 선택하는 책임을 없에줘야 한다.
```

# **관심사를 분리하자**

```java
배우는 본인의 역할인 배역을 잘 수행하는 것에 집중해야 한다.

상대 배역의 배우가 어떤 배우든지 연기를 할 수 있어야 한다. 공연을 구성하고, 담당 배우를 섭외하고, 역할에 맞는 배우를 지정하는 책임을 가진 별도의 공연 기획자가 필요하다. 이 전 시간 마지막에 얘기했던 그 ‘누군가’가 바로 공연 기획자, AppConfig이다.
```

# **AppConfig 제작**

```java
애플리케이션의 전체 동작 방식을 구성(config)하기 위해 구현 객체를 생성하고 연결하는 책임을 가진 별도의 설정 클래스를 만들어 본다.

core 패키지에 AppConfig 클래스를 생성한다.
```

![Untitled](https://res.cloudinary.com/du1acdhxq/image/upload/v1788381134/notion-blog/_/_/_-_/_/Untitled_2.png)

```java
그리고 MemberServiceImpl로 이동한다.

이 전에는 회원 저장소 인터페이스의 객체를 생성하고 어떤 구현체를 할당할지를 회원 서비스 구현체 MemberServiceImpl이 직접 선택하고 생성하였다. 이제는 회원 저장소 인터페이스에만 의존하도록 코드를 변경해야 한다.

인터페이스 객체를 선언하고(private final MemberRepository memberRepository) , 생성자를 통해 구현체를 받아서(memberRepository) 인터페이스 객체에 할당하는 방식이다.

생성자에서 받아오는 구현체도 모두 MemberRepository 인터페이스의 구현체이기 때문에 MemberRepository로 받아온다. 이렇게 하면 MemberServiceImpl은 MemberRepository 인터페이스에만 의존하게 된다.
```

![Untitled](https://res.cloudinary.com/du1acdhxq/image/upload/v1788381134/notion-blog/_/_/_-_/_/Untitled_3.png)

```java
생성자를 이용한 주입
```

```java
다시 AppConfig로 돌아가서.

MemberServiceImpl의 생성자를 통해 MemberRepository의 구현체를 할당하고 있다. MemberService는 구현체가 어떤 것이 들어올지 알지 못한다.

하지만 MemoryMemberRepository든 DBMemberRepository든 MemberRepository 역할을 구현하는 것이기 때문에 문제가 되지 않는다.
```

![Untitled](https://res.cloudinary.com/du1acdhxq/image/upload/v1788381134/notion-blog/_/_/_-_/_/Untitled_4.png)

```java
OrderServiceImpl도 똑같이 변경해본다.

회원 저장소와 할인 정책이 필요하니 MemberRepository 인터페이스 객체와 DiscountPolicy 인터페이스 객체를 선언한다. 그리고 생성자를 통해 MemberRepository 구현체와 DiscountPolicy의 구현체를 받아와 할당시킨다.
```

![Untitled](https://res.cloudinary.com/du1acdhxq/image/upload/v1788381134/notion-blog/_/_/_-_/_/Untitled_5.png)

```java
AppConfig에도 코드를 추가하도록 한다. OrderServiceImpl의 생성자를 통해 MemberRepository 구현체와 DiscountPolicy 구현체를 할당하고 있다
```

![Untitled](https://res.cloudinary.com/du1acdhxq/image/upload/v1788381135/notion-blog/_/_/_-_/_/Untitled_6.png)

```java
이제 AppConfig가 애플리케이션의 실제 동작에 필요한 구현 객체를 생성하도록 하였다. 생성한 객체 인스턴스의 참조를 생성자를 통해 주입해준다.

* MemberServiceImpl → MemoryMemberRepository

* OrderServiceImpl → MemoryMemberRepository, FixDiscountPolicy
```

![Untitled](https://res.cloudinary.com/du1acdhxq/image/upload/v1788381135/notion-blog/_/_/_-_/_/Untitled_7.png)

```java
이로써 DIP를 준수할 수 있게 되었다. MemberServiceImpl은 MemberRepository 인터페이스에만 의존하면 되고 구현체 클래스를 몰라도 되기 때문이다. 객체를 생성하고 연결하는 역할(AppConfig)과 실행(Member or Order ServiceImpl)하는 역할이 명확하게 분리되었다
```

```java
클라이언트인 MemberServiceImpl 입장에서는 마치 의존관계를 외부에서 주입해 주는 것 같다고 하여 이를 DI(Dependency Injection), 우리말로는 의존관계 주입 또는 의존성 주입이라고 한다.
```

![Untitled](https://res.cloudinary.com/du1acdhxq/image/upload/v1788381135/notion-blog/_/_/_-_/_/Untitled_8.png)

# **AppConfig 수정**

```java

MemberService 객체에 memberService() 메서드(AppConfig에 만들었던 메서드)를 통해 구현체를 할당한다.
```

# 마무리

```java
AppConfig를 통해 관심사를 확실하게 분리한다.

애플리케이션의 실제 동작에 필요한 구현 객체를 생성하고(FixDiscountPolicy, MemoryMemberRepository 등등) 이를 주입해 주고 있다. Member or Order  ServiceImpl은 인터페이스에만 의존하고, 자신의 기능을 수행하는 책임만 가지게 되었다.
```
