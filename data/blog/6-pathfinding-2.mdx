## 1. 패스파인딩이란 무엇인가?

### 패스파인딩의 개념

- **패스파인딩(Pathfinding)** : 게임에서 유닛이나 캐릭터가 장애물을 피해 목적지까지 가는 최적의 경로를 찾는 기술
- 예시: 전략 게임에서 유닛을 클릭하면 벽을 피해서 목적지로 이동하는 것

### 우리가 만들 시스템의 구조

1. **그리드 기반 맵** : 맵이 작은 칸(그리드)들로 나뉘어져 있음
2. **이동 가능/불가능 판단** : 각 그리드 칸마다 걸을 수 있는지 없는지 판단
3. **경로 계산** : A\* 알고리즘이 시작점부터 목적지까지의 경로를 계산
4. **그리드 위치 리스트 출력** : 알고리즘이 거쳐야 할 그리드 칸들의 목록을 만듦
5. **유닛 이동** : Move Action이 이 목록을 따라 유닛을 실제로 이동시킴

---

## 2. A\* 알고리즘의 목표와 동작 방식

### 알고리즘의 기본 목표

- **A에서 B로 가는 최적의 경로 찾기**
- A = 시작 노드(Start Node)
- B = 목표 노드(End Node / Goal Node)

### 이동 방향

- **8방향 이동 가능** : 상, 하, 좌, 우 + 대각선 4방향
- 그리드 기반이므로 각 칸에서 인접한 8개 칸으로 이동 가능

### 노드(Node)란?

- **노드(Node)** : 그리드의 각 칸을 의미
- 각 노드는 이동 가능한 칸이거나 장애물로 막힌 칸

---

## 3. 노드(Node)의 3가지 비용 값 이해하기

A\* 알고리즘에서 각 노드는 **3가지 비용 값**을 가집니다. 이 값들을 계산해서 어느 경로가 최적인지 판단합니다.

### 3가지 비용 값

1. **G 비용 (G Cost)** : 시작 노드부터 현재 노드까지의 **실제 이동 비용**
2. **H 비용 (H Cost)** : 현재 노드부터 목표 노드까지의 **추정 비용** (Heuristic)
3. **F 비용 (F Cost)** : G + H = **총 비용**

이 값들을 사용해서 **가장 F 비용이 낮은 노드**를 우선적으로 탐색합니다.

---

## 4. G 비용 - 시작점부터의 실제 이동 비용

### G 비용의 의미

- **G Cost** = 시작 노드에서 현재 노드까지 **실제로 걸은 거리의 합계**
- "여기까지 오는데 실제로 얼마나 걸렸는가?"

### G 비용 계산 방법

### 직선 이동 (상/하/좌/우)

- 비용 = **10**
- 예시: 오른쪽으로 한 칸 이동 → G 비용 +10

### 대각선 이동

- 비용 = **14**
- 수학적 근거: 피타고라스 정리
  - 한 칸 옆 = 1, 한 칸 위 = 1
  - 대각선 거리 = √(1² + 1²) = √2 ≈ 1.4
  - 정수로 변환: 1.4 × 10 = **14**

### 왜 10과 14를 사용하나?

- **실수(float) 대신 정수(int) 사용**을 위해
- 1과 1.4 대신 10과 14를 사용하면 계산이 더 빠르고 정확함
- 비율은 똑같음: 10:14 = 1:1.4

### G 비용 누적 예시

```
시작 노드 = 0

→ 오른쪽 한 칸 이동 = 0 + 10 = 10
→ 또 오른쪽 한 칸 이동 = 10 + 10 = 20
→ 대각선 위로 이동 = 20 + 14 = 34

현재 G 비용 = 34 (시작점부터 여기까지의 총 이동 비용)
```

---

## 5. H 비용 - 목적지까지의 추정 비용

### H 비용의 의미

- **H Cost (Heuristic Cost)** = 현재 노드에서 목표 노드까지의 **대략적인 추정 거리**
- "여기서 목적지까지 대충 얼마나 남았는가?"
- **휴리스틱(Heuristic)** : "경험적 추측" 또는 "어림잡기"를 의미

### H 비용 계산 방법

- **장애물을 완전히 무시**하고 직선 거리로 계산
- "만약 장애물이 하나도 없다면 목적지까지 얼마나 걸릴까?"라고 가정

### H 비용의 역할

- **우선순위 결정**에 사용
- H 비용이 낮다 = 목표에 가까워 보인다 = 우선적으로 탐색하자!
- 정확할 필요는 없고, 대략적인 방향성만 제공하면 됨

### H 비용 계산 예시

```
현재 위치: (2, 3)
목표 위치: (5, 7)

가로 차이 = |5 - 2| = 3칸
세로 차이 = |7 - 3| = 4칸

장애물 없다고 가정하고 직선으로:
- 대각선 3칸 이동 = 3 × 14 = 42
- 남은 직선 1칸 이동 = 1 × 10 = 10
H 비용 = 42 + 10 = 52

```

---

## 6. F 비용 - 총 비용 계산하기

### F 비용의 의미

- **F Cost** = G + H
- **F = 실제 걸린 비용 + 남은 예상 비용**
- "시작부터 목표까지 이 경로로 가면 총 얼마나 걸릴 것 같은가?"

### F 비용의 역할

- _A 알고리즘의 핵심 판단 기준_
- **F 비용이 가장 낮은 노드**를 다음에 탐색함
- F가 낮다 = 이 경로가 효율적이다 = 우선적으로 조사하자!

### F 비용 계산 예시

```
노드 A:
  G = 20 (시작부터 여기까지 실제 비용)
  H = 30 (여기서 목표까지 추정 비용)
  F = 20 + 30 = 50

노드 B:
  G = 24
  H = 20
  F = 24 + 20 = 44

→ 노드 B의 F가 더 낮으므로 B를 먼저 탐색!

```

### G와 H의 균형

- **G가 계속 증가** : 시작점에서 멀어질수록 커짐
- **H가 계속 감소** : 목표점에 가까워질수록 작아짐
- F는 이 둘을 합쳐서 **가장 효율적인 중간 지점**을 찾아냄

## 7. Open List와 Close List 이해하기

A\* 알고리즘은 두 가지 리스트를 사용해서 탐색 과정을 관리합니다.

### Open List (열린 목록)

- **아직 탐색하지 않은 노드들**의 목록
- "앞으로 조사해야 할 후보 노드들"
- 매 단계마다 Open List에서 **F 비용이 가장 낮은 노드**를 선택해서 탐색

### Close List (닫힌 목록)

- **이미 탐색을 완료한 노드들**의 목록
- "이미 조사가 끝난 노드들"
- Close List에 있는 노드는 다시 탐색하지 않음

### 리스트 사용 흐름

```
1. 시작 노드를 Open List에 추가

2. Open List에서 F가 가장 낮은 노드를 꺼냄

3. 꺼낸 노드를 Close List로 이동

4. 꺼낸 노드의 이웃 노드들을 확인:
   - 이동 불가능한 노드 → 무시
   - Close List에 있는 노드 → 무시
   - 그 외 노드 → Open List에 추가

5. Open List가 빌 때까지 반복

```

### 알고리즘 종료 조건 (2가지)

1. **현재 탐색 중인 노드가 목표 노드다** → 성공! 경로를 찾음
2. **Open List가 비었다** → 실패! 목표까지 갈 수 있는 경로가 없음

## 8. A\* 알고리즘 실행 과정 예시

강의에서 제시한 구체적인 예시를 단계별로 따라가 보겠습니다.

### 초기 상황

- **시작 노드(A)** : 왼쪽 아래
- **목표 노드(B)** : 오른쪽 위
- **장애물** : 중간에 이동 불가능한 칸들이 있음

### Step 1: 시작 노드에서 출발

```
현재 노드 = A (시작점)

이웃 노드 확인:
- 오른쪽 노드 → 이동 가능 ✓
- 위쪽 노드 → 장애물로 막혀있음 ✗
- 대각선 노드 → 장애물로 막혀있음 ✗

→ 오른쪽 노드만 Open List에 추가

```

### Step 2: 오른쪽 노드 탐색

```
Open List에서 F가 가장 낮은 노드 선택 = 오른쪽 노드

이웃 노드 확인:
- 오른쪽 노드 → 이동 가능 ✓
- 위쪽 노드 → 이동 가능 ✓
- 오른쪽 위 대각선 → 이동 가능 ✓
- 왼쪽 노드 → 이동 가능하지만 장애물 때문에 막혔음 ✗

→ 이동 가능한 3개 노드의 G, H, F 계산
→ F가 가장 낮은 것을 다음 탐색 대상으로

```

### Step 3: H 비용이 더 낮은 노드 우선 선택

```
예를 들어:
- 오른쪽 노드: H = 40
- 위쪽 노드: H = 35
- 오른쪽 위 대각선: H = 30

→ H가 가장 낮은 "오른쪽 위 대각선" 노드를 우선 탐색
   (목표에 더 가까워 보이니까!)

```

### Step 4: 계속 탐색

```
선택된 노드의 이웃들을 또 확인:
- 위 → 탐색 ✓
- 오른쪽 → 탐색 ✓
- 대각선 → 탐색 ✓
- 아래 → 이미 Close List에 있음 ✗

→ 이 중 하나가 목표 노드 B일 수 있음!

```

### Step 5: 목표 노드 도달

```
탐색 중인 노드 중 하나가 목표 노드 B와 일치!

→ 알고리즘 종료!
→ 경로 추적 시작

```

## 9. 알고리즘 종료 조건과 경로 추적

### 알고리즘이 멈추는 시점

- **현재 탐색 중인 노드 = 목표 노드**일 때
- "목표 지점에 도착했다!"

### 경로 역추적 (Backtracking)

목표 노드에서부터 **거꾸로** 시작 노드까지 경로를 추적합니다.

### 부모 노드(Parent Node) 개념

- 각 노드는 **자기를 탐색하게 만든 이전 노드**를 기억
- 이것을 "부모 노드" 또는 "이전 노드"라고 함

### 경로 추적 과정

```
목표 노드 B:
  ← 이전 노드는? 노드 X

노드 X:
  ← 이전 노드는? 노드 Y

노드 Y:
  ← 이전 노드는? 노드 Z

노드 Z:
  ← 이전 노드는? 시작 노드 A

→ 최종 경로: A → Z → Y → X → B

```

### 최종 경로 리스트

```
알고리즘 결과물:
[A, Z, Y, X, B]

이 리스트를 따라가면:
- 유닛이 A에서 출발
- Z를 거쳐
- Y를 거쳐
- X를 거쳐
- B에 도착!

```

## 10. 실제 게임에서의 패스파인딩 사용

### 성능 고려사항

### 전문 에셋 사용 권장

강의에서는 **실제 게임을 만들 때는 전문 패스파인딩 에셋을 사용하라**고 권장합니다.

**이유:**

- A\* 알고리즘 자체는 구현하기 쉬움
- 하지만 **성능을 최적화**하는 것은 매우 어려움
- 전문 에셋들은 수년간의 최적화가 되어 있음

### 턴 기반 게임에서는 괜찮음

이 강의의 경우:

- **턴 기반 전략 게임**을 만들고 있음
- 경로 계산에 1초 정도 걸려도 문제없음
- 실시간 게임처럼 즉각 반응이 필요하지 않음

### 실시간 게임 vs 턴 기반 게임

### 실시간 게임 (RTS, 액션 등)

- 경로 계산이 **즉시** 일어나야 함
- 0.1초 이상 걸리면 게임이 버벅임
- **최적화가 매우 중요**

### 턴 기반 게임 (이 강의의 경우)

- 플레이어가 명령을 내리고 기다림
- 1~2초 정도 계산 시간은 괜찮음
- **학습 목적으로 직접 구현해도 충분**

### 교육적 가치

강의에서 직접 구현하는 이유:

- **알고리즘의 원리를 깊이 이해**하기 위해
- 나중에 문제가 생겼을 때 **디버깅** 능력 향상
- 다른 알고리즘을 배울 때 **기초 지식**으로 활용

---

## 📝 정리

### A\* 알고리즘 핵심 요약

1. **목표** : 그리드 기반 맵에서 시작점(A)부터 목표점(B)까지 최적 경로 찾기
2. **3가지 비용**:
   - G = 시작부터 현재까지 실제 비용
   - H = 현재부터 목표까지 예상 비용
   - F = G + H (총 비용)
3. **이동 비용**:
   - 직선 (상하좌우) = 10
   - 대각선 = 14
4. **탐색 방법**:
   - Open List에서 F가 가장 낮은 노드 선택
   - 선택한 노드를 Close List로 이동
   - 이웃 노드들 검사 후 Open List에 추가
   - 목표 노드를 찾거나 Open List가 빌 때까지 반복
5. **경로 추적**:
   - 각 노드는 부모 노드를 기억
   - 목표에서 시작점까지 거꾸로 추적
   - 최종 경로 리스트 완성

## 1. 길찾기가 뭔가요?

### 일상생활 예시로 이해하기

**상황**: 집에서 학교까지 가려고 해요.

```
🏠 (집) ------> 🏫 (학교)
```

근데 중간에 **공사 중인 길**이 있어요!

```
🏠 (집) ---> 🚧 (공사중) ---> 🏫 (학교)
           (못 지나감!)
```

그럼 어떻게 해야 할까요?
→ **돌아가는 길**을 찾아야겠죠!

```
🏠 (집)
  ↓
  ↓ (아래로 우회)
  ↓
  → → → 🏫 (학교)
```

게임에서도 똑같아요!

- 유닛(캐릭터)이 A 지점에서 B 지점으로 가려고 함
- 중간에 벽이 있으면 못 지나감
- **자동으로 돌아가는 길**을 찾아주는 게 바로 **길찾기 알고리즘**!

## 2. A\* 알고리즘은 뭐하는 건가요?

### 바둑판처럼 생긴 맵

게임 맵을 **바둑판처럼 칸칸이 나눠놓았다**고 생각해보세요.

```
□ □ □ □ □
□ ■ ■ □ □
□ □ □ □ □
□ □ ■ □ □
□ □ □ □ □
```

- `□` = 걸을 수 있는 칸
- `■` = 벽이라서 못 가는 칸

### A\*가 하는 일

1. **출발점**과 **도착점**을 알려줌
2. A\* 알고리즘이 **가장 짧은 길**을 찾아줌
3. 가야 할 칸들의 **순서**를 알려줌

**예시:**

```
시작(A)
  ↓
칸1 → 칸2 → 칸3
            ↓
            목표(B)
```

이렇게 "칸1 → 칸2 → 칸3 → 목표" 순서로 가라고 알려주는 거예요!

---

## 3. 노드가 뭔가요?

### 노드 = 바둑판의 한 칸

어려운 용어지만 사실 간단해요!

- **노드(Node)** = 바둑판의 **한 칸**을 멋있게 부르는 말

```
이 □ 하나 = 노드 1개
```

### 8방향으로 움직일 수 있어요

한 칸에서 주변 8개 칸으로 갈 수 있어요:

```
□ □ □
□ 나 □  ← 여기가 "나"
□ □ □
```

- **상하좌우 4방향** ↑ ↓ ← →
- **대각선 4방향** ↖ ↗ ↙ ↘

---

## 4. G 비용 - 여기까지 온 거리

### G = 출발점에서부터 걸어온 거리

**만보기**를 생각하면 쉬워요!

```
출발! (만보기: 0걸음)
  ↓
한 칸 걸음 (만보기: 10걸음)
  ↓
또 한 칸 걸음 (만보기: 20걸음)
  ↓
또 한 칸 걸음 (만보기: 30걸음)
```

- **G 비용** = 출발점부터 **여기까지 걸은 총 걸음 수**

### 걸음 수 세는 방법

### 옆으로 한 칸 = 10걸음

```
나 → □  = 10걸음 추가
```

### 대각선 한 칸 = 14걸음

```
나 ↘ □  = 14걸음 추가
```

왜 14일까요?

- 대각선은 옆으로도 가고 위로도 가는 거라서 **조금 더 멀어요**
- 수학 계산하면 1.4배 더 멀어요
- 10 × 1.4 = 14

**예시:**

```
출발(G=0)
  ↓ (옆으로 10)
  (G=10)
  ↓ (옆으로 10)
  (G=20)
  ↘ (대각선 14)
  (G=34)
```

---

## 5. H 비용 - 목적지까지 남은 거리

### H = 목적지까지 **대충** 얼마나 남았을까?

**자동차 내비게이션**을 생각해보세요!

```
"목적지까지 약 500m 남았습니다"
```

정확히 500m는 아니지만, **대략** 그 정도라는 뜻이죠?

### H 비용 계산 방법

**벽을 다 무시하고** 직선거리로 계산해요!

```
현재: 나
목표: 🎯

나 .......... 🎯
  (직선으로 가면 얼마나 걸릴까?)
```

실제로는 벽 때문에 돌아가야 하지만, **어림잡기**니까 상관없어요!

### 왜 어림잡기를 하나요?

**어느 쪽으로 가는 게 좋을지** 판단하려고요!

```
길 A: H = 100 (목표까지 멀어 보임)
길 B: H = 30 (목표까지 가까워 보임)

→ 길 B를 먼저 가보자!
```

---

## 6. F 비용 - 전체 거리

### F = G + H (여기까지 온 거리 + 남은 거리)

**총 거리**를 계산하는 거예요!

```
G = 여기까지 걸어온 거리 = 30
H = 목표까지 남은 거리 = 40
F = 30 + 40 = 70 (총 거리)
```

### 왜 F를 계산하나요?

**어느 길이 더 좋은지** 비교하려고요!

```
길 A:
  G = 20 (여기까지 20걸음)
  H = 50 (남은 거리 50)
  F = 70 (총 70걸음)

길 B:
  G = 30 (여기까지 30걸음)
  H = 20 (남은 거리 20)
  F = 50 (총 50걸음)

→ 길 B가 더 짧으니까 길 B로 가자!
```

## 7. 어떤 길을 먼저 가볼까?

### Open List = 앞으로 가볼 곳 목록

**여행 계획**을 세운다고 생각해보세요!

```
가볼 만한 곳 목록:
- 명동 (F = 50)
- 강남 (F = 30)
- 홍대 (F = 70)
```

어디부터 갈까요? → **F가 제일 작은 곳**부터!
→ 강남(30)부터 가보자!

### Close List = 이미 가본 곳 목록

```
이미 가본 곳:
- 명동 ✓
- 강남 ✓
```

이미 가본 곳은 **다시 안 가요!**

### 탐색 순서

```
1. Open List에서 F가 제일 작은 곳을 골라요
2. 그곳을 Close List로 옮겨요 (이미 갔으니까)
3. 그곳 주변을 둘러봐요
4. 새로 발견한 곳들을 Open List에 추가해요
5. 목적지를 찾을 때까지 반복!
```

## 8. 실제로 어떻게 길을 찾나요?

### 단계별로 따라가보기

**상황:**

```
🏠 = 출발점
🎯 = 목적지
■ = 벽

🏠 □ □ □ □
□ ■ ■ □ □
□ □ □ □ 🎯
```

### Step 1: 출발!

```
🏠 출발점에서 시작
   ↓ ↘ →  (주변 3곳 확인)

Open List에 추가:
- 아래칸 (F=계산값)
- 오른쪽칸 (F=계산값)
- 대각선칸 (F=계산값)
```

### Step 2: F가 제일 작은 곳으로 이동

```
F가 제일 작은 곳 = 오른쪽칸

오른쪽칸에서 주변 확인:
- 위 → 가능 ✓
- 아래 → 벽! ✗
- 오른쪽 → 가능 ✓
```

### Step 3: 계속 반복

```
매번:
1. F가 제일 작은 칸을 선택
2. 그 칸 주변을 확인
3. 새로 발견한 칸들을 목록에 추가
4. 목적지를 찾을 때까지 반복!
```

### Step 4: 목적지 발견!

```
어? 이번에 확인한 칸이 🎯 목적지네?
→ 찾았다! 멈춰!
```

## 9. 길을 찾았으면 어떻게 하나요?

### 거꾸로 추적하기

각 칸은 **"어디서 왔는지"를 기억**하고 있어요!

```
🎯 (목적지) ← 어디서 왔지? 칸3에서!
칸3 ← 어디서 왔지? 칸2에서!
칸2 ← 어디서 왔지? 칸1에서!
칸1 ← 어디서 왔지? 🏠에서!
```

### 순서 뒤집기

거꾸로 추적한 걸 **다시 뒤집으면**:

```
🏠 → 칸1 → 칸2 → 칸3 → 🎯

최종 경로 완성!
```

### 게임 캐릭터가 이동

```
캐릭터: "알겠어! 이 순서대로 움직일게!"

🏠 출발
  ↓
칸1 도착
  ↓
칸2 도착
  ↓
칸3 도착
  ↓
🎯 목적지 도착!
```

### 실제 사용 예

1. **플레이어가 클릭**: "여기로 가!"
2. _A 알고리즘 실행_: 경로 계산 중...
3. **경로 완성**: [출발→칸1→칸2→칸3→목적지]

- 실시간 게임이었다면 빨라야 하지만, 우리 게임은 괜찮아요!

## 2. PathNode 클래스 만들기

### 2.1 PathNode 스크립트 생성

- Scripts 폴더에 새 C# 스크립트 생성
- 이름: `PathNode`
- **MonoBehaviour를 상속하지 않음** (데이터 클래스이므로)

### 2.2 기본 구조와 생성자

```csharp
using UnityEngine;

public class PathNode
{
    // 이 노드가 Grid 상에서 어느 위치에 있는지 저장
    private GridPosition gridPosition;

    // 생성자: PathNode를 생성할 때 반드시 위치를 지정해야 함
    public PathNode(GridPosition gridPosition)
    {
        this.gridPosition = gridPosition;
    }
}
```

**개념 설명:**

- **PathNode**: Grid의 각 셀을 나타내는 데이터 객체
- **GridPosition**: 이전에 만든 구조체로, x, z 좌표를 저장
- 생성자를 통해 반드시 위치 정보를 받아야 함

### 2.3 ToString() 메서드 오버라이드

```csharp
public class PathNode
{
    private GridPosition gridPosition;

    public PathNode(GridPosition gridPosition)
    {
        this.gridPosition = gridPosition;
    }

    // Debug 출력 시 어떻게 표시될지 정의
    // GridObject와 달리 Unit 정보는 필요 없으므로 위치만 출력
    public override string ToString()
    {
        return gridPosition.ToString();
    }
}
```

**개념 설명:**

- `ToString()`: 객체를 문자열로 변환할 때 호출되는 메서드
- Debug용으로 유용함
- GridPosition의 ToString()을 그대로 활용

### 2.4 Cost 관련 변수 추가

```csharp
public class PathNode
{
    private GridPosition gridPosition;

    // G Cost: 시작 노드로부터 이 노드까지의 실제 이동 비용
    private int gCost;

    // H Cost: 이 노드에서 목표 노드까지의 추정 비용 (휴리스틱)
    private int hCost;

    // F Cost: G Cost + H Cost (A* 알고리즘의 핵심 값)
    private int fCost;

    public PathNode(GridPosition gridPosition)
    {
        this.gridPosition = gridPosition;
    }

    public override string ToString()
    {
        return gridPosition.ToString();
    }
}
```

\*A 알고리즘 Cost 개념:\*\*

- **G Cost (이동 비용)**:
  - 시작점에서 현재 노드까지 실제로 이동하는 데 든 비용
  - 대각선 이동은 더 큰 값, 직선 이동은 작은 값
- **H Cost (휴리스틱 비용)**:
  - 현재 노드에서 목표까지의 예상 거리
  - 실제 경로를 모르므로 "추정"값
  - 보통 직선 거리를 사용
- **F Cost (총 비용)**:
  - F = G + H
  - A\* 알고리즘은 F Cost가 가장 낮은 노드를 선택
  - 이를 통해 최적 경로를 찾음

### 2.5 경로 추적을 위한 참조 변수

```csharp
public class PathNode
{
    private GridPosition gridPosition;
    private int gCost;
    private int hCost;
    private int fCost;

    // 이 노드에 도달하기 위해 거쳐온 이전 노드의 참조
    // 최종 목표에 도달한 후, 역으로 추적하여 경로를 재구성할 때 사용
    private PathNode cameFromPathNode;

    public PathNode(GridPosition gridPosition)
    {
        this.gridPosition = gridPosition;
    }

    public override string ToString()
    {
        return gridPosition.ToString();
    }
}
```

**개념 설명:**

- **cameFromPathNode**: "이전 노드" 참조
- A\* 알고리즘의 동작 방식:
  1. 시작점에서 목표점을 향해 노드를 탐색
  2. 각 노드에 "어느 노드에서 왔는지" 기록
  3. 목표에 도달하면, cameFromPathNode를 따라 역추적
  4. 역추적 경로를 뒤집으면 → 최종 경로 완성

## 3. Grid System에 PathNode 적용하기

### 3.1 GridSystem 인스턴스 생성

```csharp
public class Pathfinding : MonoBehaviour
{
    private int width;
    private int height;
    private float cellSize;

    // Generic으로 만든 GridSystem을 PathNode 타입으로 사용
    private GridSystem<PathNode> gridSystem;

    private void Awake()
    {
        // GridSystem<PathNode> 생성
        // 파라미터:
        // 1. width: 10 (x축 셀 개수)
        // 2. height: 10 (z축 셀 개수)
        // 3. cellSize: 2f (각 셀의 실제 크기)
        // 4. Func 델리게이트: 각 셀에 PathNode를 생성하는 함수
        gridSystem = new GridSystem<PathNode>(
            10,
            10,
            2f,
            (GridSystem<PathNode> g, GridPosition gridPosition) => new PathNode(gridPosition)
        );
    }
}
```

**개념 설명:**

**왜 Generic을 사용했나?**

- 이전 강의에서 GridSystem을 Generic으로 리팩토링했음
- LevelGrid에서는 `GridSystem<GridObject>` 사용
- Pathfinding에서는 `GridSystem<PathNode>` 사용
- 같은 Grid 시스템 코드를 다른 타입으로 재사용 가능

**Func 델리게이트 설명:**

```csharp
(GridSystem<PathNode> g, GridPosition gridPosition) => new PathNode(gridPosition)
```

- Lambda 표현식으로 작성된 함수
- GridSystem 생성자가 각 셀을 초기화할 때 호출
- 파라미터:
  - `g`: GridSystem 자신의 참조 (여기서는 사용 안 함)
  - `gridPosition`: 현재 생성 중인 셀의 위치
- 반환값: 새로운 PathNode 인스턴스

**값의 의미:**

- `10, 10`: LevelGrid와 동일한 크기의 Grid
- `2f`: 각 셀이 2x2 Unity 유닛 크기

### 3.2 코드 구조 개선 여지

강의에서 언급한 개선점:

```csharp
// 현재 방식: 값이 중복됨
// LevelGrid: new GridSystem<GridObject>(10, 10, 2f, ...)
// Pathfinding: new GridSystem<PathNode>(10, 10, 2f, ...)

// 개선 방안:
// LevelGrid에서만 값을 정의하고
// LevelGrid가 Pathfinding을 초기화하도록 변경
// 하지만 지금은 단순하게 유지
```

**발생한 문제:**

```csharp
// GridSystem.cs의 CreateDebugObjects 메서드 내부
public void CreateDebugObjects(Transform debugPrefab)
{
    for (int x = 0; x < width; x++)
    {
        for (int z = 0; z < height; z++)
        {
            GridPosition gridPosition = new GridPosition(x, z);
            Transform debugTransform = GameObject.Instantiate(debugPrefab, GetWorldPosition(gridPosition), Quaternion.identity);
            GridDebugObject gridDebugObject = debugTransform.GetComponent<GridDebugObject>();

            // 문제 발생 지점:
            // PathNode는 GridObject로 변환될 수 없음
            // 이전 코드: gridDebugObject.SetGridObject((GridObject)GetGridObject(gridPosition));

            // 해결: 캐스팅 제거

        }

```

**문제 원인:**

**해결 방법:**

- 캐스팅 제거
- Generic 타입 `TGridObject`를 그대로 전달
- `SetGridObject`가 `object` 타입을 받도록 수정 (다음 섹션)

## 6. GridDebugObject 베이스 클래스 리팩토링

### 6.1 문제점 파악

기존 GridDebugObject:

```csharp
public class GridDebugObject : MonoBehaviour
{
    [SerializeField] private TextMeshPro textMeshPro;
    private GridObject gridObject; // 문제: 특정 타입에 종속

    public void SetGridObject(GridObject gridObject)
    {
        this.gridObject = gridObject;
    }

    private void Update()
    {
        textMeshPro.text = gridObject.ToString();
    }
}
```

**문제:**

- `GridObject` 타입만 받을 수 있음
- PathNode를 사용하려면 수정 필요
- Generic이 아니므로 유연성 부족

### 6.2 Object 타입으로 변경

```csharp
public class GridDebugObject : MonoBehaviour
{
    [SerializeField] private TextMeshPro textMeshPro;

    // GridObject → object로 변경
    // object는 C#의 최상위 클래스
    // 모든 타입을 담을 수 있는 범용 컨테이너
    private object gridObject;

    // virtual: 자식 클래스에서 override 가능
    public virtual void SetGridObject(object gridObject)
    {
        this.gridObject = gridObject;
    }

    // protected: 자식 클래스에서 접근 가능
    // virtual: 자식 클래스에서 override 가능
    protected virtual void Update()
    {
        // object도 ToString()을 가지고 있음
        // 모든 C# 클래스는 object를 상속받기 때문
        textMeshPro.text = gridObject.ToString();
    }
}

```

**개념 설명:**

**object 타입:**

```csharp
// C#의 타입 계층 구조
object (최상위)
  ├─ PathNode
  ├─ GridObject
  ├─ string
  ├─ int
  └─ ... 모든 타입

```

- 모든 C# 클래스는 암묵적으로 `object`를 상속
- 따라서 어떤 타입이든 `object` 변수에 저장 가능
- `ToString()` 메서드는 object에 정의되어 있으므로 모든 타입이 사용 가능

**virtual 키워드:**

- 메서드를 "재정의 가능"하게 만듦
- 자식 클래스에서 `override` 키워드로 새로운 구현 제공 가능
- 기본 동작은 유지되지만, 필요시 커스터마이즈 가능

**protected 키워드:**

- `private`: 같은 클래스에서만 접근 가능
- `public`: 모든 곳에서 접근 가능
- `protected`: 같은 클래스 + 자식 클래스에서 접근 가능

## 7. 비용(Cost) 시각화 구현

### 7.1 SetGridObject Override

```csharp
public class PathfindingGridDebugObject : GridDebugObject
{
    [SerializeField] private TextMeshPro gCostText;
    [SerializeField] private TextMeshPro hCostText;
    [SerializeField] private TextMeshPro fCostText;

    private PathNode pathNode;

    // base 클래스의 SetGridObject를 override
    public override void SetGridObject(object gridObject)
    {
        // 먼저 부모 클래스의 기능 실행
        // 이렇게 하면 base.gridObject에도 저장됨
        base.SetGridObject(gridObject);

        // object를 PathNode로 형변환 (Casting)
        // 우리는 이 함수가 PathNode와 함께 호출될 것을 알고 있음
        pathNode = (PathNode)gridObject;
    }
}
```

**개념 설명:**

**base 키워드:**

- 부모 클래스의 메서드를 호출할 때 사용
- `base.SetGridObject(gridObject)`: 부모의 원래 기능 실행
- 부모의 기능을 완전히 대체하는 것이 아니라, 확장하는 것

**형변환 (Casting):**

```csharp
pathNode = (PathNode)gridObject;
```

- `gridObject`는 `object` 타입 (범용)
- 하지만 실제로는 `PathNode`가 들어있음
- `(PathNode)`: "이 object를 PathNode로 취급하겠다"
- 만약 실제로 PathNode가 아니면 런타임 에러 발생

**왜 이렇게 복잡하게?**

1. 베이스 클래스는 범용성을 위해 `object` 사용
2. 자식 클래스는 구체적인 타입(`PathNode`)으로 작업
3. 유연성과 타입 안정성을 모두 확보

### 7.2 PathNode Getter 메서드 추가

```csharp
// PathNode.cs
public class PathNode
{

    private int gCost;
    private int hCost;
    private int fCost;
    private PathNode cameFromPathNode;

    public PathNode(GridPosition gridPosition)

    // Getter 메서드들: private 변수를 외부에서 읽을 수 있게 해줌
    public int GetGCost()
    {

    }

    public int GetHCost()
    {
        return hCost;
    }

    public int GetFCost()
    {
        return fCost;
    }

```

**개념 설명:**

**Getter 메서드의 필요성:**

```csharp
// 변수는 private이므로 외부에서 직접 접근 불가:
// pathNode.gCost // ❌ 에러!

// Getter를 통해 읽기만 가능하게:
int cost = pathNode.GetGCost(); // ✅ 가능
```

**캡슐화 (Encapsulation):**

- 데이터는 private으로 보호
- 필요한 데이터만 public 메서드로 제공
- 외부에서 함부로 값을 변경하지 못하게 방지

### 7.3 Update Override로 Cost 표시

```csharp
public class PathfindingGridDebugObject : GridDebugObject
{
    [SerializeField] private TextMeshPro gCostText;
    [SerializeField] private TextMeshPro hCostText;
    [SerializeField] private TextMeshPro fCostText;

    private PathNode pathNode;

    public override void SetGridObject(object gridObject)
    {
        base.SetGridObject(gridObject);
        pathNode = (PathNode)gridObject;
    }

    // Update도 override하여 커스텀 동작 추가
    protected override void Update()
    {
        // 먼저 부모의 Update 실행
        // 중앙 텍스트(GridPositionText)가 업데이트됨
        base.Update();

        // PathNode의 G Cost를 가져와서 문자열로 변환 후 표시
        gCostText.text = pathNode.GetGCost().ToString();

        // H Cost 표시
        hCostText.text = pathNode.GetHCost().ToString();

        // F Cost 표시
        fCostText.text = pathNode.GetFCost().ToString();
    }
}

```

**실행 흐름:**

```
매 프레임마다:
1. base.Update() 호출
   └─> GridDebugObject의 Update 실행
       └─> 중앙 textMeshPro에 gridObject.ToString() 표시
           └─> PathNode.ToString() 호출
               └─> GridPosition 표시 (예: "3, 5")

2. gCostText.text = ... 실행
   └─> PathNode에서 G Cost 가져오기
       └─> 문자열로 변환
           └─> 좌상단 텍스트에 표시

3. hCostText, fCostText도 동일
```

### 7.4 GridSystem의 타입 처리 수정

```csharp
// GridSystem.cs
public class GridSystem<TGridObject>
{
    // CreateDebugObjects 메서드 내부
    public void CreateDebugObjects(Transform debugPrefab)
    {
        for (int x = 0; x < width; x++)
        {
            for (int z = 0; z < height; z++)
            {
                GridPosition gridPosition = new GridPosition(x, z);
                Transform debugTransform = GameObject.Instantiate(
                    debugPrefab,
                    GetWorldPosition(gridPosition),
                    Quaternion.identity
                );

                GridDebugObject gridDebugObject = debugTransform.GetComponent<GridDebugObject>();

                // 수정: 캐스팅 제거, 그대로 전달
                // TGridObject (Generic 타입)를 object로 자동 변환
                gridDebugObject.SetGridObject(GetGridObject(gridPosition));
            }
        }
    }
}
```

**왜 작동하는가?**

```csharp
// TGridObject는 어떤 타입이든 될 수 있음
// PathNode, GridObject, 등등

// object는 모든 타입을 받을 수 있음
// 따라서 TGridObject → object 변환은 항상 안전함 (업캐스팅)

// SetGridObject(object gridObject)가 받으면
// PathfindingGridDebugObject에서 다시 PathNode로 변환 (다운캐스팅)
```

### 7.6 최종 테스트 및 확인

플레이 버튼을 누르면:

```
각 Grid 셀마다:
┌─────────────────┐
│  0        (G)   │  ← 좌상단: G Cost
│                 │
│     3, 5        │  ← 중앙: Grid Position
│                 │
│  0  (F)    0(H) │  ← 좌하단: F Cost, 우하단: H Cost
└─────────────────┘

```

**현재 상태:**

- 모든 Cost 값은 0 (아직 계산 안 함)
- Grid Position만 제대로 표시됨
- PathNode 초기화 시 Cost를 설정하지 않았으므로 기본값 0

**다음 단계 예고:**

- 다음 강의에서 실제 A\* 알고리즘 구현
- Cost 값들이 동적으로 계산되고 업데이트됨
- 경로 찾기 과정을 시각적으로 확인 가능
