## 1. 드로우 콜이란?

### 기본 개념

**드로우 콜(Draw Call)** = CPU가 GPU에게 "이것을 화면에 그려라"고 보내는 명령 1회

```
게임 화면 = 수많은 오브젝트의 조합
각 오브젝트를 그리려면 → CPU가 GPU에게 명령 필요
이 명령 횟수 = 드로우 콜
```

### 레스토랑 비유

```
CPU (주방장):
- 명령서를 작성하고 전달하는 사람
- 생각보다 느림 (병목 발생 지점)

GPU (요리사들):
- 실제로 그리는 작업을 하는 사람
- 엄청나게 빠름

드로우 콜 (주문서):
- 주방장이 요리사에게 전달하는 지시서
- 주문서가 많으면 → 주방장이 바빠서 병목
```

**핵심 포인트:**

- GPU는 빠른데 CPU가 명령 전달하느라 바쁘면 → 성능 저하
- 드로우 콜을 줄인다 = 주문서를 통합한다

### 왜 문제가 되나?

```
나쁜 경우:
- 나무 100그루 각각 명령 → 드로우 콜 100개
- CPU: "나무1 그려!" "나무2 그려!" ... (100번 반복)

좋은 경우:
- 나무 100그루 한 번에 명령 → 드로우 콜 1개
- CPU: "같은 나무 100그루 한꺼번에 그려!"
```

**결과:**

- 드로우 콜 많음 → CPU 병목 → 프레임 드롭 → 게임 버벅임
- 드로우 콜 적음 → CPU 여유 → 높은 FPS → 부드러운 게임

# ✔️ 더 정확한 설명

### 🎮 **1. 프레임은 매번 새로 그려져야 함**

게임 화면은 1초에 60프레임이라면 **60번 다시 그려짐**.

그리고 _각 프레임마다 CPU → GPU로 draw call 요청이 계속 간다._

---

### 🧠 **2. 드로우 콜은 CPU에서 GPU로 “렌더링 명령” 보내는 행위**

드로우 콜에는 이런 내용이 담겨 있어:

- 어떤 Mesh를
- 어떤 Material로
- 어떤 셰이더 상태로
- 어떤 트랜스폼(좌표)로
- 어떤 텍스처를 사용해서
- 어떤 조명 조건으로

**그려라!**

이걸 CPU가 정리한 뒤 GPU로 보냄.

---

### 🔁 **3. 왜 매 프레임마다 또 보내야 할까?**

- 오브젝트가 움직일 수 있고
- 애니메이션이 변하고
- 카메라가 이동하고
- 조명이 바뀔 수도 있고
- 이펙트나 파티클도 변하니까

**GPU는 과거 상태를 기억하고 알아서 갱신하는 게 아니라,
CPU가 매 프레임 “지금 상황에 맞는 명령”을 계속 보내줘야 한다.**

그래서 draw call이 많으면 CPU가 바빠져서 병목이 생김.

---

# 💡 아주 쉽게 예시로 설명하면

CPU가 GPU에게 같은 장면을 계속 말로 설명해야 한다고 치면…

```
1프레임:
  "나무 1을 (0,0) 위치에 고유한 머티리얼로 그려!"
  "바위 1을 (1,0) 위치에 다른 머티리얼로 그려!"
  "플레이어를 스켈레톤 애니메이션 12번 상태로 그려!"
  ...

2프레임:
  "나무 1은 그대로인데 다시 그려!"
  "바위 1은 그대로인데 다시 그려!"
  "플레이어는 애니메이션 13번 상태로 그려!"
```

이렇게 **매 프레임 매번 새로 말해야 함.**

# ✔️ 정리

### 드로우 콜 = CPU가 GPU에게 매 프레임 보낸 “그려라” 명령.

- 매 프레임 새 요청이 맞다.
- CPU가 데이터를 준비해서 GPU에 전달한다.
- 드로우 콜 수가 많으면 CPU 병목이 발생한다.
- 그래서 **배칭, 인스턴싱** 같은 기술이 필요하다.

## 2. 드로우 콜이 증가하는 주요 원인

### 원인 1: 서로 다른 머티리얼 사용 ⭐ (가장 흔한 원인)

```
✅ 좋은 예:
빨간 공 100개 (같은 머티리얼)
→ 드로우 콜 1개 (배칭됨)

❌ 나쁜 예:
빨간 공 50개 + 파란 공 50개 (다른 머티리얼)
→ 드로우 콜 2개

❌ 최악의 예:
각기 다른 색상의 공 100개 (머티리얼 100개)
→ 드로우 콜 100개
```

**해결책:**

- 가능하면 같은 머티리얼 재사용
- 색상 차이만 필요하면 → Texture Atlas 또는 Vertex Color 사용

### 원인 2: Realtime Light 과다 사용 💡

```
Forward Rendering에서:
오브젝트 1개 × Realtime Light 3개
= 드로우 콜 3개 (라이트마다 추가 계산)

예시:
- 사무실 책상 100개
- Realtime Light 5개
→ 최악의 경우 드로우 콜 500개!
```

**해결책:**

- Baked Lighting 사용 (드로우 콜 증가 없음)
- Pixel Light Count 제한 (1~2개 권장)
- Deferred Rendering 고려 (PC 타겟)

### 원인 3: 여러 카메라 사용 📷

```
카메라마다 전체 씬을 다시 렌더링:
- Main Camera: 드로우 콜 100개
- Minimap Camera: 드로우 콜 100개
- UI Camera: 드로우 콜 50개
= 총 250개
```

**해결책:**

- 카메라 수 최소화
- Culling Mask로 필요한 것만 렌더링
- Render Texture 해상도 낮추기

### 원인 4: UI 요소 과다 🖼️

```
각 UI Image가 다른 텍스처 사용:
- UI 요소 30개 × 각기 다른 이미지
→ 드로우 콜 30개
```

**해결책:**

- UI Atlas 사용 (여러 이미지를 하나의 텍스처로 통합)
- 같은 Atlas의 UI는 배칭됨
- Canvas 분리 전략 (정적/동적 분리)

### 원인 5: 투명/반투명 오브젝트 🪟

```
투명 오브젝트:
- 배칭이 어려움 (렌더링 순서 중요)
- Sorting Layer마다 별도 드로우 콜
```

**예시:**

```
유리창 10개 (각기 다른 거리)
→ 거리순 정렬 필요
→ 배칭 불가
→ 드로우 콜 10개
```

**해결책:**

- 투명 오브젝트 최소화
- Alpha Test 대신 Alpha Blend 사용 검토
- Cutout 쉐이더는 배칭 가능

### 원인 6: 그림자(Shadow) 렌더링 🌑

```
Realtime Shadow:
- 그림자 생성용 추가 렌더링 Pass
- Light마다 Shadow Map 생성
→ 드로우 콜 2배~3배 증가 가능
```

**해결책:**

- Shadow Casting Mode: Off로 중요하지 않은 오브젝트 제외
- Shadow Distance 제한 (멀리 있는 그림자 안 그림)
- Shadow Cascades 수 줄이기

### 원인 7: 파티클 시스템 ✨

```
각 파티클 시스템 = 별도 드로우 콜:
- 연기 이펙트: 드로우 콜 1개
- 불꽃 이펙트: 드로우 콜 1개
- 먼지 이펙트: 드로우 콜 1개
```

**해결책:**

- 파티클 시스템 수 제한
- 같은 머티리얼 재사용
- GPU Instancing 활성화 (Particle System)

### 원인 8: Skinned Mesh (캐릭터/애니메이션) 🦴

```
Skinned Mesh Renderer:
- 배칭이 기본적으로 안 됨
- 각 캐릭터 = 별도 드로우 콜
```

**해결책:**

- GPU Skinning 사용
- LOD (Level of Detail) 적용
- 화면에 보이는 캐릭터 수 제한

## 3. 배칭(Batching) 시스템 이해하기

### 배칭이란?

**배칭(Batching)** = 여러 오브젝트를 하나의 드로우 콜로 묶어서 처리하는 기술

```
배칭 없이:
CPU: "나무1 그려!" "나무2 그려!" "나무3 그려!"
→ 드로우 콜 3개

배칭 있으면:
CPU: "나무 3개 한꺼번에 그려!"
→ 드로우 콜 1개
```

### 1) Static Batching (정적 배칭)

**대상:** 움직이지 않는 오브젝트

**설정 방법:**

```
1. 오브젝트 선택
2. Inspector 우측 상단 "Static" 체크박스 ✅
3. "Batching Static" 옵션 선택
```

**조건:**

- ✅ 같은 머티리얼 사용
- ✅ Static으로 마킹됨
- ✅ 움직이지 않음

**장점:**

- 런타임 오버헤드 거의 없음
- 효과가 확실함

**단점:**

- 메모리 사용량 증가 (메시 데이터 복제)
- 빌드 시간 증가

**Overtime 프로젝트 적용:**

```
Static 체크해야 할 것들:
- 벽, 바닥, 천장
- 책상, 의자 (고정된 가구)
- 장식 소품 (움직이지 않는)

Static 체크 안 해야 할 것들:
- 플레이어
- 문 (열리는 것)
- 움직이는 오브젝트
```

### 2) Dynamic Batching (동적 배칭)

**대상:** 움직이는 작은 오브젝트

**자동 조건:**

- 같은 머티리얼 사용
- 버텍스 수 300개 이하 (매우 중요!)
- 같은 스케일 (음수 스케일 사용 안 함)
- 같은 라이트맵 사용

**활성화:**

```
Edit → Project Settings → Player
→ Other Settings
→ Dynamic Batching ✅
```

**효과적인 사용:**

```
✅ 좋은 예:
- 작은 돌멩이 100개 (버텍스 50개)
- 같은 머티리얼
→ 배칭됨!

❌ 나쁜 예:
- 복잡한 캐릭터 모델 (버텍스 5000개)
- 같은 머티리얼
→ 배칭 안 됨 (버텍스 초과)
```

**주의사항:**

- CPU 오버헤드 있음 (매 프레임 계산)
- 버텍스 수 제한 엄격함
- 모바일에서는 신중하게 사용

### 3) GPU Instancing (GPU 인스턴싱)

**대상:** 같은 메시를 대량으로 사용하는 경우

**활성화 방법:**

```
1. Material 선택
2. Inspector에서 "Enable GPU Instancing" ✅
```

**조건:**

- 같은 메시 사용
- 같은 머티리얼 사용
- GPU Instancing 지원하는 쉐이더

**효과:**

```
나무 1000그루 (같은 모델):
- 배칭 없이: 드로우 콜 1000개
- GPU Instancing: 드로우 콜 1개
→ 극적인 성능 향상!
```

**언제 사용?**

- 풀, 나무, 바위 같은 자연물
- 총알, 파편 같은 대량 오브젝트
- 같은 적 캐릭터 다수

**Unity Standard Shader는 GPU Instancing 지원함!**

### 4) SRP Batcher (Scriptable Render Pipeline)

**대상:** URP/HDRP 사용 시

**조건:**

- URP/HDRP 사용 중
- SRP Compatible 쉐이더 사용
- 같은 쉐이더 (머티리얼은 달라도 됨!)

**장점:**

```
기존 배칭: 같은 머티리얼만 묶음
SRP Batcher: 같은 쉐이더면 묶음
→ 더 많은 오브젝트 배칭 가능
```

**활성화:**

```
Graphics Settings → SRP Asset
→ SRP Batcher ✅
```

## 4. 최적화 실전 가이드

### 체크리스트

### 1단계: 머티리얼 통합 ⭐⭐⭐

```
✅ 작업:
- 같은 용도의 오브젝트는 같은 머티리얼 사용
- Texture Atlas로 여러 텍스처 통합
- 색상 변화만 필요하면 Vertex Color 활용

예시:
❌ 나쁜 예: 책상1_Wood, 책상2_Wood, 책상3_Wood (머티리얼 3개)
✅ 좋은 예: Office_Furniture (머티리얼 1개, Atlas 사용)
```

### 2단계: Static 마킹 ⭐⭐⭐

```
✅ 작업:
- 움직이지 않는 모든 환경 오브젝트
- Inspector → Static ✅
- Batching Static 포함 확인

Overtime 프로젝트:
- 사무실 벽/바닥/천장
- 고정 가구 (책상, 서랍장, 선반)
- 장식 소품
```

### 3단계: 라이팅 최적화 ⭐⭐⭐

```
✅ 작업:
- 대부분의 라이트 → Baked로 변경
- Realtime Light 1~2개만 유지
- Pixel Light Count = 1

설정:
Edit → Project Settings → Quality
→ Pixel Light Count = 1
```

### 4단계: GPU Instancing 활성화 ⭐⭐

```
✅ 작업:
1. 반복적으로 사용되는 오브젝트의 머티리얼 선택
2. Enable GPU Instancing ✅

적용 대상:
- 사무실 의자 (같은 모델 여러 개)
- 복도 조명 (같은 모델)
- 소품 (펜, 컵, 서류 등)
```

### 5단계: UI 최적화 ⭐⭐

```
✅ 작업:
- Sprite Atlas 생성 및 적용
- Canvas 분리 (정적/동적)

Canvas 분리 전략:
Canvas 1 (Static): 배경, 고정 UI
Canvas 2 (Dynamic): 체력바, 점수 등 변하는 UI
→ 정적 Canvas는 재계산 안 함
```

### 6단계: 그림자 최적화 ⭐

```
✅ 작업:
Edit → Project Settings → Quality
→ Shadow Distance = 20~30 (필요한 범위만)
→ Shadow Cascades = 2 (기본 4에서 줄임)

오브젝트별:
- 중요하지 않은 소품 → Cast Shadows: Off
- 바닥 → Receive Shadows: On, Cast: Off
```

### 7단계: 카메라 최적화 ⭐

```
✅ 작업:
- 카메라 수 최소화 (꼭 필요한 것만)
- Culling Mask로 불필요한 레이어 제외
- Far Clip Plane 적절히 설정 (너무 멀리 안 그림)

Main Camera:
- Culling Mask: Everything 제외, 필요한 것만 선택
- Far Clip: 50~100 (Overtime 사무실 규모)
```

### 8단계: LOD 시스템 적용 ⭐

```
✅ 작업 (복잡한 모델에만):
1. 같은 모델의 저폴리곤 버전 준비
2. LOD Group 컴포넌트 추가
3. 거리별 모델 할당

거리 설정 예시:
- LOD 0 (0~10m): 고품질 모델 (버텍스 2000)
- LOD 1 (10~30m): 중품질 모델 (버텍스 500)
- LOD 2 (30~50m): 저품질 모델 (버텍스 100)
```

### 목표 수치


## 5. Stats 창 활용법

### Stats 창 열기

```
1. Game View 클릭
2. 우측 상단 "Stats" 버튼 클릭
```

### 주요 지표 해석

```
Batches: 152
- 실제 드로우 콜 수
- ⭐ 가장 중요한 지표
- 이 숫자를 낮추는 게 목표

Saved by batching: 48
- 배칭으로 절약된 드로우 콜 수
- 높을수록 배칭이 잘 되고 있음

Tris (Triangles): 45.2k
- 화면에 그려지는 삼각형 수
- 너무 높으면 GPU 부하

Verts (Vertices): 38.9k
- 화면에 그려지는 버텍스 수

SetPass calls: 145
- 렌더 상태 변경 횟수
- Batches와 비슷하게 낮을수록 좋음
```

### 실시간 테스트 방법

```
테스트 1: 머티리얼 영향 확인
1. Stats 창 열기
2. 오브젝트 10개 배치 (같은 머티리얼)
3. Batches 수치 확인
4. 각 오브젝트에 다른 머티리얼 적용
5. Batches 변화 관찰
→ 급증하면 머티리얼 통합 필요

테스트 2: Static 효과 확인
1. Stats 창 열기
2. 오브젝트 선택
3. Static 체크 해제 → Batches 확인
4. Static 체크 → Batches 확인
→ 감소하면 Static 배칭 작동 중

테스트 3: 라이트 영향 확인
1. Stats 창 열기
2. Realtime Light 하나씩 켜고 끄기
3. Batches 변화 관찰
→ 급증하는 라이트 제거 또는 Baked 전환
```

### Frame Debugger 활용 (고급)

```
Window → Analysis → Frame Debugger
→ "Enable" 클릭

기능:
- 각 드로우 콜이 무엇을 그리는지 확인
- 어떤 오브젝트가 배칭 안 되는지 파악
- 병목 지점 정확히 찾기

사용법:
1. 드로우 콜 목록에서 하나 클릭
2. 우측에 해당 드로우 콜 정보 표시
3. "Why this draw call can't be batched" 확인
→ 배칭 실패 이유 확인 가능
```
