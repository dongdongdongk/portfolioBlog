## 📍 나이아가라 시스템 컴포넌트 추가

### 1. 왼쪽 추진기 추가

```
BP_Kick 블루프린트 열기
  ↓
Mesh 선택
  ↓
Add Component → Niagara Particle System 검색
  ↓
이름: Thruster_Effect_L
```

**Niagara Particle System이란?**

- 언리얼의 파티클 이펙트 시스템
- 불, 연기, 폭발 같은 시각 효과 생성
- 컴포넌트로 추가하면 액터에 부착 가능

![image.png](https://res.cloudinary.com/du1acdhxq/image/upload/v1788380757/notion-blog/_/_/_5_/_8_-_3D_-_4/image.png)

```
Thruster_Effect_L 선택
  ↓
Details 패널
  ↓
Parent Socket
  └─ Browse 아이콘 클릭 → Thruster_L 선택
```

**Parent Socket이란?**

- 컴포넌트가 부착될 위치 지정
- 소켓을 선택하면 해당 위치/각도 자동 적용
- 본 대신 소켓 사용 이유: 오프셋 포함된 정확한 위치

## 📍 입력 액션 생성

### 1. 입력 액션 만들기

```
Content/Input 폴더
  ↓
우클릭 → Input Action
  └─ 이름: IA_Jetpack
```

**설정**

```
Value Type
  └─ Digital (bool) - 켜짐/꺼짐만 필요
```

**Digital (bool)이란?**

- True/False 두 가지 상태만 존재
- 버튼을 눌렀나(True), 안 눌렀나(False)
- 추진기는 켜짐/꺼짐만 필요하므로 적합

### 2. 입력 매핑 추가

```
IMC_Kick_Actions 열기
  ↓
Mappings 추가
  ├─ Input Action: IA_Jetpack
  └─ Key 설정
```

**키보드**

```
키 클릭
  ↓
Left Shift 입력
```

**게임패드**

```
+ 버튼으로 새 바인딩 추가
  ↓
키 클릭
  ↓
게임패드에서 오른쪽 트리거 입력
```

⚠️ **중요: Axis vs Button**

```
❌ Gamepad Right Trigger Axis
   └─ 0~1 사이 값 (압력 감지)

✅ Gamepad Right Trigger
   └─ 누름/안누름 (Digital)
```

**왜 Axis가 아닌가?**

- Axis: 트리거를 얼마나 세게 누르는지 측정 (0~1)
- Button: 단순히 눌렀는지만 체크 (True/False)
- 제트팩은 세기 조절 불필요, 켜짐/꺼짐만 필요

## 🔧 방법 1: 캐릭터에서 직접 처리

### Event Graph 구성

```
BP_Kick 이벤트 그래프
  ↓
우클릭 → IA_Jetpack 검색
```

### 블루프린트 노드

```
IA_Jetpack
  ├─ Started → Activate
  │   ├─ Thruster_Effect_R
  │   └─ Thruster_Effect_L
  │
  └─ Completed → Deactivate
      ├─ Thruster_Effect_R
      └─ Thruster_Effect_L
```

**노드 설명**

- `Started`: 키를 누르는 순간
- `Completed`: 키를 떼는 순간
- `Activate`: 컴포넌트 켜기
- `Deactivate`: 컴포넌트 끄기

**동작 원리**

```
Shift 누름
  ↓
Started 실행
  ↓
두 추진기 Activate
  ↓
이펙트 시작

Shift 뗌
  ↓
Completed 실행
  ↓
두 추진기 Deactivate
  ↓
이펙트 중지
```

## 🏗️ 방법 2: 인터페이스 활용 (권장)

### 왜 인터페이스를 사용하나?

**문제 상황**

```
Player Controller
  ↓
Get Controlled Character (Character 타입)
  ↓
❌ Thruster_Effect가 없음
```

![image.png](https://res.cloudinary.com/du1acdhxq/image/upload/v1788380756/notion-blog/_/_/_5_/_8_-_3D_-_4/image_4.png)

```csharp
컨트롤러에 이게 없어서 이걸 가지기 위해서는 Cast 를 해줘야 해서 문제가 생김
```

**나쁜 해결책: Cast 사용**

```
Player Controller
  ↓
Cast to BP_Kick
  ↓
❌ Player Controller가 BP_Kick에 의존
```

**의존성 문제란?**

- Player Controller는 범용 클래스
- 여러 캐릭터에서 재사용 가능해야 함
- 특정 캐릭터(BP_Kick)에 묶이면 안 됨

**좋은 해결책: Interface**

```
Player Controller
  ↓
Interface 함수 호출
  ↓
✅ 어떤 캐릭터든 Interface만 구현하면 작동
```

## ❓ 왜 Thruster_Effect가 없나?

### 타입 차이 때문

```
Player Controller의 Get Controlled Character
  ↓
반환 타입: Character (엔진 기본 클래스)
  ├─ 모든 캐릭터의 기본 기능만 포함
  └─ ❌ Thruster_Effect 없음

실제 우리 캐릭터: BP_Kick
  ├─ Character를 상속받음
  └─ ✅ Thruster_Effect 추가됨
```

### 비유

```
Character 클래스
  └─ "사람"이라는 일반 개념
      └─ 걷기, 점프 같은 기본 기능만

BP_Kick 클래스
  └─ "제트팩 든 특정 사람"
      └─ 기본 기능 + Thruster_Effect
```

### 해결 방법

**Cast 사용 (비추천)**

```
Character → Cast to BP_Kick
  └─ 특정 클래스에 의존
```

**Interface 사용 (권장)**

```
Character → Interface 함수 호출
  └─ 타입 상관없이 작동
```

## 🎮 Player Controller에서 처리

### Event Graph 구성

```
BP_Kick_PlayerController
  ↓
IA_Jetpack 노드 추가
```

### Started 처리

```
Started
  ↓
Get Controlled Character (validated)
  ├─ Is Valid → Start Jetpack
  └─ Is Not Valid → (무시)
```

**Get Validated란?**

- Get + 유효성 검사 자동 수행
- Controlled Character가 존재하면 Is Valid
- 존재하지 않으면 Is Not Valid

### Completed 처리

```
Completed
  ↓
Get Controlled Character (validated)
  ├─ Is Valid → Stop Jetpack
  └─ Is Not Valid → (무시)
```

### 최종 구조

```
Player Controller
  ├─ 입력 처리
  └─ Interface 함수 호출
       ↓
Character (BP_Kick)
  └─ Interface 구현
       └─ 실제 추진기 제어
```

## 📚 용어 정리

**Enhanced Input System**

- 언리얼의 새로운 입력 시스템
- Input Action으로 입력 추상화
- IMC로 키 매핑 관리

**Blueprint Interface**

- C++의 Interface와 동일 개념
- 여러 클래스가 같은 함수 구현
- Cast 없이 함수 호출 가능

**Dependency (의존성)**

- 한 클래스가 다른 클래스를 알아야 함
- 의존성 높을수록 수정 어려움
- Interface로 의존성 감소

**Validated Get**

- Get + 유효성 검사 자동
- Is Valid/Is Not Valid 핀 제공
- Null 체크 간편화

## 🚀 시작 사운드 구현 (Start Thruster Sound)

### 1. 함수 생성 준비

```
Event Start Jetpack에서
  ├─ Activate 노드들 분리
  └─ 사운드 재생 추가 예정
```

**왜 분리하나?**

- 단순 Activate만 → 추가 기능 필요
- 사운드 재생, 페이드 등 복잡해짐
- 함수로 분리해 관리 용이

### 2. Spawn Sound at Location 노드

```
Spawn Sound at Location
  ├─ Sound: MS_Thruster_Start
  ├─ Location: Get Actor Location (Self)
  ├─ Volume Multiplier: 0.6
  └─ Return Value → Audio Component
```

**각 설정의 의미**

**Sound (필수)**

- 재생할 사운드 파일 선택
- MS_Thruster_Start 할당

**Location (필수)**

```
Get Actor Location
  └─ 현재 캐릭터(Self)의 위치
  └─ 그 위치에서 소리 재생
```

**Volume Multiplier**

```
기본값: 1.0 (100%)
설정값: 0.6 (60%)
  └─ 소리가 너무 크면 조절
```

**Return Value**

```
Audio Component 오브젝트
  ├─ 재생 중인 사운드 제어 가능
  ├─ Stop, Pause, Fade 등
  └─ 이 레퍼런스로 사운드 조작
```

### 3. Fade Out 적용

```
Spawn Sound at Location
  ↓
Return Value
  ↓
Fade Out
  ├─ Fade Out Duration: 1.0초
  ├─ Fade Volume Level: 0.0
  └─ Fade Curve: Linear
```

**왜 Fade Out이 필요한가?**

```
문제
  └─ 시작 소리가 너무 길게 재생됨

해결
  └─ 1초 동안 서서히 볼륨 감소

효과
  └─ 자연스러운 전환
```

**Fade Out 옵션 설명**

**Target (자동 연결)**

- Audio Component 레퍼런스
- 어떤 소리를 페이드 할지 지정

**Fade Out Duration**

```
1.0초 설정
  └─ 1초에 걸쳐 볼륨 감소
```

**Fade Volume Level**

```
0.0 설정
  └─ 최종적으로 소리 완전 꺼짐
```

**Fade Curve**

```
Linear (선형)
  └─ 일정한 속도로 감소

다른 옵션
  ├─ Exponential: 점점 빠르게
  ├─ Logarithmic: 점점 느리게
  └─ S-Curve: 중간 빠름
```

### 4. 함수로 축소

```
노드 선택
  ↓
우클릭 → Collapse to Function
  └─ 이름: Start Thruster Sound

**함수로 만드는 이유**

```
장점

  ├─ 수정 시 한 곳만 변경
  └─ 디버깅 쉬움

## 🔁 반복 사운드 구현 (Looping Sound)

### 1. Spawn Sound Attached 노드

```
Spawn Sound Attached
  ├─ Sound: MS_Thruster_Loop
  ├─ Attach to Component: Capsule Component (Root)
  ├─ Location Type: Keep Relative Offset
  ├─ Location: (0, 0, 0)
  ├─ Volume Multiplier: 0.6
  └─ Auto Destroy: False (중요!)
```

**왜 Spawn Sound Attached를 사용하나?**

```
Spawn Sound at Location
  └─ 위치 고정, 캐릭터 이동 시 소리 멀어짐

Spawn Sound Attached
  └─ 캐릭터 따라다님, 항상 가까이 들림
```

**Attach to Component 설명**

```
Capsule Component 선택
  └─ 캐릭터의 Root Component

이유
  ├─ 캐릭터 중심에서 소리 재생
  ├─ 캐릭터 이동 시 함께 이동
  └─ 안정적인 위치
```

**Location Type 옵션**

```
Keep Relative Offset
  └─ 부모 컴포넌트 기준 상대 위치 유지

Snap to Target
  └─ 정확히 부모 위치에 붙음

Keep World Position
  └─ 월드 좌표 기준 (사용 안 함)
```

**Location (0, 0, 0)**

```
Relative Offset이므로
  └─ Capsule 중심에서 (0,0,0) 오프셋
  └─ 즉, Capsule 정중앙에서 재생
```

**Auto Destroy 중요!**

```
True
  └─ 재생 끝나면 자동 삭제

False
  └─ 계속 유지 (우리가 직접 제어)

우리 선택: False
  └─ 반복 재생 제어 위해 유지
```

### 2. Fade In 적용

```
Spawn Sound Attached
  ↓
Return Value
  ↓
Fade In
  └─ Fade In Duration: 0.35초
```

**왜 Fade In이 필요한가?**

```
문제
  └─ 반복 소리가 갑자기 시작됨

해결
  └─ 0.35초 동안 부드럽게 증가

효과
  └─ 자연스러운 시작
```

### 3. 변수로 저장

```
Return Value
  ↓
Promote to Variable
  └─ 이름: Looping Thruster Sound
  └─ Category: Thruster
```

**왜 변수로 저장하나?**

```
필요성
  └─ 나중에 정지할 때 접근 필요

저장 안 하면
  └─ Audio Component 레퍼런스 없음
  └─ 정지 불가능

변수 저장 후
  └─ 언제든지 Stop, Pause 가능
```

## ⚠️ 메모리 누수 문제와 해결

### 문제 발견 과정

**테스트 1: Auto Destroy = True**

```
제트팩 시작
  ↓
반복 소리 재생
  ↓
제트팩 정지
  ↓
Stop 호출 → 소리 멈춤 + 자동 삭제
  ↓
다시 시작
  ↓
Is Valid 체크 → 유효하지 않음 (빨간 메시지)
  └─ 매번 새로 생성해야 함
```

**Auto Destroy = True의 문제**

```
장점
  └─ 메모리 자동 정리

단점
  ├─ 매번 새로 생성/삭제
  ├─ 성능 낭비 (생성/삭제 비용 큼)
  └─ 비효율적
```

**테스트 2: Auto Destroy = False (문제)**

```
제트팩 시작
  ↓
반복 소리 재생 (Audio Component 1)
  ↓
Looping Thruster Sound 변수에 저장
  ↓
제트팩 정지
  ↓
Stop 호출 → 소리 멈춤 (삭제 안 됨)
  ↓
다시 시작
  ↓
새 Audio Component 2 생성
  ↓
Looping Thruster Sound에 덮어쓰기
  ↓
❌ Component 1은 메모리에 남음 (접근 불가)
```

**메모리 누수란?**

```
정의
  └─ 사용 안 하는 오브젝트가 메모리에 계속 쌓임

문제
  ├─ 메모리 점점 증가
  ├─ 게임 느려짐
  └─ 최악: 메모리 부족으로 크래시

비유
  └─ 쓰레기를 버리지 않고 계속 쌓는 것
```

### 올바른 해결 방법

**체크 후 생성 방식**

```
Looping Thruster Sound
  ↓
Is Valid?
  ├─ Is Not Valid (없음)
  │   └─ Spawn Sound Attached
  │       └─ Looping Thruster Sound에 저장
  │       └─ Fade In
  │
  └─ Is Valid (이미 있음)
      └─ Play (기존 것 재사용)
      └─ Fade In
```

**Is Valid 노드란?**

```
기능
  └─ 오브젝트가 유효한지 체크

Is Valid (True)
  └─ 오브젝트가 존재하고 사용 가능

Is Not Valid (False)
  ├─ None (Null)
  ├─ 삭제됨
  └─ 유효하지 않음
```

**Play 노드란?**

```
기능
  └─ 멈춘 Audio Component 다시 재생

vs Spawn
  ├─ Spawn: 새로 생성 (비쌈)
  └─ Play: 기존 것 재생 (저렴)

Start Time 옵션
  └─ 0.0: 처음부터 재생
```

**최종 로직**

```
시작 버튼 누름
  ↓
Is Valid?

첫 실행 (Is Not Valid)
  ├─ Spawn Sound Attached
  ├─ 변수 저장
  └─ Fade In

두 번째 실행 (Is Valid)
  ├─ Play (재사용)
  └─ Fade In

메모리
  └─ Audio Component 1개만 유지
  └─ 생성/삭제 반복 없음
```

**성능 비교**

```
Auto Destroy = True (매번 생성)
  └─ 시작: 생성 비용 + 재생
  └─ 정지: 삭제 비용
  └─ 비용: 높음

Auto Destroy = False + Is Valid 체크
  └─ 첫 시작: 생성 비용 + 재생 (1회)
  └─ 이후: 재생만 (저렴)
  └─ 정지: 중지만 (저렴)
  └─ 비용: 낮음
```

## 🎓 용어 정리

**Meta Sound**

- 언리얼의 고급 오디오 시스템
- 노드 기반 사운드 편집
- 동적 사운드 생성 가능

**Audio Component**

- 재생 중인 사운드 오브젝트
- 생성/제어/삭제 가능
- 3D 공간 음향 지원

**Fade (페이드)**

- 볼륨 서서히 변화
- In: 증가, Out: 감소
- 자연스러운 전환

**Memory Leak (메모리 누수)**

- 사용 안 하는 메모리 점유
- 성능 저하 원인
- 최악: 크래시

**Object Reference (오브젝트 레퍼런스)**

- 오브젝트의 주소/포인터
- 해당 오브젝트 접근/제어
- 변수에 저장 가능

**Attenuation (감쇠)**

- 거리에 따른 볼륨 감소
- 현실감 있는 3D 사운드
- 설정으로 조절 가능

## 🔍 상세 원리

### 부착(Attach)의 의미

```
Spawn Sound Attached
  ├─ Attach to Component: Capsule Component
  └─ 결과: Audio Component가 Capsule의 "자식"이 됨

계층 구조
BP_Kick
  └─ Capsule Component (부모)
      └─ Audio Component (자식) ← 여기에 붙음!
```

**자식-부모 관계**

```
부모가 이동하면
  └─ 자식도 자동으로 따라 이동

부모가 회전하면
  └─ 자식도 함께 회전

위치 계산
  └─ 자식 위치 = 부모 위치 + 상대 오프셋
```

## 🎮 실제 동작 과정

### 첫 번째 실행

```
1. 제트팩 시작
   ↓
2. Looping Thruster Sound Is Valid?
   └─ Is Not Valid (변수가 None)
   ↓
3. Spawn Sound Attached
   ├─ Capsule Component에 부착
   ├─ Audio Component 생성
   └─ Looping Thruster Sound 변수에 저장
   ↓
4. Fade In & Play

위치: (100, 200, 300) 캐릭터 위치
Audio Component: Capsule에 부착됨
```

### 캐릭터 이동 중

```
캐릭터가 (500, 600, 700)으로 이동
  ↓
Capsule Component 이동
  ↓
Audio Component 자동으로 따라감 ✅
  └─ 부모-자식 관계이므로

소리 위치
  └─ 항상 캐릭터와 함께
  └─ 별도 처리 불필요!
```

### 제트팩 정지

```
1. Stop 버튼
   ↓
2. Looping Thruster Sound → Stop
   ├─ 소리만 멈춤
   ├─ Audio Component는 여전히 존재
   └─ 여전히 Capsule에 부착되어 있음

위치: 캐릭터와 함께
상태: 정지됨 (삭제 안 됨)
```

### 두 번째 실행

```
1. 제트팩 다시 시작
   ↓
2. Looping Thruster Sound Is Valid?
   └─ Is Valid! (이미 있음)
   ↓
3. 새로 만들지 않고 Play 호출
   ├─ 기존 Audio Component 재사용
   └─ 이미 Capsule에 부착되어 있음
   ↓
4. Fade In

위치: 현재 캐릭터 위치 (자동)
Audio Component: 그대로 부착되어 있음
```

## 💡 왜 다시 Spawn 안 해도 되나?

### 이유 1: 부착 관계 유지

```
Audio Component가 Capsule에 붙어있음
  ↓
캐릭터 어디로 가든
  ↓
Audio Component도 함께
  ↓
별도로 위치 업데이트 불필요
```

### 이유 2: 컴포넌트 수명

```
Auto Destroy = False
  ↓
Stop해도 삭제 안 됨
  ↓
계속 Capsule에 붙어있음
  ↓
Play만 하면 다시 재생
```

## 📊 비교: Location vs Attached

### Spawn Sound at Location

```
생성 시
  └─ 월드 좌표 (100, 200, 300)에 고정

캐릭터 이동
  ├─ 캐릭터: (500, 600, 700)
  └─ 소리: (100, 200, 300) ← 그대로!

결과
  └─ 소리가 멀어짐
  └─ 재사용 불가능 (위치 다름)
  └─ 매번 새로 만들어야 함 ✅
```

### Spawn Sound Attached

```
생성 시
  └─ Capsule Component의 상대 위치 (0, 0, 0)

캐릭터 이동
  ├─ 캐릭터: (500, 600, 700)
  └─ 소리: (500, 600, 700) ← 자동으로 따라감!

결과
  └─ 항상 캐릭터 위치
  └─ 재사용 가능 ✅
  └─ 한 번만 만들면 됨 ✅
```

## 🔧 상대 위치의 비밀

### Location Type: Keep Relative Offset

```
Spawn Sound Attached
  └─ Location: (0, 0, 0)
  └─ 상대 좌표!

의미
  └─ Capsule 중심에서 (0, 0, 0) 떨어진 곳

캐릭터가 (100, 200, 300)
  └─ 소리 위치 = (100, 200, 300) + (0, 0, 0)
  └─ = (100, 200, 300)

캐릭터가 (500, 600, 700) 이동
  └─ 소리 위치 = (500, 600, 700) + (0, 0, 0)
  └─ = (500, 600, 700) ← 자동 업데이트!
```

## 🎯 정리

### 핵심 원리

```
1. Attach = 부모-자식 관계
   └─ 자식은 부모 따라 자동 이동

2. Auto Destroy = False
   └─ 컴포넌트 유지

3. 상대 좌표
   └─ 부모 기준으로 위치 자동 계산

결론
  └─ 한 번 만들어두면
  └─ 어디로 가든 따라다님
  └─ Play/Stop만 하면 됨
```

### 왜 효율적인가?

```
매번 새로 만들기
  ├─ Spawn 비용 (무거움)
  ├─ Destroy 비용 (무거움)
  └─ 반복 시 성능 저하

한 번 만들고 재사용
  ├─ Spawn 1회만 (초기만)
  ├─ Play/Stop (가벼움)
  └─ 성능 좋음 ✅
```

### 비유

```
매번 새로 만들기
  └─ 음악 들을 때마다 스피커 사고 버리기

재사용
  └─ 스피커 하나 사서 재생/정지 버튼만 누르기
```

**바로 이게 Attach의 마법입니다! 🎩✨**
