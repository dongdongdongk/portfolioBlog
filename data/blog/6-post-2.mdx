![image.png](https://res.cloudinary.com/du1acdhxq/image/upload/v1788381350/notion-blog/_/React_Node_/_6_Post_-_2_-/image.png)

## Redis에서 데이터를 조회하는 구조 이해하기

```jsx
Redis에서 데이터를 관리할 때 두 가지 주요 데이터 구조를 사용했습니다:

Sorted Set (정렬된 집합):

		ZADD 명령을 사용해 각 포스트의 key와 score 값을 저장합니다. score는 정렬 기준이 되며, 이를 통해 최근 데이터를 우선으로 가져올 수 있습니다.

Hash (해시):

		각 포스트의 상세 데이터를 HSET 명령으로 저장합니다. 포스트의 ID를 키로 사용하고, 데이터는 필드-값 형식으로 저장됩니다.
```

## 왜 Sorted Set과 Hash를 함께 사용하나요?

```jsx
Sorted Set은 데이터의 정렬과 범위 기반 조회가 쉽습니다.

Hash는 단일 객체의 상세 데이터를 저장하고 조회할 때 효율적입니다.

하지만 Hash만으로는 모든 데이터를 한 번에 조회할 수 없기 때문에,

Sorted Set을 통해 필요한 ID 목록을 가져오고, 이후 해당 ID를 기반으로 Hash에서 세부 데이터를 조회합니다.
```

## 데이터 조회 흐름

### 1. 포스트 ID 가져오기 (`ZRANGE`)

```jsx
ZRANGE 명령을 사용해 Sorted Set에서 ID 목록을 가져옵니다.

		예를 들어, 최신 포스트 3개를 가져오려면 시작 값(start)과 끝 값(end)을 지정합니다.

		REV 옵션을 사용해 최신 데이터부터 가져옵니다.
```

```jsx
const reply: string[] = await this.client.ZRANGE(key, start, end, { REV: true });

		key: post와 같은 Sorted Set의 이름

		start: 시작 인덱스 (예: 0)

		end: 끝 인덱스 (예: 2)
```

```jsx
Redis 명령 예시:

ZRANGE post 0 2 REV
```

### 2. 포스트 세부 데이터 가져오기 (`HGETALL`)

```jsx
각 ID를 기반으로 Hash에서 포스트 세부 데이터를 가져옵니다.

		HGETALL 명령은 Hash의 모든 필드와 값을 반환합니다.

		Redis에서는 한 번에 여러 Hash를 가져올 수 없기 때문에, Multi 명령을 사용해 여러 요청을 모은 뒤 실행합니다.
```

```jsx
// Redis 클라이언트를 사용하여 여러 명령을 한 번에 실행할 수 있도록 하는 multi 객체를 생성합니다.
const multi = this.client.multi();

// reply는 Redis에서 가져온 ID 리스트입니다. 예: ['123', '456', '789']
// 이 리스트에 있는 각 ID에 대해 해당하는 해시 데이터를 요청할 것입니다.
for (const value of reply) {
  // 각 ID에 대해 `posts:{value}` 형식으로 Redis에서 해시 데이터를 가져오는 명령을 multi 객체에 추가합니다.
  // HGETALL은 해당 키에 저장된 해시 데이터의 모든 필드와 값을 반환합니다.
  multi.HGETALL(`posts:${value}`);
}

// multi.exec()는 multi 객체에 추가된 모든 명령을 한 번에 실행합니다.
// exec()는 비동기적으로 실행되며, 실행 결과는 배열 형태로 반환됩니다.
// 배열의 각 요소는 해당 명령의 결과입니다.
const replies = await multi.exec();

// replies 배열에는 각 `posts:{value}`에 해당하는 해시 데이터가 들어 있습니다.
// 예를 들어, `posts:123`에 대한 HGETALL의 결과는 첫 번째 요소로, `posts:456`에 대한 HGETALL의 결과는 두 번째 요소로 들어갑니다.

		reply는 ID 리스트입니다.

		multi.HGETALL은 각 ID에 해당하는 Hash 데이터를 요청합니다.

		multi.exec()는 모든 요청을 한 번에 실행하고 결과를 반환합니다
```

### 3. 결과 데이터 가공

```jsx
Redis에서 가져온 데이터는 문자열로 반환되기 때문에, JSON이나 날짜 등의 타입으로 변환해야 합니다.

예를 들어, 댓글 수(commentsCount), 반응 데이터(reactions), 생성일(createdAt)을 적절히 변환합니다.
```

```jsx
for (const post of replies) {
  post.commentsCount = Helpers.parseJson(`${post.commentsCount}`) as number;
  post.reactions = Helpers.parseJson(`${post.reactions}`) as IReactions;
  post.createdAt = new Date(post.createdAt);
  postReplies.push(post);
}
```

# { 몽고 DB 게시물 데이터를 가져오는 `getPosts` }

```jsx
getPosts 메서드는 MongoDB의 aggregate 메서드를 사용하여 데이터를 가져오는 방법을 설명합니다.

이 메서드는 게시물을 검색하고, 정렬하고, 페이징 처리하기 위해 사용됩니다.
```

```jsx
// 게시물 데이터를 가져오는 서비스 클래스 메서드
// MongoDB의 aggregate와 find 메서드를 사용하여 데이터를 처리합니다.
public async getPosts(
  query: IGetPostsQuery, // 검색 조건을 담고 있는 객체 (예: 특정 이미지 ID, GIF URL 등)
  skip = 0,             // 기본값 0: 페이징 처리에서 몇 개의 데이터를 건너뛸지 설정
  limit = 0,            // 기본값 0: 가져올 데이터의 개수 제한
  sort: Record<string, 1 | -1> // 정렬 기준. 키는 필드 이름, 값은 1(오름차순) 또는 -1(내림차순)
): Promise<IPostDocument[]> { // 반환 타입: 게시물 문서 목록 (Promise)

  // 게시물 검색 조건을 정의할 변수
  let postQuery = {};

  // 검색 조건이 특정 이미지 ID와 GIF URL을 포함하고 있는 경우
  if (query?.imgId && query?.gifUrl) {
    // 검색 조건을 'imgId가 비어있지 않거나 gifUrl이 비어있지 않은 문서'로 설정 $ne 는 eq 의 반대 존재 하지 않으면 true
    postQuery = { $or: [{ imgId: { $ne: '' } }, { gifUrl: { $ne: '' } }] };
  } else {
    // 그렇지 않으면 그대로 전달받은 query를 사용
    postQuery = query;
  }

  // MongoDB aggregate 메서드를 사용하여 데이터를 가져옵니다.
  const posts: IPostDocument[] = await PostModel.aggregate([
    { $match: postQuery }, // $match: 검색 조건에 맞는 문서를 필터링
    { $sort: sort },       // $sort: 정렬 조건을 적용 (예: 날짜 오름차순, 내림차순 등)
    { $skip: skip },       // $skip: 지정된 수만큼 문서를 건너뜀 (페이징에 사용)
    { $limit: limit }      // $limit: 가져올 문서의 최대 개수를 제한
  ]);

  // 가져온 게시물 데이터를 반환
  return posts;
}

// 게시물 개수를 세는 서비스 클래스 메서드
// MongoDB의 countDocuments 메서드를 사용하여 총 문서 수를 계산합니다.
public async postCount(): Promise<number> { // 반환 타입: 문서 개수 (Promise)
  // 조건 없이 모든 문서를 찾아 개수를 셉니다.
  const count: number = await PostModel.find({}).countDocuments();

  // 계산된 총 문서 개수를 반환
  return count;
}

```

```jsx
메서드 구조

매개변수 설명:

		query: 검색 조건을 담고 있는 객체 (예: imgId, gifUrl 등의 조건).

		skip: 기본값은 0. 데이터를 몇 개 건너뛸지 설정 (페이징 처리에 사용).

		limit: 기본값은 0. 한 번에 가져올 데이터의 개수 (페이징 처리에 사용).

		sort: 정렬 기준을 나타내는 객체. 키는 필드 이름, 값은 1(오름차순) 또는 -1(내림차순).

작동 방식:

1. query에 따라 검색 조건(postQuery)을 설정:

		imgId와 gifUrl이 모두 있을 경우, 이미지 ID가 비어있지 않거나 GIF URL이 비어있지 않은 게시물을 필터링.

		조건이 없을 경우에는 그대로 query를 사용.

2. aggregate 메서드로 MongoDB에서 데이터를 가져옴:

		$match: postQuery 조건에 맞는 데이터를 필터링.

		$sort: sort 객체를 사용하여 정렬.

		$skip: skip 값을 사용하여 데이터 건너뛰기.

		$limit: limit 값을 사용하여 데이터 제한.
```

### `Record` 유형이란?

```jsx
Record는 TypeScript에서 제공하는 유틸리티 타입입니다.

객체 타입을 정의할 때, 키와 값의 타입을 명확히 지정할 수 있게 해줍니다.

* 왜 Record를 사용하는가?

		객체에서 키와 값의 타입을 일관성 있게 정의할 수 있음.

		정렬 같은 경우, 특정 필드와 정렬 방향을 전달해야 하므로 유용.
```

```jsx
Record<Keys, Values>

Keys: 객체의 키(key)에 해당하는 타입.

Values: 객체의 값(value)에 해당하는 타입.
```

### 페이징 처리의 원리

```jsx
페이징 처리는 데이터를 부분적으로 가져와 한 번에 너무 많은 양의 데이터를 처리하지 않도록 돕습니다.
```

```jsx
예제: 한 페이지에 3개의 항목을 표시.

skip=0, limit=3: 첫 번째 페이지.

skip=3, limit=3: 두 번째 페이지 (첫 3개 항목을 건너뜀).

skip=6, limit=3: 세 번째 페이지 (6개 항목을 건너뜀).
```

### MongoDB의 `aggregate` 메서드란?

```jsx
aggregate는 MongoDB에서 데이터를 다양한 방식으로 처리

(필터링, 정렬, 그룹화, 변환 등)할 수 있게 해주는 고급 쿼리 메서드입니다.

SQL의 GROUP BY, ORDER BY, WHERE와 같은 복잡한 작업을 수행할 때 사용하며,

데이터를 여러 단계(stages)에 걸쳐 처리할 수 있습니다.

aggregate는 파이프라인(pipeline) 구조로 동작합니다.

		파이프라인은 데이터를 단계별로 처리할 수 있게 합니다.

		각 단계는 특정 작업(예: 필터링, 정렬)을 수행하며, 다음 단계로 결과를 전달합니다.

		여러 단계를 조합해 복잡한 작업을 수행할 수 있습니다.
```

## MongoDB에서 게시물 수를 세는 `postCount` 메서드

```jsx
postCount 메서드는 MongoDB 컬렉션에 저장된 게시물의 총 개수를 반환합니다.

작동 방식:

		find({}): 조건 없이 모든 문서를 찾음.

		countDocuments(): 문서의 개수를 셈.
```

### \* newSkip ?

```jsx
newSkip은 Redis에서 데이터를 가져올 때 사용되는 시작점(start index)입니다.

이 값은 MongoDB의 skip 값과 비슷하지만, 캐시와 데이터베이스의 데이터 구조 차이로 인해 약간 다르게 설정됩니다.
```

```jsx
1. MongoDB의 skip

		MongoDB의 skip은 특정 개수의 데이터를 건너뛰고 나머지 데이터를 반환하도록 설정합니다.

		예를 들어, 게시글 데이터를 가져올 때:

				skip = 0: 처음부터 데이터를 가져옴.

				skip = 10: 처음 10개의 데이터를 건너뛰고 11번째 데이터부터 가져옴.

		MongoDB는 데이터를 일반적으로 순차적으로 정렬된 상태에서 처리합니다.


2. Redis에서 newSkip이 필요한 이유

		Redis는 MongoDB와 달리 데이터를 순차적 정렬 상태로 관리하지 않을 수도 있고,

		0 기반 인덱싱으로 데이터에 접근합니다. 여기서 몇 가지 고려 사항이 있습니다:


		1. Redis는 데이터를 블록으로 처리

				Redis에서는 데이터를 가져올 때 시작점과 끝점을 명시해야 합니다.

				const cachedPosts = await postCache.getPostFromCashe('post', newSkip, limit);

				newSkip: 시작 인덱스 (예: 0, 11 등)

				limit: 끝 인덱스 (예: 10, 20 등)


		2. Pagination 시 데이터 누락 방지 Redis에서 데이터를 요청할 때, skip 값과 limit 값이 잘못 설정되면 데이터가 중복되거나 누락될 수 있습니다.

				이를 방지하기 위해 **newSkip**이 다음과 같이 설정됩니다:

				const newSkip: number = skip === 0 ? skip : skip + 1;

						첫 페이지(skip = 0)에서는 newSkip도 0으로 설정합니다.

						이 경우 첫 번째 데이터부터 정확히 가져올 수 있습니다.

						두 번째 페이지 이후(skip > 0)에는 newSkip = skip + 1로 설정합니다.

						이렇게 하면 Redis에서 데이터를 가져올 때 직전 요청과의 중복을 방지합니다.


		3. Redis와 MongoDB 데이터 구조 차이

				MongoDB에서는 skip 값만으로 데이터를 정확히 건너뛸 수 있습니다.

				그러나 Redis에서는 범위로 데이터를 지정하므로,

				첫 번째 요청과 다음 요청의 데이터 중복 문제를 해결하기 위해 newSkip을 추가로 조정합니다.
```

### 예시로 이해하기

```jsx
예시 1: 첫 번째 페이지 요청 (page = 1)

const skip = (page - 1) * PAGE_SIZE = 0;

const limit = PAGE_SIZE * page = 10;

MongoDB:

skip = 0, limit = 10 → 첫 번째 데이터부터 10개 가져옴.

Redis:

newSkip = 0, limit = 10 → 첫 번째 데이터부터 10개 가져옴.
```

```jsx
예시 2: 두 번째 페이지 요청 (page = 2)

const newSkip = (skip === 0 ? skip : skip + 1) = 11;

MongoDB:

skip = 10, limit = 10 → 11번째 데이터부터 20번째 데이터 가져옴.

Redis:

newSkip = 11, limit = 20 → 12번째 데이터부터 20번째 데이터 가져옴.

Redis의 경우, 11번 데이터를 중복으로 가져오지 않도록 **newSkip**을 skip + 1로 설정합니다.
```

## ZRANGE(key**,** start**,** end**,** { REV**:** true }) 에서 REV:ture 사용 불가

```jsx
게시글을 가져오면서 최신 글 부터 가져오기 위해서는 글 목록을 리버스 시켜야한다

그러나 REV:true 분법을 사용하지 못하기 때문에 아래와 같이 변수를 새로 만들어 배열 순서를 뒤집어 넣어주도록 한다

( 이미지 게시물 불러오기 역시 )
```

```jsx
public async getPostFromCache(key: string, start: number, end: number): Promise<IPostDocument[]> {
  try {
    // Redis 클라이언트가 열려 있지 않은 경우 연결 시도
    if (!this.client.isOpen) {
      log.info('Connecting to Redis...'); // 연결 시도를 로깅
      await this.client.connect(); // Redis 서버에 연결
    }

    // Redis의 Sorted Set에서 지정된 범위(start부터 end까지)의 데이터를 가져옴
    log.info(`Fetching posts from sorted set ${key}, range ${start} to ${end}`);
    const reply: string[] = await this.client.ZRANGE(key, start, end); // ZRANGE는 기본적으로 낮은 점수부터 높은 점수로 반환
    log.info(`ZRANGE result for ${key}: ${reply}`); // 가져온 결과를 로깅

    // 가져온 데이터를 역순으로 정렬하여 최신 게시물이 먼저 오도록 변경
    const reversedReply = reply.reverse(); // 배열의 순서를 반대로 뒤집음
    log.info(`Reversed order: ${reversedReply}`); // 역순 정렬 결과를 로깅

    // Redis의 MULTI 명령을 사용하여 여러 명령을 일괄 실행
    const multi = this.client.multi();
    for (const value of reversedReply) {
      // 각 게시물 ID를 사용하여 Redis의 Hash에서 세부 정보를 가져오도록 명령 추가
      log.info(`Fetching hash for post:${value}`); // 가져올 키를 로깅
      multi.HGETALL(`post:${value}`); // Hash에서 모든 필드와 값을 가져오는 HGETALL 명령 추가
    }

    // MULTI 명령 실행 및 결과 저장
    const replies: PostCacheMultiType = (await multi.exec()) as PostCacheMultiType;
    log.info(`Fetched data for posts: ${JSON.stringify(replies)}`); // 실행 결과를 로깅

    // 가져온 데이터를 타입 변환 및 파싱하여 최종 결과 배열 생성
    const postReplies: IPostDocument[] = [];
    for (const post of replies as IPostDocument[]) {
      // 각 게시물의 세부 정보를 JSON 형식으로 파싱
      post.commentsCount = Helpers.parseJson(`${post.commentsCount}`) as number; // 댓글 수를 숫자로 변환
      post.reactions = Helpers.parseJson(`${post.reactions}`) as IReactions; // 반응 데이터를 객체로 변환
      post.createdAt = Helpers.parseJson(`${post.createdAt}`) as Date; // 생성 시간을 Date 객체로 변환
      postReplies.push(post); // 변환된 게시물 데이터를 결과 배열에 추가
    }

    // 최종 변환된 게시물 데이터 배열 반환
    return postReplies;
  } catch (error) {
    // 오류 발생 시 로그를 기록하고 서버 오류로 처리
    log.error(error); // 오류 내용을 로깅
    throw new ServerError('Server error. Try again.'); // 사용자에게 표시할 에러 메시지
  }
}

```

### TypeScript의 `ReturnType` 유틸리티 타입

```jsx
TypeScript의 ReturnType 유틸리티 타입은 함수의 반환 타입을 자동으로 추출하는 데 사용됩니다
```

```jsx
1. ReturnType이란?

		ReturnType은 TypeScript에서 제공하는 유틸리티 타입입니다.

		주어진 함수 타입에서 **"이 함수가 반환하는 값의 타입"**을 자동으로 추론하여 가져옵니다.

		ReturnType<Type>

		Type: 반환 타입을 추출할 함수 타입.


2. ReturnType을 쓰는 이유

		코드 재사용성:

				함수의 반환 타입을 다른 곳에서 재사용할 때, 동일한 타입을 유지하기 쉽습니다.

		유지보수성:

				함수의 반환 타입이 바뀌어도 ReturnType을 사용한 모든 곳에서 자동으로 업데이트됩니다.

		코드 간결화:

				반환 타입을 직접 작성하지 않아도 TypeScript가 자동으로 추론합니다
```

```jsx
3. ReturnType의 작동 원리

예제 1: 함수의 반환 타입 추출

		function getUser() {
		  return { id: 1, name: "Alice" };
		}

		// getUser 함수의 반환 타입을 가져옵니다.
		type UserType = ReturnType<typeof getUser>;

getUser 함수는 { id: number, name: string } 타입의 객체를 반환합니다.

ReturnType<typeof getUser>를 사용하면, **UserType**은 아래와 동일한 타입으로 추론됩니다:

type UserType = { id: number, name: string };
```

```jsx
예제 2: API 응답 타입 재사용

		function fetchUser() {
		  return { id: 123, username: "JohnDoe" };
		}

		type ApiResponse = ReturnType<typeof fetchUser>;

		// ApiResponse 타입은 { id: number, username: string }입니다.

		const user: ApiResponse = fetchUser();
```

```jsx
예제 3: 콜백 함수의 반환 타입 추출

		const callback = (x: number) => x * 2;

		type CallbackReturn = ReturnType<typeof callback>; // CallbackReturn은 number 타입
```

## 게시물 삭제 컨트롤러

```jsx
Delete 클래스 구조

		export class Delete {
		  public async post(req: Request, res: Response): Promise<void> {

				  Delete 클래스의 post 메서드는 게시물 삭제 요청을 처리합니다.

					async 키워드가 붙어 있으므로, 비동기 작업을 수행합니다.



1단계: 실시간 삭제 이벤트 전송 (Socket.IO 사용)

		socketIOPostObject.emit('delete post', req.params.postId);

				emit() 메서드는 이벤트를 발생시킵니다.

				여기서는 delete post라는 이름의 이벤트를 발생시키고, 삭제된 게시물의 ID를 클라이언트에 전송합니다.

				이렇게 하면, 해당 게시물을 보고 있던 다른 사용자들은 실시간으로 삭제 알림을 받게 됩니다.



2단계: Redis 캐시에서 게시물 삭제

		await postCache.deletePostFromCache(req.params.postId, `${req.currentUser!.userId}`);

				Redis 캐시에서 게시물을 삭제합니다.

				req.params.postId: 삭제할 게시물의 고유 ID입니다.

				req.currentUser!.userId: 현재 요청을 보낸 사용자의 ID입니다.


3단계: 큐에 작업 추가 (비동기 데이터베이스 작업)

		postQueue.addPostJob('deletePostFromDB', { keyOne: req.params.postId, keyTwo: req.currentUser!.userId });

				큐에 작업을 추가하여 데이터베이스에서 게시물 삭제 작업을 처리합니다.

				큐를 사용하는 이유는 비동기 작업으로 데이터베이스에 부담을 줄이고, 응답 속도를 높이기 위해서입니다.


4단계: 성공 응답 반환

		res.status(HTTP_STATUS.OK).json({ message: 'Post deleted successfully' });

				클라이언트에 HTTP 200 OK 상태 코드와 함께 성공 메시지를 반환합니다.

				Post deleted successfully라는 메시지를 클라이언트가 수신하게 됩니다.
```

```jsx
      if (!this.client.isOpen) {
        log.info('Connecting to Redis...');
        await this.client.connect();
      }

      const postCount: string[] = await this.client.HMGET(`users:${currentUserId}`, 'postsCount');
      log.info(`Fetched post count for user ${currentUserId}: ${postCount}`);

      // ZADD 명령 실행
      log.info(`Adding post key ${key} with score ${uId} to sorted set.`);
      await this.client.ZADD('post', { score: parseInt(uId, 10), value: `${key}` });

      // HSET 명령 실행
      for (let i = 0; i < dataToSave.length; i += 2) {
        log.info(`Setting field ${dataToSave[i]} with value ${dataToSave[i + 1]} for key post:${key}`);
        // dataToSave[i]는 키(필드 이름), dataToSave[i + 1]는 값
        // 예: i가 0일 때 => HSET('users:key', '_id', '123')
        //     i가 2일 때 => HSET('users:key', 'username', 'john')
        await this.client.HSET(`posts:${key}`, dataToSave[i], dataToSave[i + 1]);
      }

      // postsCount 업데이트
      const count: number = parseInt(postCount[0], 10) + 1;
      log.info(`Updating posts count for user ${currentUserId}: ${count}`);
      await this.client.HSET(`users:${currentUserId}`, 'postsCount', count);
    } catch (error) {
      log.error(error);
      throw new ServerError('Server error. Try again.');
    }
  }
```

```jsx
public async updatePostInCache(key: string, updatedPost: IPostDocument): Promise<IPostDocument> {
  // 업데이트할 게시물 데이터에서 필요한 필드를 추출합니다.
  const { post, bgColor, feelings, privacy, gifUrl, imgVersion, imgId, profilePicture } = updatedPost;

  // Redis에 저장할 데이터 형식을 미리 구성합니다.
  const dataToSave = {
    'post': `${post}`,                // 게시물 내용
    'bgColor': `${bgColor}`,          // 게시물 배경색
    'feelings': `${feelings}`,        // 게시물의 감정 상태
    'privacy': `${privacy}`,          // 공개/비공개 설정
    'gifUrl': `${gifUrl}`,            // 첨부된 GIF URL

    'imgVersion': `${imgVersion}`,    // 이미지 버전

    if (!this.client.isOpen) {
      await this.client.connect(); // Redis 서버에 연결
    }

    // 구성된 데이터를 Redis의 해시(Hash) 자료구조에 저장합니다.
    // HSET 명령어로 각각의 키와 값을 `posts:${key}`라는 Redis 해시에 저장합니다.
```

```jsx
		캐시 업데이트:

		Redis를 사용해 게시물 데이터를 캐시에 저장.

		빠른 읽기/쓰기를 위해 캐시에 데이터를 저장하는 단계.

(4) 소켓 통신 (실시간 데이터 업데이트)

socketIOPostObject.emit('update post', postUpdated, 'posts');

Socket.IO 사용:

		서버가 클라이언트에게 실시간으로 업데이트된 데이터를 전송.

				이벤트 이름: 'update post'.

				전송 데이터:

						postUpdated: 업데이트된 게시물 데이터.

						'posts': 업데이트된 데이터의 범주(채널).

		소켓이 필요한 이유

				실시간 사용자 경험 제공:

				사용자가 브라우저에서 페이지를 새로 고침하지 않아도 게시물 업데이트가 반영됨.

				여러 사용자가 같은 게시물을 보고 있을 때, 변경 사항을 실시간으로 동기화.

(5) DB 업데이트 작업을 큐에 추가

		postQueue.addPostJob('updatePostInDB', { key: postId, value: updatedPost });

		DB 업데이트 작업을 워커에 전달:

				postQueue에 작업을 추가해 비동기로 DB를 업데이트.

		작업 데이터:

				key: 업데이트할 게시물의 ID.

				value: 업데이트할 게시물 데이터.
```

# { 업데이트의 두 가지 이미지 포함 경우 }

## 1. 게시물 업데이트의 두 가지 경우

```jsx
1-1. 기존 이미지를 유지하며 게시물 업데이트

		사용자가 게시물의 텍스트, 감정, 공개 범위 등 메타데이터만 수정하려는 경우.

		이미지는 변경하지 않고 이미지 ID(imgId)와 이미지 버전(imgVersion)을 그대로 사용.

1-2. 기존 이미지를 새로운 이미지로 교체

		사용자가 게시물에 포함된 이미지를 새로운 이미지로 교체하려는 경우.

		Cloudinary(이미지 저장 서비스)에 새로운 이미지를 업로드하고,

		새로 생성된 이미지 ID와 이미지 버전을 저장.
```

### 메서드 1: `postWithImage`

```jsx
게시물 업데이트를 처리하는 메인 메서드.

imgId와 imgVersion의 유무에 따라 작업을 분기합니다.

		이미지 교체 불필요: 기존 이미지 유지 (updatedPostWithImage 호출).

		이미지 교체 필요: 새로운 이미지 업로드 및 게시물 업데이트 (addImageToExistingPost 호출).
```

```jsx
@joiValidation(postWithImageSchema)
public async postWithImage(req: Request, res: Response): Promise<void> {
  try {
    const { imgId, imgVersion } = req.body;
    if (imgId && imgVersion) {
      await Update.prototype.updatedPostWithImage(req); // 기존 이미지 유지
    } else {
      const result = await Update.prototype.addImageToExistingPost(req); // 새 이미지 업로드
      if (!result?.public_id) {
        throw new BadRequestError('Image upload failed');
      }
    }
    res.status(HTTP_STATUS.OK).json({ message: 'Post with image updated successfully' });
  } catch (error) {
    const errorMessage = error instanceof BadRequestError ? error.message : 'Server error occurred';
    res.status(HTTP_STATUS.BAD_REQUEST).json({ message: errorMessage });
  }
}
```

```jsx
private async updatedPostWithImage(req: Request): Promise<void> {
```

### 메서드 3: `addImageToExistingPost`

```jsx
새로운 이미지를 업로드하고 게시물에 추가.

이미지 업로드 후:

		Cloudinary의 응답에서 public_id와 version을 가져옴.

		새로 생성된 이미지 ID와 이미지 버전으로 게시물 데이터 업데이트.

		캐시 및 데이터베이스 업데이트.
```

```jsx
private async addImageToExistingPost(req: Request): Promise<UploadApiResponse> {
  const { post, bgColor, feelings, privacy, gifUrl, profilePicture, image } = req.body;
  const { postId } = req.params;

  if (!image) throw new BadRequestError('Image is required');

  const result = await upload(image);
  if (!result?.public_id || !result?.version) {
    throw new BadRequestError('Image upload failed');
  }

  const updatedPost: IPostDocument = {
    post,
    bgColor,
    feelings,
    privacy,
    gifUrl,
    profilePicture,
    imgId: result.public_id,
    imgVersion: result.version.toString()
  };

  const postUpdated = await postCache.updatePostInCache(postId, updatedPost);
  if (!postUpdated) throw new BadRequestError('Failed to update post in cache');

  socketIOPostObject.emit('update post', postUpdated, 'posts');
  postQueue.addPostJob('updatePostInDB', { key: postId, value: updatedPost });

  return result;
}
```

# { Mongoose의 제네릭 타입 }

```jsx
Mongoose의 제네릭(Generic) 타입을 처음 접하면 헷갈릴 수 있지만,

간단하게 생각하면 **제네릭 타입은 "데이터의 타입을 미리 설정해서 코드가 더 안전하게 동작하도록 돕는 것"**입니다.

예를 들어, 어떤 함수가 문자열을 받아야 하는데 숫자를 받으면 오류가 나겠죠?

이런 실수를 타입 검사로 미리 방지하는 것이 제네릭 타입의 역할입니다.
```

## 제네릭 타입이란?

```jsx
제네릭(Generic)이란 **"데이터의 타입을 동적으로 설정할 수 있는 템플릿"**이라고 생각하면 됩니다.

💡 쉽게 비유하면, 제네릭은 **"빈 박스에 나중에 어떤 물건을 넣을지 미리 정하는 것"**과 같습니다.

박스를 만들 때는 어떤 물건이 들어갈지 모릅니다.

하지만 나중에 "이 박스에는 책만 넣을 거야"라고 정하면, 다른 물건(예: 과일)은 넣을 수 없게 됩니다.
```

## 제네릭 타입의 기본 구조

```jsx
TypeScript에서는 제네릭 타입을 다음과 같이 선언합니다:
```

```jsx
function identity<T>(value: T): T {
  return value;
}
```

```jsx
여기서 T는 제네릭 타입 변수입니다.

T는 아무 타입이나 될 수 있는 변수입니다.

함수 호출 시 실제 타입을 넣으면, T는 그 타입으로 대체됩니다.
```

```jsx
identity < string > 'Hello' // T가 string이 됨
identity < number > 123 // T가 number가 됨
```

## Mongoose에서 제네릭 타입이 왜 중요할까?

```jsx
Mongoose에서는 데이터 모델과 CRUD 연산에서 제네릭 타입을 사용합니다.

MongoDB 컬렉션에는 다양한 데이터가 들어갈 수 있기 때문에,

제네릭을 사용해 각 문서(Document)의 타입을 명확하게 정의하는 것이 중요합니다.
```

## Mongoose의 주요 제네릭 타입

### Document<T>

```jsx
Document<T>는 MongoDB의 **문서(Document)**를 나타내는 타입입니다.

T는 문서의 데이터 타입을 나타냅니다.

모든 문서에는 기본적으로 _id, createdAt, updatedAt 필드가 포함됩니다.
```

```jsx
// Mongoose의 Document 타입을 임포트
import { Document } from 'mongoose';

// 1️⃣ IUser 인터페이스 정의
// 사용자 데이터에 필요한 필드를 정의합니다.
// name: 사용자 이름
// email: 사용자 이메일
interface IUser {
  name: string;
  email: string;
}

// 2️⃣ IUserDocument 타입 정의
// IUser와 Mongoose의 Document를 결합하여
// MongoDB 문서에 기본적으로 포함되는 필드(_id, createdAt, updatedAt)를 추가합니다.
type IUserDocument = IUser & Document;

// 3️⃣ IUserDocument 타입으로 user 객체 생성
// _id, createdAt, updatedAt 같은 필드는 Document에서 제공됩니다.
const user: IUserDocument = {
  name: "John Doe",
  email: "john@example.com",
  _id: new ObjectId(), // MongoDB의 ObjectId를 생성
  createdAt: new Date(), // 문서 생성 시간
  updatedAt: new Date()  // 문서 업데이트 시간
};
```

### Model<T>

```jsx
Model<T>는 Mongoose에서 모델을 정의할 때 사용하는 타입입니다.

T는 모델이 관리하는 문서의 타입을 나타냅니다.

모델은 MongoDB 컬렉션과 연결되어, 데이터를 조회하거나 저장하는 기능을 제공합니다.
```

```jsx
import { Model } from 'mongoose';

// 1️⃣ IUser 인터페이스 정의 (재사용)
interface IUser {
  name: string;
  email: string;
}

// 2️⃣ UserModel 정의
// Mongoose 모델을 생성합니다.
// Model<IUser>는 이 모델이 IUser 타입의 데이터를 관리한다는 것을 명시합니다.
const UserModel: Model<IUser> = mongoose.model('User', userSchema);

// 3️⃣ findOne 메서드로 사용자 조회
// email 필드가 "john@example.com"인 사용자를 조회합니다.
UserModel.findOne({ email: "john@example.com" }).then((user) => {
  console.log(user?.name); // 조회된 사용자의 이름 출력
});
```

### FilterQuery<T>

```jsx
FilterQuery<T>는 조회 쿼리에 사용되는 타입입니다.

T는 조회할 문서의 데이터 타입을 나타냅니다.

find(), findOne() 메서드에서 조건을 정의할 때 사용합니다.
```

```jsx
import { FilterQuery } from 'mongoose';

// 1️⃣ IUser 인터페이스 정의 (재사용)
interface IUser {
  name: string;
  email: string;
}

// 2️⃣ FilterQuery 타입 사용
// findOne 메서드에서 사용할 필터 조건을 정의합니다.
// FilterQuery<IUser>는 IUser 타입에 기반하여 필터를 작성할 수 있도록 도와줍니다.
const filter: FilterQuery<IUser> = { email: "john@example.com" };

// 3️⃣ 필터를 사용하여 사용자 조회
UserModel.findOne(filter).then((user) => {
  console.log(user?.name); // 조회된 사용자의 이름 출력
});
```

### LeanDocument<T>

```jsx
LeanDocument<T>는 Mongoose에서 lean() 메서드를 사용할 때 반환되는 Plain JavaScript Object 타입을 나타냅니다.

lean()을 사용하면 Mongoose의 문서 메서드가 제거되고 평범한 JavaScript 객체를 반환합니다.
```

```jsx
import { LeanDocument } from 'mongoose';

// 1️⃣ IUser 인터페이스 정의 (재사용)
interface IUser {
  name: string;
  email: string;
}

// 2️⃣ lean() 메서드 사용
// lean()은 Mongoose의 문서 객체 대신 순수 자바스크립트 객체를 반환합니다.
// 반환 타입은 LeanDocument<IUser>로 정의됩니다.
UserModel.findOne({ email: "john@example.com" })
  .lean()
  .then((user: LeanDocument<IUser> | null) => {
    console.log(user?.name); // 조회된 사용자의 이름 출력
  });

```

### 실무에서 자주 사용하는 조합 예제

```jsx
import mongoose, { Document, Model, UpdateQuery, FilterQuery } from 'mongoose';

// 1️⃣ IUser 인터페이스 정의
// 사용자 데이터에 필요한 필드를 정의합니다.
interface IUser {
  name: string;
  email: string;
}

// 2️⃣ IUserDocument 타입 정의
// IUser와 Mongoose의 Document를 결합하여 MongoDB 문서 타입을 만듭니다.
type IUserDocument = IUser & Document;

// 3️⃣ UserModel 정의
// Mongoose 모델을 생성하며, IUserDocument를 기반으로 동작합니다.
const UserModel: Model<IUserDocument> = mongoose.model('User', new mongoose.Schema<IUser>({
  name: { type: String, required: true },  // name 필드 정의
  email: { type: String, required: true } // email 필드 정의
}));

// 4️⃣ UpdateQuery 타입 사용
// UpdateQuery<IUserDocument>는 MongoDB 업데이트 쿼리를 안전하게 작성할 수 있도록 도와줍니다.
const updateData: UpdateQuery<IUserDocument> = {
  $set: { name: "Updated Name" } // name 필드의 값을 "Updated Name"으로 변경
};

// 5️⃣ updateOne 메서드로 문서 업데이트
// email 필드가 "john@example.com"인 사용자를 찾아 name을 업데이트합니다.
await UserModel.updateOne({ email: "john@example.com" }, updateData);
```

# { as 를 사용하는 이유 }

## 1. **객체 리터럴이 타입에 완전히 맞지 않는 경우**

```jsx
TypeScript는 객체 리터럴이 인터페이스 타입과 정확히 일치하지 않으면 오류를 발생시킵니다.

예를 들어, updatedPost에 일부 필드가 누락되었거나,

IPostDocument에 정의되지 않은 필드가 포함된 경우, 컴파일러가 오류를 표시합니다.

as IPostDocument를 사용하면 타입 일치를 강제로 통과시킬 수 있습니다.
```

```jsx
interface IPostDocument {
  post: string;
  bgColor: string;
  feelings: string;
  privacy: string;
  gifUrl: string;
  imgVersion: string;
  imgId: string;
  profilePicture: string;
}

// 여기서 필드를 일부 누락시키는 경우
const updatedPost = {
  post,
  bgColor,
  feelings,
  privacy,
  gifUrl,
  imgVersion,
  imgId
} as IPostDocument; // profilePicture가 없어도 오류를 무시

```

## 2. **타입 추론이 충분하지 않은 경우**

```jsx
TypeScript는 객체 리터럴의 타입을 추론하려고 하지만,

복잡한 타입 체계에서는 추론이 실패하거나 제대로 동작하지 않을 수 있습니다.

이때 as를 사용해 컴파일러가 원하는 타입으로 간주하도록 강제합니다.

예를 들어, 다음 상황에서 updatedPost가 추론된 타입이 IPostDocument와 다를 수 있습니다.
```

```jsx
const partialData = {
  post,
  bgColor,
  feelings,
  privacy,
  gifUrl,
  imgVersion,
  imgId,
  profilePicture
};

// partialData의 타입이 IPostDocument와 정확히 일치하지 않는다면, 에러 발생
const updatedPost = partialData as IPostDocument;

```

## 3. **인터페이스의 선택적 필드(Optional fields)가 원인일 수 있음**

```jsx
만약 IPostDocument 인터페이스에 일부 필드가 선택적(optional)로 선언되었다면,

TypeScript가 타입 일치 여부를 확신하지 못할 수 있습니다.

as를 사용해 명시적으로 타입을 선언하여 오류를 피할 수 있습니다.
```

```jsx
interface IPostDocument {
  post: string;
  bgColor?: string; // 선택적 필드
  feelings: string;
  privacy: string;
  gifUrl: string;
  imgVersion: string;
  imgId: string;
  profilePicture?: string; // 선택적 필드
}

```

## 결론

```jsx
as IPostDocument는 다음과 같은 이유로 사용되었을 가능성이 높습니다:

1. 타입 일치 강제.

2. 객체 리터럴의 필드가 IPostDocument와 정확히 일치하지 않음.

3. 타입 추론 실패 방지.

4. 선택적 필드가 포함된 경우.

as 없이 오류가 없다면 제거해도 괜찮습니다. 하지만 오류가 발생한다면,

위와 같은 이유를 고려해 as를 유지하거나 타입 정의를 수정하는 것이 좋습니다.
```

# { `config` 파일과 관련된 경로 설정 문제 }

## 1. **문제의 원인**

```jsx
jest.config.css 또는 관련 파일이 특정 위치에서 에러를 발생시키고 있습니다.

원인은 jest.config.js 또는 jest.config.css 파일의 경로 설정이 올바르지 않거나

빌드 결과에서 파일 위치가 예상과 다르기 때문입니다.

예를 들어, jest가 파일을 찾으려는 root 디렉토리가 src로 지정되어 있지만,

실제 파일은 프로젝트 최상위(root) 폴더에 있습니다.

```

## 2. **해결 방법**

### jest 설정에서 root 경로 변경

```jsx

jest가 파일을 올바르게 인식할 수 있도록 root 경로를 수정합니다.

현재 설정된 root가 src인 경우, 이를 .(현재 디렉토리)로 변경합니다.
```

```jsx
변경 전:

module.exports = {
  rootDir: "src",
};

변경 후:

module.exports = {
  rootDir: ".",
};
```

### 파일 확장자 확인 및 경로 수정

```jsx
jest.config.js 또는 관련 파일이 .js가 아니라 .css로 잘못 설정된 경우가 있습니다.

파일 이름을 .js로 변경하거나 설정 파일에서 정확한 확장자를 지정합니다.
```

```jsx
변경 전:

module.exports = {
  setupFilesAfterEnv: ["<rootDir>/jest.config.css"],
};

변경 후:

module.exports = {
  setupFilesAfterEnv: ["<rootDir>/jest.config.js"],
};
```

### 빌드 및 테스트 실행

```jsx
root 경로와 파일 이름을 수정한 후, npm run build 명령으로 빌드를 실행합니다.

빌드가 완료되면 npm test를 실행하여 설정이 올바르게 동작하는지 확인합니다.
```

## 3. **빌드 결과 확인**

```jsx
빌드 후 출력 폴더를 확인하여 파일들이 올바른 위치에 있는지 점검합니다.

예를 들어, jest.config.js 파일이 build 폴더에 포함되어 있는지 확인합니다.
```

## 4. **배포 스크립트 설정**

```jsx
배포를 위해 실행 스크립트에서 빌드된 파일 경로를 지정합니다.
```

```jsx
빌드 파일이 build/source 폴더에 있는 경우:

"start": "node build/source/app.js"

빌드 파일이 build 폴더에 직접 있는 경우:

"start": "node build/app.js"
```

## 5. **정리**

```jsx
1. jest.config.js의 root 경로 설정을 .으로 변경하여 파일 경로 문제를 해결합니다.

2. 파일 이름과 확장자를 올바르게 지정합니다.

3. 빌드 후 파일 위치를 확인하고, 배포 시 스크립트를 경로에 맞게 수정합니다.
```
