## 1. Canvas 생성하기

- **Hierarchy 창**에서 우클릭 → **UI** → **Canvas** 선택
- Canvas는 UI 요소(버튼, 이미지, 텍스트 등)를 담는 **도화지** 같은 역할

---

## 2. Canvas 기본 설정

**Inspector 창**에서 확인:

### Render Mode (렌더링 방식)

- **Screen Space - Overlay** 유지
  - **의미**: UI가 게임 화면 **맨 앞**에 항상 표시됨
  - 카메라와 관계없이 화면 전체를 덮음
  - 버튼, 체력바 같은 일반적인 UI에 적합
- 다른 설정들은 기본값 유지

---

## 3. Canvas Scaler 설정

다양한 화면 크기(모니터, 해상도)에서 UI가 **일정한 크기**를 유지하도록 조절하는 설정입니다.

### Scale Mode (크기 조절 방식)

- **Scale With Screen Size**로 변경
  - **의미**: 화면 크기에 따라 UI 요소들이 **자동으로 확대/축소**됨
  - 다양한 해상도에서도 UI가 너무 작거나 크지 않게 유지

### Reference Resolution (기준 해상도)

- **1280 x 720** (720p) 입력
  - **의미**: 이 해상도를 **기준점**으로 삼아서 다른 해상도에서 비율 계산
  - 예: 1280x720 화면에서 버튼이 100픽셀이면, 2560x1440 화면에서는 자동으로 200픽셀로 커짐

### Match (매칭 기준)

- **Match**: `Height` (높이) 선택
- 슬라이더를 **완전히 오른쪽(1.0)**으로 이동
  - **의미**:
    - 0.0 = Width(가로) 기준으로 크기 조절
    - 1.0 = Height(세로) 기준으로 크기 조절
  - **Height 선택 시**: **세로 크기가 변할 때만** UI가 확대/축소됨
  - **가로 크기 변화**에는 UI 크기가 변하지 않음
  - **장점**: 와이드 모니터(21:9) vs 일반 모니터(16:9)처럼 **가로 비율이 달라도** UI 크기는 동일하게 유지

### Reference Pixels Per Unit

- **100** 유지 (기본값)
  - **의미**: 스프라이트 1 유닛이 몇 픽셀인지 정의하는 값
  - 기본값 사용 권장

## 4. 설정 테스트 및 확인

### 테스트용 이미지 추가

- Canvas 우클릭 → **UI** → **Image** 생성
- 실제 UI 요소가 어떻게 동작하는지 확인용

### 동작 확인

**세로 크기 변경 시**:

- Game 창을 세로로 줄이면 → 이미지도 **함께 작아짐**
- 세로로 늘리면 → 이미지도 **함께 커짐**

**가로 크기 변경 시**:

- Game 창 Aspect Ratio를 **16:9 → 5:4**로 변경
- 이미지 크기는 **그대로 유지**됨
- 위치만 상대적으로 바뀔 수 있음

**이 설정의 장점**:

- UI를 **모서리(왼쪽 위, 오른쪽 아래 등)**에 고정시키면
- 다양한 화면 비율에서도 **항상 같은 모서리**에 위치
- 크기만 신경 쓰면 되어 배치가 간편

### 테스트 이미지 삭제

- 확인이 끝나면 테스트용 Image 오브젝트 삭제

## ✅ 정리

- **Screen Space - Overlay**: UI가 화면 맨 앞에 표시
- **Scale With Screen Size**: 화면 크기에 따라 UI 자동 조절
- **Reference Resolution (1280x720)**: 크기 조절의 기준점
- **Match Height (1.0)**: 세로 크기 기준으로만 UI 확대/축소

이 설정은 **데스크톱 게임용**으로 최적화된 방식입니다. 모바일 세로 화면 게임이라면 Match를 Width 쪽으로 조절하거나, Reference Resolution을 세로로 긴 해상도(예: 1080x1920)로 바꾸면 됩니다.

## 2. 액션 버튼 디자인하기

### 버튼 생성

- UnitActionSystemUI 내부에서 **UI → Button** 생성
- 이름: **ActionButtonUI**

### 버튼 크기 설정

- Rect Transform의 Width, Height를 **60 x 60**으로 설정
- 정사각형 버튼으로 만듦

### 텍스트 오브젝트 설정

버튼 내부의 Text 자식 오브젝트 선택:

- 이름을 **Text**로 간단하게 변경
- Rect Transform은 **Stretch** 상태 유지 (부모를 따라감)

- 텍스트가 버튼 밖으로 나가지 않도록 **Left, Right 여백**을 각각 **3**으로 설정

- **Font Style**: **Bold**로 설정 → 두껍고 선명하게
- **Auto Size** 활성화
  - **Min Size**: **8** (최소 크기)
  - **Max Size**: **24** (최대 크기)
  - 이렇게 하면 어떤 텍스트를 넣어도 자동으로 크기가 조절되어 항상 버튼 안에 딱 맞게 들어감

## 3. Grid Layout Group으로 버튼 자동 배치

### 버튼을 Prefab으로 만들기

- 완성된 ActionButtonUI를 **Prefabs 폴더**로 드래그
- Prefab으로 만들면 나중에 코드로 복제(Instantiate)할 수 있음

### 버튼 컨테이너 생성

- UnitActionSystemUI 안에 **빈 게임 오브젝트** 생성
- 이름: **ActionButtonContainer**
- 이 안에 버튼들이 담길 예정

### 테스트용 버튼 배치

- ActionButtonUI Prefab을 Container 안으로 드래그
- **Duplicate**로 복사해서 총 **3개의 버튼** 배치
- 이것은 순전히 **시각적 테스트용**이며, 나중에 코드로 자동 생성할 예정

### Grid Layout Group 컴포넌트 추가

- ActionButtonContainer 선택
- **Add Component → Grid Layout Group** 추가

**Grid Layout Group**이란?

- 자식 오브젝트들을 **자동으로 격자 형태로 배치**해주는 컴포넌트
- 버튼 개수가 몇 개든 항상 일정한 간격으로 정렬됨

### Grid Layout Group 설정

**Cell Size (각 셀의 크기)**:

- Width: **60**
- Height: **60**
- 버튼 크기와 동일하게 설정

**Spacing (간격)**:

- X: **15** (버튼 사이 가로 간격)
- Y: **0** (세로 간격 없음)

**Start Corner (시작 지점)**:

- **Upper Left** 유지 (왼쪽 위부터 시작)

**Start Axis (배치 방향)**:

- **Horizontal** 유지 (가로 방향으로 배치)

**Child Alignment (정렬 위치)**:

- **Middle Center**로 설정
- 버튼들이 컨테이너의 중앙에 배치됨

**Constraint (배치 제약)**:

- **Fixed Row Count** 선택
- Row Count: **1**
- 항상 **1줄로만** 배치됨 (버튼이 아무리 많아도 한 줄)

### Grid vs Horizontal Layout Group

- **Horizontal Layout Group**을 써도 되지만, **Grid Layout Group**이 더 유연함
- 나중에 게임에 액션이 많아져서 여러 줄이 필요할 경우 Grid가 더 적합
- Grid는 행/열 제약을 자유롭게 조절 가능

### 컨테이너 위치 조정

- 컨테이너를 **화면 하단**에 배치
- **Anchor Presets**에서 **Bottom Center** 선택
- 약간 위로 올려서 적절한 위치에 배치

### Width와 Height는 0으로 설정

- Grid Layout Group은 자식 오브젝트의 크기에 따라 자동 배치하므로
- 컨테이너 자체의 Width, Height는 **0**으로 둬도 상관없음

## 4. Unit 스크립트에 BaseAction 배열 추가

### 기존 Unit 스크립트 구조

```csharp
public class Unit : MonoBehaviour
{
    private GridPosition gridPosition;
    private MoveAction moveAction;  // 이동 액션
    private SpinAction spinAction;  // 회전 액션

    private void Awake()
    {
        moveAction = GetComponent<MoveAction>();
        spinAction = GetComponent<SpinAction>();
    }
}
```

- 현재는 MoveAction, SpinAction을 **개별 필드**로 가지고 있음
- 액션이 추가될 때마다 필드를 일일이 추가해야 함 → 비효율적

### BaseAction 배열 추가

```csharp
private BaseAction[] baseActionArray;  // 모든 액션을 담을 배열

```

### GetComponents<T>()로 모든 액션 가져오기

```csharp
private void Awake()
{
    moveAction = GetComponent<MoveAction>();
    spinAction = GetComponent<SpinAction>();

    // 이 유닛에 붙어있는 모든 BaseAction 타입 컴포넌트를 배열로 가져옴
    baseActionArray = GetComponents<BaseAction>();
}

```

**GetComponents<T>() 메서드**:

- **GetComponent<T>()**: 한 개의 컴포넌트만 가져옴
- **GetComponents<T>()**: 해당 타입의 **모든 컴포넌트**를 배열로 가져옴
- 여기서는 BaseAction을 상속받은 모든 액션들(MoveAction, SpinAction 등)을 한 번에 가져옴

### Public 메서드로 배열 노출

```csharp
// UI에서 이 유닛의 액션 목록을 가져갈 수 있도록 public 메서드 제공
public BaseAction[] GetBaseActionArray()
{
    return baseActionArray;
}
```

- 외부(UI)에서 이 유닛이 어떤 액션들을 가지고 있는지 알 수 있게 함

## 5. UI 스크립트로 동적 버튼 생성

### UnitActionSystemUI 스크립트 생성

- Scripts 폴더에 **UnitActionSystemUI.cs** 생성
- UnitActionSystemUI 게임 오브젝트에 **스크립트 연결**

### using 구문 추가

```csharp
using UnityEngine;
using UnityEngine.UI;  // UI 관련 작업을 위해 필요
```

### SerializeField로 참조 변수 선언

```csharp
[SerializeField] private Transform actionButtonPrefab;  // 버튼 Prefab
[SerializeField] private Transform actionButtonContainerTransform;  // 버튼이 생성될 컨테이너
```

**Transform 타입을 사용하는 이유**:

- Instantiate할 때 Transform 타입으로 받으면 편리함
- 나중에 컴포넌트 접근도 쉬움

### Unity Editor에서 참조 연결

- Inspector에서 **actionButtonPrefab**에 ActionButtonUI Prefab 드래그
- **actionButtonContainerTransform**에 ActionButtonContainer 게임 오브젝트 드래그

### CreateUnitActionButtons() 메서드 작성

```csharp
private void CreateUnitActionButtons()
{
    // 1. 현재 선택된 유닛 가져오기
    Unit selectedUnit = UnitActionsSystem.Instance.GetSelectedUnit();

    // 2. 선택된 유닛의 모든 액션 가져오기
```

- `Instantiate(original, parent)`: **부모 지정** 방식
  - position, rotation은 신경 쓸 필요 없을 때 사용

## 6. 유닛 변경 시 UI 업데이트

### 문제점 발견

- 첫 번째 유닛은 2개 액션 (Move, Spin)
- 두 번째 유닛에서 Spin 액션 제거
- 하지만 두 번째 유닛 선택해도 여전히 2개 버튼이 표시됨

**원인**:

- 유닛을 바꿔도 `CreateUnitActionButtons()`가 다시 호출되지 않음
- 버튼이 갱신되지 않음

### UnitActionsSystem의 이벤트 활용

UnitActionsSystem에는 이미 **OnSelectedUnitChanged** 이벤트가 있음:

- 유닛 선택이 바뀔 때마다 발생하는 이벤트

### 이벤트 구독하기

```csharp
void Start()
{
    // 유닛 선택 변경 이벤트 구독
    UnitActionsSystem.Instance.OnSelectedUnitChanged += UnitActionsSystem_OnSelectedUnitChanged;

    CreateUnitActionButtons();
}

// 이벤트 핸들러 메서드
private void UnitActionsSystem_OnSelectedUnitChanged(object sender, EventArgs e)
{
    CreateUnitActionButtons();  // 유닛이 바뀔 때마다 버튼 다시 생성
}

```

**EventHandler 델리게이트**:

- C#의 표준 이벤트 패턴
- `using System;` 필요
- `object sender`: 이벤트를 발생시킨 객체
- `EventArgs e`: 이벤트 관련 추가 정보

### 또 다른 문제 발견

- 유닛을 바꿀 때마다 버튼이 **추가로 생성**됨
- 첫 유닛: 2개 → 두 번째 유닛 선택: 2+1=3개 → 다시 첫 유닛: 3+2=5개...
- **기존 버튼을 삭제하지 않아서** 계속 누적됨

### 기존 버튼 삭제 로직 추가

```csharp
private void CreateUnitActionButtons()
{
    // 1. 먼저 기존 버튼들을 모두 삭제
    foreach (Transform buttonTransform in actionButtonContainerTransform)
    {
        Destroy(buttonTransform.gameObject);  // Transform이 아닌 GameObject를 삭제
    }

    // 2. 새로운 버튼들 생성
    Unit selectedUnit = UnitActionsSystem.Instance.GetSelectedUnit();
    foreach (BaseAction baseAction in selectedUnit.GetBaseActionArray())
    {
        Transform actionButtonTransform = Instantiate(
            actionButtonPrefab,
            actionButtonContainerTransform
        );
    }
}

```

**foreach로 자식 순회**:

- `foreach (Transform child in parent)` 형태로 **모든 자식 Transform** 순회 가능
- Unity의 Transform은 IEnumerable을 구현하고 있어서 가능

**Destroy(transform) vs Destroy(gameObject)**:

- `Destroy(transform)`: **에러 발생**
  - Unity에서 Transform은 GameObject 없이 존재할 수 없음
  - GameObject도 Transform 없이 존재할 수 없음
  - 따라서 Transform만 삭제하는 것은 불가능
- `Destroy(gameObject)`: **정상 작동**
  - GameObject를 삭제하면 Transform도 함께 삭제됨

### 테스트용 버튼 추가

- Container에 미리 버튼 3개를 배치해 두면
- **편집 모드에서 UI 위치**를 시각적으로 확인 가능
- Play 모드 시작되면 이 버튼들은 삭제되고 실제 액션 버튼들이 생성됨

### 최종 테스트

- 첫 유닛 선택: Move, Spin 2개 버튼
- 두 번째 유닛 선택: Move 1개 버튼만
- 다시 첫 유닛: Move, Spin 2개 버튼
- **정상 작동!**

## 8. 추상 메서드로 액션 이름 구현

### 문제 상황

- `baseAction.GetActionName()`을 호출하려는데
- BaseAction에는 아직 이 메서드가 없음

### BaseAction에 추상 메서드 선언

```csharp
public abstract class BaseAction : MonoBehaviour
{
    protected Unit unit;
    protected bool isActive = false;
    protected Action onActionComplete;

    protected virtual void Awake()
    {
        unit = GetComponent<Unit>();
    }

    // 추상 메서드: 각 액션이 반드시 구현해야 함
    public abstract string GetActionName();
}

```

**abstract 키워드**:

- **추상 메서드**는 구현부가 없음 (세미콜론으로 끝남)
- 이 클래스를 상속받는 모든 자식 클래스는 **반드시 이 메서드를 구현**해야 함
- 강제성을 부여하여 일관성 유지

### MoveAction에서 구현

```csharp
public class MoveAction : BaseAction
{
    // ... 기존 코드 ...

    // GetActionName() 구현하지 않으면 컴파일 에러 발생
    public override string GetActionName()
    {
        return "Move";  // 이 액션의 이름 반환
    }
}

```

**override 키워드**:

- 부모의 추상 메서드나 가상 메서드를 **재정의**할 때 사용
- `abstract` 메서드는 반드시 `override`로 구현해야 함

### SpinAction에서 구현

```csharp
public class SpinAction : BaseAction
{
    // ... 기존 코드 ...

    public override string GetActionName()
    {
        return "Spin";  // 이 액션의 이름 반환
    }
}

```

### 컴파일 에러 확인

GetActionName()을 구현하지 않으면:

```
error CS0534: 'MoveAction' does not implement inherited abstract member 'BaseAction.GetActionName()'
```

- 이렇게 컴파일 단계에서 에러가 발생
- 실수로 메서드 구현을 빼먹을 일이 없음

- Play 모드 실행
- 첫 번째 유닛 선택: **MOVE**, **SPIN** 버튼 표시
- 두 번째 유닛 선택: **MOVE** 버튼만 표시

## 3. 익명 함수(Anonymous Function)와 람다 표현식(Lambda Expression) 개념

### 일반 함수 방식 (기존 방법)

```csharp
// 먼저 함수를 선언
private void MoveActionButtonClick()
{
    // 실행할 코드
}

// 그 함수를 전달
button.onClick.AddListener(MoveActionButtonClick);

```

- 이전에 `ClearBusy` 함수를 전달했던 방식과 동일
- 장점: 코드가 명확하고 재사용 가능
- 단점: 간단한 동작에도 별도 함수 선언 필요

### 익명 함수 방식 (새로운 방법)

```csharp
button.onClick.AddListener(() =>
{
    // 여기에 실행할 코드를 직접 작성
});
```

**구문 분석:**

- `()` : 매개변수 목록 (현재는 매개변수가 없으므로 빈 괄호)
- `=>` : 화살표 연산자 (equals + angle bracket으로 구성)
- `{ }` : 코드 블록 (실행할 코드를 작성하는 중괄호)

**의미:**

- 함수에 이름을 붙이지 않고 **즉석에서 정의**하는 방식
- 일반 함수와 기능은 동일하지만, 별도 선언 없이 사용 가능

### 람다 표현식의 다른 예시 (강의에서 언급)

```csharp
// LevelGrid 스크립트의 passthrough 함수에서 이미 사용했던 방식
someFunction((param) =>
{
    // 코드
});
```

### 왜 람다 표현식을 사용하는가?

- **간결성** : 짧은 코드를 위해 별도 함수를 만들 필요 없음
- **가독성** : 관련 코드가 한 곳에 모여있어 이해하기 쉬움
- **학습 목적** : 실무에서 자주 사용되므로 익숙해질 필요가 있음

## 8. Switch 문과 패턴 매칭 이해하기

### 코드 아키텍처 질문

**현재 상황:**

- `MoveAction`은 `Move(GridPosition, Action)` 함수 사용
- `SpinAction`은 `Spin(Action)` 함수 사용
- 각 액션마다 **함수 이름과 매개변수가 다름**

**문제점:**

- 일반적인 `TakeAction()` 같은 통일된 함수를 만들기 어려움
- 액션마다 필요한 정보가 다르기 때문

**해결 방법 (이번 강의):**

- C# 7의 **패턴 매칭(Pattern Matching)** 기능 사용
- Switch 문으로 액션 타입별로 다른 처리 수행

### C# 7의 Switch 패턴 매칭

```csharp
switch (selectedAction)
{
    case MoveAction moveAction:
        // selectedAction이 MoveAction 타입이면 이 블록 실행
        // moveAction 변수로 접근 가능
        break;

    case SpinAction spinAction:
        // selectedAction이 SpinAction 타입이면 이 블록 실행
        // spinAction 변수로 접근 가능
        break;
}

```

**구문 분석:**

- **`switch (selectedAction)`** : `selectedAction`의 타입을 검사
- **`case MoveAction moveAction:`**
  - `MoveAction` : 검사할 타입
  - `moveAction` : 이 블록 안에서 사용할 변수 이름 (캐스팅된 상태)
- 타입이 일치하면 해당 case 블록 실행

**일반적인 Switch와의 차이:**

- 일반 Switch : 값(정수, 문자열 등)으로 분기
- 패턴 매칭 : **타입(Type)** 으로 분기

### HandleSelectedAction 함수 완성

```csharp
private void HandleSelectedAction()
{
    if (Input.GetMouseButtonDown(0)) // 마우스 왼쪽 버튼 클릭 감지
    {
        // 마우스 위치를 그리드 좌표로 변환
        GridPosition mouseGridPosition = LevelGrid.Instance.GetGridPosition(MouseWorld.GetPosition());

        // 선택된 액션의 타입에 따라 다른 처리
        switch (selectedAction)
        {
            case MoveAction moveAction:
                // Move 액션인 경우

                // 1. 유효한 이동 위치인지 확인
                if (moveAction.IsValidActionGridPosition(mouseGridPosition))
                {
                    SetBusy(); // 액션 실행 중 상태로 변경
                    moveAction.Move(mouseGridPosition, ClearBusy); // 이동 실행
                }
                break;

            case SpinAction spinAction:
                // Spin 액션인 경우
                SetBusy(); // 액션 실행 중 상태로 변경
                spinAction.Spin(ClearBusy); // 회전 실행
                break;
        }
    }
}

```

**코드 상세 설명:**

**MoveAction 처리:**

1. **`case MoveAction moveAction:`** - `selectedAction`이 `MoveAction` 타입인지 확인
2. **`moveAction.IsValidActionGridPosition(mouseGridPosition)`**
   - 클릭한 위치가 이동 가능한 곳인지 검증
   - 이동 범위 내에 있는지, 다른 유닛이 없는지 등 확인
3. **`SetBusy()`** - `isBusy = true` 설정하여 액션 실행 중임을 표시
4. **`moveAction.Move(mouseGridPosition, ClearBusy)`**
   - 유닛을 목표 위치로 이동시킴
   - 이동 완료 시 `ClearBusy` 콜백 함수 호출

**SpinAction 처리:**

1. **`case SpinAction spinAction:`** - `selectedAction`이 `SpinAction` 타입인지 확인
2. **`SetBusy()`** - 액션 실행 중 상태로 변경
3. **`spinAction.Spin(ClearBusy)`**
   - 유닛을 회전시킴
   - 회전 완료 시 `ClearBusy` 콜백 함수 호출
   - Spin은 위치 검증이 필요 없음 (제자리 회전이므로)

## 9. 코드 리팩토링과 일관성 유지하기

### 입력 처리의 일관성 문제

**현재 상황:**

- `HandleSelectedAction` : 함수 **내부**에서 마우스 버튼 체크
- `TryHnadleUnitSelection` : 함수 **외부**(Update)에서 마우스 버튼 체크

**두 방식 모두 작동하지만:**

- **일관성(Consistency)** 이 중요함
- 팀 프로젝트나 유지보수 시 혼란 방지

### TryHnadleUnitSelection 함수 수정

```csharp
private bool TryHnadleUnitSelection()
{
    // 마우스 왼쪽 버튼 클릭 체크를 함수 내부로 이동
    if (Input.GetMouseButtonDown(0))
    {
        // 카메라에서 마우스 위치로 Ray 발사
        Ray ray = Camera.main.ScreenPointToRay(Input.mousePosition);

        // Raycast 수행 (유닛 레이어만 감지)
        if (Physics.Raycast(ray, out RaycastHit raycastHit, float.MaxValue, unitLayerMask))
        {
            // Ray가 유닛에 충돌했는지 확인
            if (raycastHit.transform.TryGetComponent<Unit>(out Unit unit))
            {
                SetSelectedUnit(unit); // 유닛 선택
                return true; // 유닛 선택 성공
            }
        }
    }
    return false; // 유닛 선택 실패
}
```

**변경사항:**

- 이전: Update에서 `if (Input.GetMouseButtonDown(0))` 체크 후 함수 호출
- 이후: 함수 내부에서 직접 입력 체크 수행
- 이제 `HandleSelectedAction`과 동일한 패턴 사용

### Update 함수 최종 정리

```csharp
private void Update()
{
    // 액션 실행 중이면 모든 입력 무시
    if (isBusy)
    {
        return;
    }

    // 유닛 선택 시도 (내부에서 입력 체크)
    // 유닛을 선택했으면 true 반환 → 아래 코드 실행 안 함
    if (TryHnadleUnitSelection())
    {
        return;
    }

    // 액션 실행 처리 (내부에서 입력 체크)
    HandleSelectedAction();
}
```

**개선된 코드의 장점:**

1. **가독성** : Update가 간결해지고 흐름 파악이 쉬움
2. **일관성** : 모든 입력 처리가 각 함수 내부에서 수행됨
3. **유지보수** : 각 기능이 독립적으로 관리됨

### 인라인 If문 제거

```csharp
// 이전 코드 (인라인 if)
if (TryHnadleUnitSelection()) return;

// 개선된 코드 (블록 사용)
if (TryHnadleUnitSelection())
{
    return;
}
```

**개선 이유:**

- 코드가 더 명확해짐
- 나중에 디버깅이나 코드 추가 시 편리함
- 중괄호 사용이 일관성 있는 코딩 스타일

## 10. 테스트 및 결과 확인하기

### 테스트 시나리오

**초기 상태 확인:**

- 게임 시작 시 자동으로 Move 액션이 선택되어 있어야 함
- UI에서 Move 버튼이 기본적으로 선택된 상태로 표시

**Move 액션 테스트:**

1. 유닛 선택
2. Move 액션 버튼 확인 (기본 선택)
3. 맵의 유효한 위치 클릭
4. **결과** : 유닛이 클릭한 위치로 이동

**Spin 액션 테스트:**

1. Spin 액션 버튼 클릭
2. 맵의 아무 곳이나 클릭
3. **결과** : 유닛이 제자리에서 회전

### 주의사항

**버튼 클릭 시 문제 방지:**

- Spin 버튼을 클릭할 때, 버튼 아래에 **유효한 그리드 위치가 없어야** 함
- 만약 버튼 아래에 유효한 이동 위치가 있다면:
  - 버튼 클릭 = Spin 액션 선택
  - 동시에 = Move 액션이 실행될 수 있음 (버튼 아래 위치로)

**왜 이런 문제가 발생하나?**

- Update 실행 순서:
  1. `TryHnadleUnitSelection()` - 유닛 선택 확인
  2. `HandleSelectedAction()` - 액션 실행
- 버튼 클릭도 마우스 클릭이므로 `HandleSelectedAction`이 감지할 수 있음

**해결 방법 (다음 강의 예고):**

- UI 클릭 시 게임 월드 클릭을 무시하는 처리 필요
- EventSystem을 사용한 UI 우선순위 처리

### 테스트 결과

- ✅ Move 액션 선택 시 클릭한 위치로 이동 가능
- ✅ Spin 액션 선택 시 제자리 회전 가능
- ✅ 버튼 클릭으로 액션 전환 가능
