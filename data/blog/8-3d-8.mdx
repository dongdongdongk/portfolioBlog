## 💡 핵심 개념: 클래스 의존성

### 의존성(Dependency)이란?

```
의존성 (Dependency)
  ↓
한 클래스가 다른 클래스를 "사용"하는 관계
  ├─ A 클래스가 B 클래스를 사용하면
  └─ "A는 B에 의존한다" (A depends on B)

예시:
  BP_KixPlayerController가 Character 클래스를 사용
    ↓
  BP_KixPlayerController는 Character에 의존
```

### 실생활 비유

```
자동차와 연료:
  ├─ 자동차는 연료에 의존함
  ├─ 연료 없으면 자동차 작동 안 됨
  └─ 하지만 연료는 자동차 몰라도 됨

프로그래밍:
  ├─ PlayerController는 Character에 의존
  ├─ Character 없으면 제어 불가능
  └─ Character는 PlayerController 몰라도 됨
```

---

## 🔍 의존성이 생기는 경우

### 1. 변수로 타입 사용

```
BP_KixPlayerController
  ↓
변수: Controlled Character (Character 타입)
  ↓
의존성: Character 클래스에 의존
```

**노드로 표현:**

```
Get Controlled Pawn
  ↓
Cast to Character
  ↓
Set Controlled Character (Character 타입 변수)
```

### 2. 캐스팅(Casting)

```
Cast to Character
  ↓
Character 클래스를 "알아야" 함
  ↓
의존성 발생
```

### 3. 함수 파라미터

```
함수: Do Something
  ├─ Input: Character 타입
  └─ 의존성: Character에 의존
```

## ⚠️ 순환 의존성 (Circular Dependency)

### 순환 의존성이란?

```
Circular Dependency (순환 의존성)
  ↓
두 클래스가 서로를 의존하는 상황
  ├─ A가 B에 의존
  └─ B가 A에 의존
       ↓
     서로 얽힘!
```

### 문제 상황 예시

```
나쁜 설계:
  BP_KixPlayerController
    ├─ BP_Kix에 의존 (Cast to BP_Kix)
    └─ "BP_Kix 필요해!"
         ↓
       BP_Kix
         ├─ BP_KixPlayerController에 의존
         └─ "BP_KixPlayerController 필요해!"
              ↓
            서로 의존! (순환)
```

**문제점:**

```
1. 분리 불가능
   ├─ BP_Kix 없이 PlayerController 사용 불가
   └─ PlayerController 없이 BP_Kix 사용 불가

2. 재사용 불가능
   ├─ 다른 프로젝트에 이식 어려움
   └─ 항상 두 개를 함께 가져가야 함

3. 유연성 상실
   ├─ 새 캐릭터 추가 어려움
   └─ 변경 시 두 클래스 모두 수정 필요

4. 테스트 어려움
   └─ 한 클래스만 테스트 불가능
```

## ✅ 좋은 설계: 단방향 의존성

### 단방향 의존성 (One-Way Dependency)

```
One-Way Dependency (단방향 의존성)
  ↓
한쪽만 다른 쪽을 의존
  ├─ A → B (A는 B에 의존)
  └─ B는 A를 모름
       ↓
     느슨한 결합 (Loose Coupling)
```

### 현재 프로젝트 구조

```
좋은 설계:
  BP_KixPlayerController
    ├─ Character에 의존 (엔진 클래스)
    └─ BP_Kix에 의존 안 함!
         ↓
       BP_Kix
         ├─ Character에서 상속
         ├─ PlayerController 모름
         └─ 독립적!
```

**장점:**

```
1. 분리 가능
   └─ PlayerController와 BP_Kix 독립적 사용

2. 재사용 가능
   └─ BP_Kix를 다른 프로젝트에 이식 쉬움

3. 유연성
   ├─ BP_Torque (새 캐릭터) 추가 가능
   └─ PlayerController 수정 불필요

4. 테스트 용이
   └─ 각 클래스 독립적으로 테스트
```

## 🎨 느슨한 결합 vs 강한 결합

### 강한 결합 (Tight Coupling)

```
Tight Coupling
  ↓
클래스들이 서로 강하게 연결됨
  ├─ 순환 의존성
  ├─ 직접적인 참조
  └─ 구체적인 클래스에 의존

예시:
  BP_JetFuel
    ↓
  Cast to BP_Kix
    ↓
  직접 변수 접근
    ↓
  강하게 결합됨
```

**문제:**

```
BP_Torque (새 캐릭터) 추가 시:
  BP_JetFuel 코드 수정 필요
    ├─ Cast to BP_Kix 실패
    ├─ Cast to BP_Torque 추가
    └─ 캐릭터 추가할 때마다 수정!
         ↓
       유지보수 악몽
```

### 느슨한 결합 (Loose Coupling)

```
Loose Coupling
  ↓
클래스들이 약하게 연결됨
  ├─ 단방향 의존성
  ├─ 인터페이스를 통한 통신
  └─ 추상화에 의존

예시:
  BP_JetFuel
    ↓
  Does Implement Interface? (BPI_Jetpack)
    ↓
  Handle Refill Fuel (인터페이스 함수)
    ↓
  느슨하게 결합됨
```

**장점:**

```
BP_Torque (새 캐릭터) 추가 시:
  1. BP_Torque에 BPI_Jetpack 구현
  2. Handle Refill Fuel 구현
  3. 끝!
       ↓
     BP_JetFuel 수정 불필요 ✅
       ↓
     유지보수 쉬움
```

## 🎯 인터페이스의 진정한 가치

### 왜 인터페이스를 사용하는가?

```
초보자의 생각:
  "Cast 하면 더 쉬운데 왜 인터페이스?"
    ├─ Cast to BP_Kix
    ├─ 직접 변수 접근
    └─ 간단하잖아!

하지만 문제:
  └─ 새 캐릭터마다 코드 수정
       ↓
     확장 불가능
```

### 인터페이스의 장점

```
Interface 사용:
  ├─ 구체적인 클래스에 의존 안 함
  ├─ 새 클래스 추가 시 기존 코드 수정 불필요
  └─ "계약(Contract)"만 지키면 됨

예시:
  BPI_Jetpack 인터페이스
    ├─ Handle Refill Fuel (계약)
    └─ 구현:
         ├─ BP_Kix의 방식
         ├─ BP_Torque의 방식
         └─ 각자 자유롭게!
```

## 📊 프로젝트 구조 분석

### 현재 의존성 그래프

```
BP_KixPlayerController
  ├─ → Character (엔진 클래스) ✅
  ├─ → BPI_Jetpack (인터페이스) ✅
  └─ ✗ BP_Kix (구체 클래스) ❌

BP_Kix
  ├─ → Character (상속) ✅
  ├─ → BPI_Jetpack (구현) ✅
  └─ ✗ BP_KixPlayerController ❌

BP_JetFuel (픽업)
  ├─ → BPI_Jetpack (인터페이스) ✅
  └─ ✗ BP_Kix ❌
  └─ ✗ BP_KixPlayerController ❌

결과:
  └─ 모두 단방향 의존성! ✅
```

### 왜 이렇게 설계했나?

```
1. PlayerController
   ├─ Character만 알면 됨
   └─ 어떤 Character든 제어 가능
        (BP_Kix, BP_Torque, BP_Human 등)

2. BP_Kix
   ├─ Character에서 상속
   ├─ BPI_Jetpack 구현
   └─ PlayerController 몰라도 됨

3. BP_JetFuel
   ├─ BPI_Jetpack만 알면 됨
   └─ 어떤 캐릭터든 연료 보충 가능
```

### Dependency (의존성)

```
의존성
  ↓
한 클래스가 다른 클래스를 사용하는 관계
  ├─ "알아야 한다"
  └─ "필요하다"
```

### Circular Dependency (순환 의존성)

```
순환 의존성
  ↓
두 클래스가 서로를 의존
  ├─ A → B
  └─ B → A
       ↓
     나쁜 설계!
```

```
느슨한 결합
  ↓
클래스들이 약하게 연결됨
  ├─ 단방향 의존성
  ├─ 인터페이스 사용
  └─ 독립적으로 변경 가능
       ↓
     좋은 설계!
```

### Tight Coupling (강한 결합)

```
강한 결합
  ↓
클래스들이 강하게 연결됨
  ├─ 순환 의존성
  ├─ 직접 참조
  └─ 함께 변경 필요
       ↓
     나쁜 설계!
```

## 🎓 코딩 원칙

### SOLID 원칙 중 일부

### Dependency Inversion Principle

```
의존성 역전 원칙
  ↓
구체적인 것이 아닌 추상적인 것에 의존
  ├─ BP_Kix (구체) ❌
  └─ BPI_Jetpack (추상) ✅

예시:
  PlayerController → BPI_Jetpack
    └─ 인터페이스에 의존 (추상)
```

### Open/Closed Principle

```
개방/폐쇄 원칙
  ↓
확장에는 열려있고, 수정에는 닫혀있어야 함
  ├─ 새 캐릭터 추가: 가능 (확장)
  └─ 기존 코드 수정: 불필요 (폐쇄)

인터페이스 사용 시:
  └─ 이 원칙 자동으로 달성 ✅
```

## 💡 핵심 요약

```
클래스 의존성
  ↓
한 클래스가 다른 클래스를 사용하는 관계
  ↓
  ├─ 단방향: 좋음 ✅
  │    └─ A → B (B는 A 모름)
  │
  └─ 순환: 나쁨 ❌
       └─ A ⇄ B (서로 알아야 함)

해결책:
  └─ 인터페이스 사용
       ├─ 구체 클래스 대신 추상화
       ├─ 느슨한 결합 유지
       └─ 확장 가능한 설계
```

**이번 강의의 핵심:**

- 의존성은 피할 수 없지만 관리해야 함
- 순환 의존성은 피해야 함
- 단방향 의존성이 좋은 설계
- 인터페이스는 느슨한 결합의 핵심
- 구체보다 추상에 의존
- 당장 복잡해 보여도 장기적으로 이득

**다음 강의:**

- 연료 보충 시 UI 업데이트 문제 해결
- Event Dispatcher (이벤트 디스패처)
- 의존성 없이 알림 보내기
- Observer Pattern 구현

## 📝 핵심 노드 정리

### Get Controller

```
Get Controller
  ├─ Target: Pawn (Self)
  └─ Return: Controller
       └─ 이 Pawn을 제어하는 Controller

용도:
  Pawn이 자신의 Controller 참조 필요할 때
```

### Validated Get

```
Validated Get
  ├─ 변수 가져오기 + 유효성 검사
  ├─ Is Valid: 값이 유효함 (null 아님)
  └─ Is Not Valid: 값이 null
       ↓
     안전한 접근
```

**일반 Get vs Validated Get:**

```
Get (일반):
  └─ 값 가져오기만 함
       null이면 에러 발생 가능

Validated Get:
  └─ 값 가져오기 + null 체크
       null이면 Is Not Valid 경로로
       ↓
     크래시 방지 ✅
```

## 💾 메모리 비용 - 핵심 문제!

### Hard Reference란?

```
Hard Reference (하드 레퍼런스)
  ↓
"강한 참조" = 반드시 함께 로드
  ├─ A가 B를 Cast하면
  └─ A 로드 시 B도 자동 로드
       ↓
     메모리에 함께 존재
```

**실생활 비유:**

```
하드 레퍼런스 = 짐에 붙어있는 무거운 돌
  ├─ 짐(Blueprint) 들 때
  └─ 돌(Referenced Asset)도 함께 들어야 함
       ↓
     짐이 무거워짐!
```

### 현재 상황 분석

```
BP_Kix
  ↓
Cast to BP_KixPlayerController
  ↓
Hard Reference 생성
  ↓
BP_Kix 로드 시
  └─ BP_KixPlayerController도 함께 로드
       ↓
     BP_Kix 메모리 크기 증가!
```

## 🎯 Polymorphism (다형성) - 고급 개념

### 다형성이란?

```
Polymorphism (다형성)
  ↓
"같은 이름, 다른 동작"
  ├─ 부모 타입으로 저장
  └─ 자식 구현 실행
```

**실제 동작:**

```
BP_Kix에서:
  ├─ 변수 타입: BP_PlayerControllerBase
  ├─ 실제 객체: BP_KixPlayerController
  └─ Fuel Update 호출
       ↓
     어느 구현 실행?
       ↓
     자식 구현! (Override된 버전)
```

### 왜 작동하나?

```
변수에 저장된 것:
  └─ BP_PlayerControllerBase 타입

하지만 실제 객체:
  └─ BP_KixPlayerController 인스턴스

함수 호출 시:
  ├─ "런타임"에 실제 타입 확인
  └─ 자식의 Override 버전 실행
       ↓
     다형성! ✅
```

**코드로 비유:**

```
Parent parent = new Child();
  ├─ 변수 타입: Parent
  └─ 실제 객체: Child

parent.doSomething();
  └─ Child의 doSomething() 실행!
```

## 🎓 Pattern 비교 정리

### Interface vs Base Class

```
Interface (BPI_Jetpack):
  ├─ Hard Reference: 없음 ✅
  ├─ 유연성: 매우 높음
  ├─ 관계: 독립적
  └─ 사용: 완전히 다른 클래스 간

Base Class (BP_PlayerControllerBase):
  ├─ Hard Reference: 최소화 ✅
  ├─ 유연성: 높음
  ├─ 관계: 상속
  └─ 사용: 같은 계열의 클래스
```

### 언제 무엇을 쓰나?

```
Interface 사용:
  ├─ 완전히 다른 종류 (픽업 ↔ 캐릭터)
  ├─ 여러 클래스가 구현
  └─ Hard Reference 제거 필요

Base Class 사용:
  ├─ 같은 계열 (PlayerController 변형들)
  ├─ 상속 관계 유지 필요
  └─ Hard Reference 최소화 필요

둘 다 사용:
  └─ 상황에 맞게 조합 가능!
```

- 4096 x 4096 = 4K보다 큰 텍스처

**크기별 용량**

```

2048 x 2048 → 4K (5.6MB 정도)
1024 x 1024 → 2K (1.4MB 정도)
512 x 512   → 하프K (0.3MB 정도)
```

```

2. **T_Kick_E (Emissive - 발광)**

   - 크기: 2048 x 2048 (4K)

## 💡 지연 로딩 개념

### 지연 로딩(Lazy Loading)이란?

**필요할 때까지 기다렸다가 로드하는 방식**

```
일반 로딩 (지금 상태)
  게임 시작
    ↓
  BP_JetFuel 로드
    ↓
  Niagara System도 즉시 로드 ❌
    └─ 사용 안 해도 메모리 차지

지연 로딩 (목표)
  게임 시작
    ↓
  BP_JetFuel 로드
    ↓
  Niagara System은 아직 로드 안 함 ✅
    ↓
  플레이어가 연료 픽업과 충돌
    ↓
  그때 Niagara System 로드
```

### 실제 사례

```
30분 동안 제트팩 안 쓰는 경우
  ├─ 연료 픽업을 볼 일 없음
  ├─ Niagara 효과 필요 없음
  └─ 메모리 낭비!

지연 로딩 적용 시
  └─ 30분 동안 0.88MB 절약
```

## 🔧 하드 레퍼런스 vs 소프트 레퍼런스

### 현재 상태: Hard Reference

```
BP_JetFuel → HandlePickup 함수
  └─ Spawn System at Location
      └─ System Template: NS_FuelPickup
          (직접 선택됨 = 하드 레퍼런스)
```

**하드 레퍼런스 특징**

```
에셋을 직접 선택
  ↓
Blueprint 로드될 때
  ↓
선택된 에셋도 즉시 로드
  └─ 메모리에 항상 존재
```

### 목표: Soft Object Reference

**파일 경로만 저장, 실제 로드는 나중에**

```
Soft Object Reference
  ├─ 실제 에셋이 아님
  ├─ 파일 경로만 저장
  └─ 필요할 때 경로로 찾아서 로드
```

## 🛠️ 소프트 레퍼런스로 변경하기

### 1단계: 변수로 승격

```
HandlePickup 함수 열기
  ↓
Spawn System at Location 노드의
System Template 입력 우클릭
  ↓
Promote to Variable (변수로 승격)

변수 이름: PickupEffect

**Promote to Variable이란?**

- 직접 연결된 값을 변수로 만드는 기능
- 나중에 타입 변경 가능

### 2단계: Soft Object Reference로 변경

```
Variables 패널에서 PickupEffect 선택
  ↓
Details → Variable Type 드롭다운
  ↓
하단의 "Change to" 섹션
  ├─ Object Reference (현재 - 파란색)
  ├─ Class Reference (보라색)
  ├─ Soft Object Reference ✅ (하늘색)
  └─ Soft Class Reference (하늘색)

Soft Object Reference 선택
```

```
파란색 = Object Reference (일반)
보라색 = Class Reference (클래스용)
하늘색 = Soft Reference (지연 로딩용)

```
경고: "연결이 끊어질 수 있음"

  └─ Spawn System 노드와 호환 안 됨

## 🔧 해결 방법 1: Load Asset (Blocking)

### 블로킹 로드란?

**에셋을 로드할 때까지 게임이 멈춤**

```
Blocking Call (차단 호출)
  ├─ 로딩 시작
  ├─ 로딩 완료될 때까지 대기
  ├─ 게임이 일시 정지 (freeze)
  └─ 로딩 완료 후 계속 진행
```

### 구현 방법

```
HandlePickup 함수

Is Valid 노드 추가
  ├─ Input: PickupEffect (Convert 후)
  ├─ Is Valid: 이미 로드됨 → 시스템 스폰
  └─ Is Not Valid: 아직 안 로드됨
      ↓
      Load Asset (Blocking) 노드
        ├─ Input: PickupEffect (Soft Reference)
        ├─ Return: Object Reference
        └─ 로딩 완료될 때까지 대기
      ↓
      Convert 노드 (다시)
      ↓
      Spawn System at Location
```

**Is Valid 노드란?**

- 값이 유효한지(존재하는지) 확인
- 두 개의 실행 핀
  - Is Valid: 값 있음
  - Is Not Valid: null (값 없음)

### 실행 흐름

```
첫 번째 충돌
  ├─ Is Valid 체크 → Not Valid
  ├─ Load Asset (Blocking) 실행
  │   └─ 게임 일시 정지 (짧게)
  ├─ Niagara 로드 완료
  └─ 효과 스폰

두 번째 충돌
  ├─ Is Valid 체크 → Valid
  ├─ 이미 로드됨
  └─ 바로 효과 스폰
```

### 장단점

```
✅ 장점
  ├─ 구현 간단
  └─ 확실하게 로드됨

❌ 단점
  ├─ 게임이 잠깐 멈춤 (hitching)
  └─ 중요한 순간에 사용 시 문제
```

### 사용 적합한 경우

```
로딩 화면 있을 때
  ├─ "Loading..." 표시
  ├─ 로딩 바 표시
  └─ 사용자가 대기 예상

게임 중에는 비추천
  └─ 끊김 현상 발생
```

## 🚀 해결 방법 2: Async Load Asset (비동기)

### 비동기 로딩이란?

**백그라운드에서 로드하면서 게임은 계속 진행**

```
Async Call (비차단 호출)
  ├─ 로딩 시작
  ├─ 다른 스레드에서 로딩
  ├─ 게임은 계속 진행 ✅
  └─ 로딩 완료되면 알림
```

**스레드(Thread)란?**

- CPU가 작업을 처리하는 통로
- 여러 스레드 = 여러 작업 동시 진행
- 메인 스레드: 게임 실행
- 로딩 스레드: 에셋 로드

### 함수에서 사용 불가

```
⚠️ Async Load Asset은 Latent 노드
  ├─ 시간이 걸리는 작업
  ├─ 완료 핀이 있음
  └─ 함수에서 사용 불가

함수는
  ├─ 즉시 완료되어야 함
  └─ Delay, Timeline 등도 사용 불가

해결책
  └─ Custom Event로 만들기
```

### 1단계: Custom Event 만들기

```
Event Graph (이벤트 그래프)
  ↓
우클릭 → Add Custom Event
  ↓
이름: LoadPickupEffect
```

**Custom Event란?**

- 직접 만드는 이벤트
- Call 노드로 어디서든 호출 가능
- Latent 노드 사용 가능

### 2단계: Async Load Asset 노드

```
PickupEffect 변수 드래그
  ↓
검색: "async load"
  ↓
Async Load Asset 선택
```

**노드 구조**

```
Async Load Asset
  ├─ 입력
  │   └─ Asset (Soft Object Reference)
  ├─ 출력 실행 핀 (2개)
  │   ├─ [빈 핀]: 즉시 실행 (로딩 시작)
  │   └─ Completed: 로딩 완료 후 실행
  └─ 출력 값
      └─ Loaded Object
```

### 3단계: 완료 후 스폰

```
Completed 핀
  ↓
PickupEffect 변수 → Resolve Soft Object Reference
  ↓
Spawn System at Location
  ├─ System Template: (연결)
  ├─ Location: GetActorLocation
  └─ Rotation: (0,0,0)
```

## 📊 실행 흐름 비교

### Blocking 방식

```
연료 충돌
  ↓
Is Not Valid
  ↓
Load Asset (Blocking) 시작
  ↓
⏸️ 게임 일시 정지
  ↓
로딩 완료 (0.1초?)
  ↓
▶️ 게임 재개
  ↓
효과 스폰
```

### Async 방식

```
연료 충돌
  ↓
Is Not Valid
  ↓
LoadPickupEffect 호출
  ↓
Async Load Asset 시작
  ├─ [빈 핀] 즉시 실행 (아무것도 안 함)
  └─ 백그라운드 로딩 시작

▶️ 게임 계속 진행 (플레이어 조작 가능)

(0.1초 후)
Completed 핀 실행
  ↓
효과 스폰
```

### 실제 체감

```
Blocking
  └─ 충돌 → (짧은 멈춤) → 효과

Async
  └─ 충돌 → (약간 늦게) → 효과
      └─ 멈춤 없음!
```

## 🎓 핵심 정리

### Hard Reference vs Soft Reference

```
Hard Reference (일반)
  ├─ Blueprint 로드 시 즉시 로드
  ├─ 메모리 항상 차지
  ├─ 사용: 자주 쓰는 에셋
  └─ 색상: 파란색

Soft Object Reference (지연)
  ├─ 파일 경로만 저장
  ├─ 필요할 때 수동 로드
  ├─ 사용: 가끔 쓰는 에셋
  └─ 색상: 하늘색
```

### 로딩 방식 비교

```
Load Asset (Blocking)
  ✅ 간단함
  ✅ 확실함
  ❌ 게임 멈춤
  사용: 로딩 화면

Async Load Asset
  ✅ 게임 안 멈춤
  ✅ 자연스러움
  ❌ 약간 복잡
  ❌ Event Graph 필요
  사용: 게임 중
```

### 변환 노드들

```
Convert (자동 생성)
  └─ Soft → Object 변환
  └─ 안 로드된 건 null

Resolve Soft Reference (수동)
  └─ Soft → Object 변환
  └─ 이름만 다름
```

### 최적화 전략

```
1. Size Map으로 큰 에셋 찾기
2. 자주 안 쓰는 에셋 확인
3. Soft Reference로 변경
4. Async Load로 지연 로딩
5. 첫 사용 시에만 로드
```

## ⚠️ 주의사항

### 함수 vs Event Graph

```
❌ 함수에서는
  └─ Latent 노드 사용 불가
      ├─ Async Load
      ├─ Delay
      └─ Timeline

✅ Event Graph에서만
  └─ Latent 노드 사용 가능
```

### 언제 지연 로딩?

```
적합한 경우
  ├─ 가끔 사용하는 에셋
  ├─ 큰 에셋 (1MB+)
  ├─ 선택적 기능
  └─ 나중에 필요한 것

부적합한 경우
  ├─ 항상 사용
  ├─ 매우 작은 에셋 (<100KB)
  ├─ 즉시 필요
  └─ 게임 시작 필수
```

### 테스트 필수

```
반드시 확인
  ├─ 에디터 재시작 후 테스트
  ├─ 첫 로딩 지연 확인
  ├─ 두 번째부터 즉시 작동 확인
  └─ 게임 멈춤 없는지 확인
```
