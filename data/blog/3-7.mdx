# { 🎮 UI 입력 모드 & 버튼 기능 구현 }

## 🎯 목표

마우스 커서를 표시하고, 버튼 클릭으로 재시작/종료 기능 구현하기

---

## 📋 전체 시스템 구조

```
UI 입력 시스템
  ├─ Player Controller로 로직 이동
  │   ├─ Show End Game Widget 함수
  │   └─ 입력 모드 제어
  │
  ├─ 입력 모드 변경
  │   ├─ UI Only (메뉴 표시 시)
  │   └─ Game Only (게임 플레이 시)
  │
  └─ 버튼 기능
      ├─ Replay: 레벨 재시작
      └─ Quit: 게임 종료
```

## 🎮 1단계: Player Controller로 로직 이동

### 1-1. 왜 Player Controller인가?

**Player Controller의 역할**

```
특징:
  ✅ 입력 처리
  ✅ UI 관리
  ✅ 마우스 커서 제어
  ✅ 게임 흐름 제어

vs Character:
  └─ Character: 게임플레이 로직
  └─ Player Controller: 입력/UI 로직
```

💡 **설계 원칙**: 책임 분리 (Separation of Concerns)

### 1-2. BP_Player_Controller_Base에 함수 추가

**함수 생성**

```
BP_Player_Controller_Base
  ↓

  ├─ 이름: Show End Game Widget
  └─ 입력 추가
      ├─ 이름: Won Game
      └─ 타입: Boolean
```

**자식 클래스에서 구현**

```
함수 내용: 비워둠
이유: 자식 클래스(BP_Kix_Player_Controller)에서 Override
```

## 🔧 2단계: BP_Kix_Player_Controller에서 구현

### 2-1. Override 함수

**함수 Override**

```
BP_Kix_Player_Controller
  ↓
Functions → Override
  └─ Show End Game Widget 선택
```

**Override란?**

```
개념: 부모 함수를 자식에서 재정의
효과:
  ├─ 부모의 빈 함수를 채움
  └─ 자식만의 로직 구현

장점:
  ✅ 부모에서 호출 가능
  ✅ Casting 불필요
```

### 2-2. Soft Class Reference 변수

```
Variables → + 버튼
  ├─ 이름: End Game Widget Class
  ├─ 타입: WBP_End_Game
  └─ Soft Class Reference: 체크 ✅

Details 패널에서 설정:
  └─ Default Value: WBP_End_Game
```

### 2-3. Load End Game Widget Class (Custom Event)

**Custom Event 생성**

```
이름: Load End Game Widget Class

내용:
  Async Load Class Asset
    ├─ Asset Class: End Game Widget Class
    └─ Completed → Create End Game Menu
```

**역할**

```
Soft Reference를 실제 클래스로 로드
  ↓
로딩 완료 시 위젯 생성
```

### 2-4. Show End Game Widget 구현

**노드 구조**

```
Show End Game Widget
  ↓
Is Valid Class?
  ├─ Class: End Game Widget Class
  └─ Return Value
      ↓
Branch
  ├─ True → Create End Game Menu (이미 로드됨)
  └─ False → Load End Game Widget Class (로드 필요)
```

**기존 문제**

```
  ↓
```

```
  └─ 이름: Set Position to Center
```

### 5-2. 함수 구현

**노드 구조**

```
Get Viewport Size
  ↓
Split (X, Y)
  ↓
/ 4 (약간 위쪽 배치)

Size Box Root
  ├─ Get Width Override
  └─ Get Height Override
  ↓
/ 2

계산:
  Position X = ViewportX / 4 - Width / 2
  Position Y = ViewportY / 4 - Height / 2
  ↓
Make Vector2D
  ↓
Set Position in Viewport
  └─ Target: Self
```

**Self 사용**

```
위젯 자체에서 호출
  └─ Target: Self (이 위젯)
```

**각 노드 설명**

**Get Player Controller**

```
용도: 플레이어 컨트롤러 가져오기
입력: Player Index (0 = 첫 번째)
출력: Player Controller
활용: 입력 모드 복원
```

**Set Input Mode Game Only**

```
용도: 입력을 게임으로만 제한
효과:
  ✅ 캐릭터 조작 가능
  ✅ 키보드 입력 작동
  ❌ UI 입력 무시

  └─ 남은 입력 버퍼 비우기
```

**Open Level (by Object Reference)**

```
용도: 레벨 로드
입력: Level (Soft Object Reference)
효과: 레벨 재시작

vs by Name:
  ├─ by Name: 문자열 (오타 위험)
  └─ by Object: 직접 선택 ✅
```

💡 **Soft Object Reference**

- 레벨은 자동으로 Soft Reference
- 메모리 효율적
- 필요할 때 로드

```
   │   │   └─ Async Load → Create End Game Menu
   │   └─ True → Create End Game Menu
   ↓
6. Create End Game Menu
   ├─ Create Widget
```

## 🎯 입력 모드 비교

### UI Only vs Game Only

```
UI Only
  ✅ 마우스 클릭 → 위젯
  ✅ 키보드 → 위젯 (포커스)
  ❌ WASD → 무시
  ❌ 마우스 → 카메라 회전 안 됨

Game Only
  ❌ 마우스 클릭 → 위젯 무시
  ❌ 키보드 → 위젯 무시
  ✅ WASD → 캐릭터 이동
  ✅ 마우스 → 카메라 회전

Game and UI (사용 안 함)
  ✅ 모든 입력 작동
  └─ 혼란 가능성
```

## ⚠️ 주의사항

### 1. 입력 모드 복원

```
❌ UI Only로 변경 후 복원 안 하면
  └─ 게임 조작 불가

✅ Replay 버튼에서
  └─ Set Input Mode Game Only
  └─ Set Show Mouse Cursor(false)
```

### 2. Soft Reference 설정

```
❌ End Game Widget Class 설정 안 하면
  └─ Async Load 실패
  └─ 위젯 표시 안 됨

✅ Details 패널에서 설정
  └─ Default Value: WBP_End_Game
```

### 3. Get Player Controller

```
Player Index: 0
  └─ 첫 번째 플레이어

멀티플레이어:
  ├─ 각 플레이어 Index 다름
  └─ 적절한 Index 사용 필요
```

### 4. Widget 변수 저장

```
❌ 변수 저장 안 하면
  └─ Set Input Mode에서 참조 불가

✅ Promote to Variable
  └─ End Game Widget
```

## 📋 핵심 개념: Delegate (델리게이트)

### Delegate란?

```
개념: 이벤트를 "방송"하는 시스템
비유: 라디오 방송국

방송국 (Delegate):
  └─ 신호 송출 (Call)

청취자 (Listener):
  └─ 라디오 켜고 듣기 (Bind)

특징:
  ✅ 방송국은 누가 듣는지 몰라도 됨
  ✅ 청취자는 원할 때 튜닝
  ✅ 여러 청취자 가능
```

### Blueprint에서의 이름

```
C++ 용어: Delegate (델리게이트)
Blueprint 용어: Event Dispatcher (이벤트 디스패처)

→ 같은 개념, 다른 이름
```

---

## 🏗️ 현재 구조의 문제점

### 기존 방식

```
WBP_End_Game (위젯)
  ├─ On Clicked (Button_Quit)
  │   └─ Quit Game ❌ (직접 호출)
  │
  └─ On Clicked (Button_PlayAgain)
      ├─ Set Input Mode ❌
      ├─ Set Show Mouse Cursor ❌
      └─ Open Level ❌ (직접 호출)
```

**문제점**

```
위젯이 너무 많은 책임:
  ❌ 게임 종료
  ❌ 입력 모드 제어
  ❌ 레벨 관리

→ 위젯은 "표시"만 해야 함!
```

### 개선된 방식

```
WBP_End_Game (위젯)
  ├─ On Clicked (Button_Quit)
  │   └─ Call On Quit (이벤트 방송만) ✅
  │
  └─ On Clicked (Button_PlayAgain)
      └─ Call On Play Again (이벤트 방송만) ✅

BP_Kix_Player_Controller
  ├─ On Quit 이벤트 수신
  │   └─ Quit Game (실제 처리)
  │
  └─ On Play Again 이벤트 수신
      ├─ Set Input Mode
      ├─ Set Show Mouse Cursor
      └─ Open Level
```

**장점**

```
책임 분리:
  ✅ 위젯: UI 표시 + 이벤트 방송
  ✅ Controller: 게임 로직 처리
  ✅ 느슨한 결합 (Loose Coupling)
```

## 🔗 2단계: Event Dispatcher에 이벤트 할당

### 2-1. 개념 이해

**Bind (바인딩)이란?**

```
의미: 이벤트를 델리게이트에 "연결"
비유: 라디오 주파수 맞추기

Bind 전:
  Call On Quit 호출
    → 아무 일도 안 일어남

Bind 후:
  Call On Quit 호출
    → Bind된 이벤트 실행 ✅
```

### 2-2. Custom Event 생성

**AssignToEndMenuDelegates**

```
BP_Kix_Player_Controller
  ↓
Event Graph
  ↓
우클릭 → Add Custom Event
  └─ 이름: AssignToEndMenuDelegates
```

**입력 추가**

```
Details 패널 → Inputs
  ├─ 이름: End Menu (또는 End Game Widget)
  └─ 타입: WBP_End_Game (Object Reference)
```

💡 **왜 Custom Event?**

```
함수 안 되는 이유:
  ❌ Bind는 비동기적
  ❌ 함수에서 불가능

Custom Event:
  ✅ Event Graph에서 실행
  ✅ Bind 가능
```

### 2-3. Bind Event 노드 사용

**노드 구조**

```
AssignToEndMenuDelegates
  ↓
End Menu (입력)
  ↓
Is Valid?
  ├─ Is Not Valid → (종료)
  └─ Is Valid
      ↓
End Menu 드래그
  └─ On Quit → Bind Event to On Quit
      ↓
  On Quit_Event 자동 생성
```

**Bind Event to On Quit**

```
용도: 델리게이트에 이벤트 연결
입력:
  ├─ Target: 위젯 (End Menu)
  └─ Event: 연결할 이벤트 (자동 생성)
효과:
  └─ Call On Quit 시 Event 실행
```

**자동 생성되는 이벤트**

```
이름: On Quit_Event (빨간색 노드)
타입: Custom Event
용도: 실제 로직 구현 위치
```

### 2-4. On Quit 이벤트 구현

```
On Quit_Event
  ↓
Quit Game
  ├─ Specific Player: None
  ├─ Quit Preference: Quit
  └─ Ignore Platform Restrictions: false
```

### 2-5. On Play Again도 동일하게

```
End Menu 드래그
  └─ On Play Again → Bind Event to On Play Again
      ↓
  On Play Again_Event 자동 생성
      ↓
  구현:
    ├─ Set Input Mode Game Only
    │   └─ Player Controller: Self
    ├─ Set Show Mouse Cursor: false
    └─ Open Level (JetpackLevel)
```

## 🎓 핵심 노드 기능

### Event Dispatcher 관련

**Call [Event Dispatcher]**

```
용도: 델리게이트 호출 (방송)
입력: Target (델리게이트 소유 객체)
효과: Bind된 모든 이벤트 실행
비유: 라디오 송출

예시:
  Call On Quit
    └─ On Quit에 Bind된 이벤트들 실행
```

**Bind Event to [Event Dispatcher]**

```
용도: 델리게이트에 이벤트 연결
입력:
  ├─ Target: 델리게이트 소유 객체
  └─ Event: 연결할 이벤트 (자동 생성)
효과: Call 시 Event 실행
비유: 라디오 주파수 맞추기

예시:
  Bind Event to On Quit
    ├─ Target: End Menu Widget
    └─ Event: On Quit_Event
```

**Unbind (사용 안 함, 참고용)**

```
용도: 델리게이트에서 이벤트 분리
사용: 메모리 정리, 더 이상 필요 없을 때
```

## 💡 Event Dispatcher vs 기존 방식

### 기존 방식 (함수 직접 호출)

```
WBP_End_Game
  ↓
Get Player Controller
  ↓
Cast to BP_Kix_Player_Controller
  ↓
함수 호출

문제점:
  ❌ 위젯이 Controller 타입 알아야 함
  ❌ 강한 결합 (Tight Coupling)
  ❌ 확장 어려움
```

### Event Dispatcher 방식

```
WBP_End_Game
  ↓
Call On Quit (방송)

Player Controller
  ↓
On Quit_Event (수신)

장점:
  ✅ 위젯은 Controller 몰라도 됨
  ✅ 느슨한 결합 (Loose Coupling)
  ✅ 여러 객체가 동시 수신 가능
  ✅ 확장 쉬움
```

## 🏗️ 설계 원칙

### 1. 단일 책임 원칙 (Single Responsibility)

```
WBP_End_Game:
  ✅ UI 표시
  ✅ 버튼 클릭 감지
  ✅ 이벤트 방송
  ❌ 게임 로직 (X)

BP_Kix_Player_Controller:
  ✅ 입력 모드 제어
  ✅ 레벨 관리
  ✅ 게임 흐름 제어
  ❌ UI 렌더링 (X)
```

### 2. 느슨한 결합 (Loose Coupling)

```
위젯은 누가 듣는지 몰라도 됨
  ↓
Call만 하면 됨
  ↓
새 리스너 추가 쉬움
  ↓
유지보수 편함
```

### 3. 이벤트 기반 아키텍처

```
동작 → 이벤트 발생 → 리스너 반응

예시:
  버튼 클릭 → On Quit 방송 → 여러 시스템 반응
```

## 📝 주의사항

### 1. Compile 필수

```
❌ Event Dispatcher 추가 후 Compile 안 하면
  └─ 다른 곳에서 접근 불가

✅ 추가 즉시 Compile
  └─ Bind 가능
```

### 2. Bind 타이밍

```
❌ 위젯 생성 전 Bind
  └─ Target이 없어서 실패

✅ 위젯 생성 후 Bind
  └─ 정상 작동
```

### 3. 변수 정리

```
❌ 중복 변수 사용
  └─ 혼란, 버그 유발

✅ 하나의 변수만 사용
  └─ End Game Widget
```

### 4. Is Valid 체크

```
✅ Bind 전 Is Valid 체크
  └─ Null Reference 방지
```

### 5. Unbind (메모리 관리)

```
위젯 제거 시:
  └─ Unbind 권장 (메모리 누수 방지)

하지만:
  └─ 위젯 Destroy 시 자동 정리됨
```

## 🎓 핵심 정리

### Event Dispatcher란?

```
개념: 이벤트 방송 시스템
비유: 라디오 방송
목적: 느슨한 결합

작동:
  1. Declare (선언)
  2. Call (방송)
  3. Bind (수신 등록)
  4. Event (반응)
```

### 장점

```
✅ 느슨한 결합
✅ 확장성
✅ 재사용성
✅ 유지보수성
✅ 여러 리스너 가능
```

### vs 다른 방식

```
직접 호출:
  └─ 강한 결합, 확장 어려움

Interface:
  └─ 타입 필요, 1:1 통신

Event Dispatcher:
  └─ 타입 불필요, 1:N 방송
```

# 📊 Blueprint 데이터 타입 완벽 가이드

## 📋 데이터 타입이란?

```
개념: 변수에 저장할 수 있는 값의 종류
역할:
  ├─ 저장 가능한 값 결정
  ├─ 수행 가능한 연산 결정
  └─ 메모리 사용량 결정

시각적 구분:
  └─ 색상으로 구분
      └─ 노드 핀의 색 = 데이터 타입
```

**비유**

```
데이터 타입 = 컨테이너 종류

병 (Float):
  └─ 액체 담기 (소수점 숫자)

상자 (Integer):
  └─ 물건 담기 (정수)

봉투 (String):
  └─ 편지 담기 (문자)
```

## 🔢 1. 기본 타입 (Primitive Types)

### Boolean (부울) - 빨간색

```
색상: 빨간색
값: True 또는 False (2가지만)
표시: 체크박스
메모리: 1비트 (실제로는 1바이트 사용)

용도:
  ✅ 참/거짓 판단
  ✅ 스위치 ON/OFF
  ✅ 조건문

예시:
  ├─ Is Jumping: true/false
  ├─ Has Key: true/false
  └─ Game Over: true/false
```

**주요 사용처**

```
Branch 노드:
  └─ Condition 입력 (Boolean)

비교 연산자 출력:
  ├─ == (같음)
  ├─ != (다름)
  ├─ > (큼)
  └─ < (작음)
  → 모두 Boolean 반환
```

## 🔢 2. 정수 타입 (Integer Types)

### Byte (바이트) - 초록색

```
색상: 초록색 (밝음)
크기: 8비트 = 1바이트
범위: 0 ~ 255 (256개 값)
부호: 없음 (Unsigned)
  └─ 음수 불가 ❌

용도:
  ✅ 작은 양수만 필요할 때
  ✅ 메모리 절약
  ✅ 열거형 내부 값

예시:
  └─ 플레이어 수 (0~4)
```

### Integer (정수) - 초록색

```
색상: 초록색 (중간)
크기: 32비트 = 4바이트
범위: -2,147,483,648 ~ 2,147,483,647
부호: 있음 (Signed)

용도:
  ✅ 일반적인 정수
  ✅ 카운터, 인덱스
  ✅ 가장 많이 사용 ⭐

예시:
  ├─ 체력: 100
  ├─ 점수: 5000
  ├─ 배열 인덱스: 0, 1, 2...
  └─ 적 수: -5 (빚) ~ 999
```

### Integer64 (정수64) - 초록색

```
색상: 초록색 (어두움)
크기: 64비트 = 8바이트
범위: 매우 큰 수
  └─ ±9,223,372,036,854,775,807

용도:
  ✅ 매우 큰 수 필요할 때
  ✅ 타임스탬프
  ✅ 대규모 통계

예시:
  └─ 총 플레이 시간 (밀리초)
```

💡 **선택 가이드**

```
대부분: Integer (32비트) 사용
작은 범위만: Byte
매우 큰 수: Integer64
```

---

## 🔢 3. 실수 타입 (Float Types)

### Float (플로트) - 초록색

```
색상: 초록색 (연한 초록)
크기: 32비트 = 4바이트
값: 소수점 포함 가능
범위: 약 ±3.4 × 10^38

용도:
  ✅ 소수점 필요한 모든 것
  ✅ 위치, 회전, 속도
  ✅ 퍼센트, 배율

예시:
  ├─ 이동 속도: 600.5
  ├─ 체력 비율: 0.75 (75%)
  ├─ 위치: 123.456
  └─ 각도: 45.0
```

**Integer vs Float**

```
Integer:
  ├─ 1, 2, 100, -50
  └─ 소수점 없음

Float:
  ├─ 1.0, 2.5, 100.999, -50.123
  └─ 소수점 가능 ✅
```

## 📝 4. 문자 타입 (String Types)

### String (문자열) - 분홍색

```
색상: 분홍색 (밝음)
내용: 문자의 연속
용도:
  ✅ 일반적인 텍스트
  ✅ 파일 경로
  ✅ 디버그 메시지

예시:
  ├─ "Hello World"
  ├─ "Player Name: John"
  └─ "C:/Games/Save.dat"

특징:
  ✅ 대소문자 구분
  ✅ 공백 허용
  ✅ 연산 가능 (Append)
```

### Name (이름) - 보라색

```
색상: 보라색
내용: 식별자
용도:
  ✅ 오브젝트 식별
  ✅ 룩업 테이블
  ✅ 소켓/본 이름

예시:
  ├─ "Head" (본 이름)
  ├─ "Muzzle" (소켓 이름)
  └─ "Player1" (태그)

특징:
  ❌ 대소문자 구분 안 함
  ❌ 공백 사용 불가
  ✅ 빠른 검색 (최적화)
  ✅ 메모리 효율적
```

### Text (텍스트) - 분홍색

```
색상: 분홍색 (진함)
내용: UI용 텍스트
용도:
  ✅ 위젯 텍스트
  ✅ 사용자에게 보이는 문자
  ✅ 지역화 지원 ⭐

예시:
  ├─ "You Won!"
  ├─ "Press Start"
  └─ "게임 종료" (한글 지원)

특징:
  ✅ 다국어 번역 가능
  ✅ 포맷팅 지원
  ✅ UI 전용
```

**비교 표**

```
| 타입   | 용도              | 대소문자 | 공백 | 지역화 |
|--------|-------------------|----------|------|--------|
| String | 일반 텍스트       | 구분     | 가능 | 불가   |
| Name   | 식별자/태그       | 무시     | 불가 | 불가   |
| Text   | UI 표시           | 구분     | 가능 | 가능   |
```

## 🎨 5. 기하학 타입 (Geometry Types)

### Vector (벡터) - 노란색

```
색상: 노란색
구성: X, Y, Z (3개의 Float)
용도:
  ✅ 3D 위치
  ✅ 방향
  ✅ 속도

예시:
  Vector(100.0, 200.0, 300.0)
    ├─ X: 100.0
    ├─ Y: 200.0
    └─ Z: 300.0

활용:
  ├─ Actor Location
  ├─ Movement Direction
  └─ Velocity
```

### Rotator (회전자) - 주황색

```
색상: 주황색
구성: Pitch, Yaw, Roll (3개의 Float)
용도:
  ✅ 3D 회전

예시:
  Rotator(0.0, 90.0, 0.0)
    ├─ Pitch: 0.0 (위아래)
    ├─ Yaw: 90.0 (좌우)
    └─ Roll: 0.0 (기울기)

활용:
  ├─ Actor Rotation
  ├─ Camera Angle
  └─ Object Orientation
```

### Transform (트랜스폼) - 주황색

```
색상: 주황색 (진함)
구성: Location + Rotation + Scale
  ├─ Location: Vector (위치)
  ├─ Rotation: Rotator (회전)
  └─ Scale: Vector (크기)

용도:
  ✅ 완전한 3D 변환 정보

활용:
  ├─ Get Socket Transform
  ├─ Set Actor Transform
  └─ Spawn Actor Transform
```

**복합 타입 (Composite Types)**

```
Vector, Rotator, Transform:
  └─ 여러 Float로 구성됨
  └─ Split Struct Pin으로 분리 가능

예시:
  Vector 분리
    ├─ X (Float)
    ├─ Y (Float)
    └─ Z (Float)
```

## 🏗️ 6. 고급 타입 (Advanced Types)

### Struct (구조체) - 파란색

```
색상: 파란색
별칭: Structure (C++)
개념: 여러 값의 집합

예시 - Hit Result:
  ├─ Impact Point (Vector)
  ├─ Impact Normal (Vector)
  ├─ Hit Actor (Object)
  ├─ Hit Component (Object)
  └─ Distance (Float)

용도:
  ✅ 관련 데이터 묶기
  ✅ 여러 값을 하나로

장점:
  ✅ 데이터 정리
  ✅ 함수 파라미터 단순화
  ✅ 재사용 가능
```

### Interface (인터페이스) - 청록색

```
색상: 청록색 (녹색+노랑)
개념: 함수 약속

특징:
  ✅ 함수 시그니처만 정의
  ✅ 구현은 각 클래스에서
  ✅ 느슨한 결합

예시:
  BPI_Interact
    ├─ Activate 함수
    └─ DeActivate 함수

사용:
  └─ Interface Message 노드
      └─ 빨간색 노드
```

### Enum (열거형) - 진한 초록색

```
색상: 진한 초록색
개념: 정의된 값들의 목록
내부: 실제로는 Integer

예시 - Movement Mode:
  ├─ Walking (내부: 0)
  ├─ Falling (내부: 1)
  ├─ Flying (내부: 2)
  └─ Swimming (내부: 3)

장점:
  ✅ 의미 있는 이름
  ✅ 오타 방지
  ✅ 코드 가독성

vs Integer:
  ❌ 0 = 걷기? 뛰기?
  ✅ Walking = 명확!
```

### Object Types (오브젝트 타입) - 파란색

```
색상: 파란색 (여러 종류)
종류:
  ├─ Object Reference (오브젝트 참조)
  ├─ Class Reference (클래스 참조)
  ├─ Soft Object Reference (소프트)
  └─ Soft Class Reference (소프트)

계층:
  Object
    └─ Actor
        ├─ Pawn
        │   └─ Character
        ├─ Controller
        │   └─ Player Controller
        └─ Game Mode

용도:
  ✅ 게임 오브젝트 참조
  ✅ Blueprint 간 통신
  ✅ 동적 생성
```

## 💡 핵심 개념 정리

### 기본 vs 복합

```
기본 타입 (Primitive):
  ├─ Boolean
  ├─ Integer
  ├─ Float
  ├─ String
  └─ 단일 값

복합 타입 (Composite):
  ├─ Vector (Float × 3)
  ├─ Rotator (Float × 3)
  ├─ Transform (여러 타입)
  └─ Struct (사용자 정의)
```

### 참조 vs 값

```
값 타입:
  ├─ Integer, Float, Boolean
  └─ 복사됨

참조 타입:
  ├─ Object Reference
  └─ 원본 가리킴
```

## ⚠️ 주의사항

### 1. Float 정밀도

```
❌ Float 정확도 제한
  └─ 0.1 + 0.2 ≠ 0.3
  └─ 근사값

✅ 돈 계산은 Integer 사용
  └─ 센트 단위로 저장
```

### 2. Name vs String

```
❌ Name으로 UI 텍스트
  └─ 대소문자 구분 안 됨

✅ Text 사용
  └─ 정확한 표시
```

### 3. Enum 확장

```
✅ 나중에 값 추가 가능
❌ 순서 변경 주의
  └─ 저장된 데이터 영향
```

### 4. 메모리 효율

```
100개 변수:
  Byte: 100바이트
  Integer: 400바이트
  Integer64: 800바이트

→ 필요한 만큼만 사용
```

## 🎯 목표

Construction Script를 이해하고, 환경에 따라 자동으로 색이 바뀌는 절차적 오브젝트 만들기

---

## 📋 Blueprint의 3가지 탭

### 기본 탭 구조

```
Blueprint를 열면:
  ├─ Viewport (뷰포트)
  │   └─ 컴포넌트 시각 편집
  │
  ├─ Event Graph (이벤트 그래프)
  │   └─ 게임플레이 로직
  │
  └─ Construction Script (구성 스크립트) ⭐
      └─ 초기화 및 설정
```

---

## 🔨 Construction Script란?

### 개념

```
이름: Construction Script (건설 스크립트)
의미: "건설할 때 실행되는 스크립트"

비유: 건물 지을 때 설계도
  └─ 집 짓기 전에 미리 정해놓는 것
```

### 실행 시점

```
✅ 실행되는 경우:
  ├─ Blueprint 인스턴스 생성 시
  ├─ 레벨에 배치할 때
  ├─ Blueprint 컴파일할 때
  ├─ Details 패널에서 값 변경 시
  ├─ Actor 이동/회전/스케일 시
  └─ 에디터에서 속성 변경 시

❌ 실행 안 되는 경우:
  └─ 게임 플레이 중 (Play 후) ⚠️
```

**중요!**

```
게임 시작 전:
  ✅ Construction Script 실행

게임 시작 후 (Play):
  ❌ Construction Script 실행 안 됨
  ✅ Event Graph만 실행
```

### vs Event Graph

```
Construction Script:
  ├─ 언제: 배치/편집 시
  ├─ 용도: 초기 설정
  └─ 게임 중: 실행 안 됨

Event Graph:
  ├─ 언제: 게임 플레이 중
  ├─ 용도: 게임 로직
  └─ 게임 중: 실행됨
```

## 🎨 실전 예제: 절차적 색 변경

### 목표

```
제트 연료 색상을 위치에 따라 자동 변경:
  ├─ 허공: 노란색
  ├─ 플랫폼 위: 파란색
  └─ 압력판 위: 빨간색

```

### 절차적 (Procedural)이란?

```
개념: 조건에 따라 자동으로 변경
비유: 카멜레온

수동 방식:
  └─ 하나하나 손으로 색 변경 ❌

절차적 방식:
  └─ 위치만 바꾸면 자동 변경 ✅
```

## 🔍 1단계: Line Trace로 아래 확인

### Line Trace by Channel

```
용도: 레이저처럼 직선으로 쏴서 부딪힌 것 감지
비유: 레이저 포인터

입력:
  ├─ Start: 시작점
  ├─ End: 끝점
  ├─ Trace Channel: 감지 채널
  └─ Actors to Ignore: 무시할 액터

출력:
  ├─ Return Value: 맞았는지 (Boolean)
  └─ Out Hit: 맞은 정보 (Hit Result)
```

### 노드 구조

```
Construction Script
  ↓
Line Trace by Channel
  ├─ Start: Get Actor Location
  │   └─ 현재 액터 위치
  │
  └─ End: Get Actor Location + (0, 0, -200)
      └─ 현재 위치에서 200 아래
```

**Start 계산**

```
Get Actor Location (Self)
  └─ 제트 연료의 현재 위치
```

**End 계산**

```
Get Actor Location + Vector(0, 0, -200)
  └─ 현재 위치에서 Z축으로 200 내려간 곳

Vector(0, 0, -200):
  ├─ X: 0 (좌우 이동 없음)
  ├─ Y: 0 (앞뒤 이동 없음)
  └─ Z: -200 (아래로 200)
```

💡 **+ 연산자 (벡터)**

```
Vector + Vector = 새 Vector

예시:
  (100, 200, 300) + (0, 0, -200)
  = (100, 200, 100)
```

### 추가 설정

```
Ignore Self: 체크 ✅
  └─ 자기 자신은 무시

Trace Channel: Visibility
  └─ 보이는 오브젝트만 감지

Draw Debug Type: For Duration (5초)
  └─ 디버그 선 표시
```

**Draw Debug Type**

```
None: 안 보임
For One Frame: 1프레임만
For Duration: 지정 시간 동안 ✅

용도: 디버깅 (문제 해결)
```

## 🎨 2단계: 기본 색 설정 (노란색)

### Set Material 노드

```
용도: 메시의 재질 변경
타겟: Fuel Mesh (Static Mesh Component)

입력:
  ├─ Target: Fuel Mesh
  ├─ Element Index: 0
  │   └─ 첫 번째 재질 슬롯
  └─ Material: MI_JetFuel
```

![image.png](https://res.cloudinary.com/du1acdhxq/image/upload/v1788380679/notion-blog/_/_/_5_/3/image_22.png)

**Element Index란?**

```
메시는 여러 재질 슬롯 가능:
  ├─ 0: 첫 번째 재질
  ├─ 1: 두 번째 재질
  └─ 2: 세 번째 재질

제트 연료:
  └─ 0번만 변경 (몸통 색)
```

### Branch로 조건 분기

```
Line Trace by Channel
  └─ Return Value (Boolean)
      ↓
Branch
  ├─ True: 뭔가 맞음
  │   └─ 파란색으로
  │
  └─ False: 허공
      └─ 노란색으로
```

**False 경로 (허공)**

```
Set Material
  ├─ Target: Fuel Mesh
  ├─ Element Index: 0
  └─ Material: MI_JetFuel (노란색)
```

## 🔷 3단계: 플랫폼 위 색 (파란색)

### Material Instance 복제

```
MI_JetFuel 복제
  ↓
이름: MI_JetFuel_AbovePlatform
  ↓
Color Override: 파란색으로 변경
```

**Material Instance란?**

```
개념: 재질의 변형 버전
비유: 같은 옷의 다른 색

장점:
  ✅ 원본 손상 없음
  ✅ 파라미터만 변경
  ✅ 가볍고 빠름
```

### True 경로 설정

```
Branch → True
  ↓
Set Material
  ├─ Target: Fuel Mesh
  ├─ Element Index: 0
  └─ Material: MI_JetFuel_AbovePlatform (파란색)
```

## 🔴 4단계: 압력판 위 색 (빨간색)

### Hit Result 분석

```
Line Trace → Out Hit
  └─ Hit Result Struct

내용:
  ├─ Hit Actor: 맞은 액터
  ├─ Hit Component: 맞은 컴포넌트
  ├─ Impact Point: 충돌 지점
  └─ 기타 정보들
```

### Break Hit Result

```
용도: Hit Result의 내부 값 꺼내기
비유: 선물 상자 뜯기

Out Hit → Break Hit Result
  ↓
개별 값 추출:
  ├─ Hit Actor ⭐
  ├─ Impact Point
  ├─ Distance
  └─ 등등...
```

### Cast to BP_PressurePlate

```
Break Hit Result → Hit Actor
  ↓
Cast to BP_PressurePlate
  ├─ 성공: 압력판이 맞음 ✅
  └─ 실패: 압력판 아님
```

**Cast란?**

```
개념: "이게 압력판 맞아?" 확인
비유: 신분증 확인

성공:
  └─ "네, 압력판입니다"
      └─ As BP Pressure Plate 출력

실패:
  └─ "아니요, 다른 겁니다"
      └─ Cast Failed 실행
```

### 최종 구조

```
Line Trace → Return Value
  ↓
Branch
  ├─ False (허공)
  │   └─ Set Material: 노란색
  │
  └─ True (뭔가 맞음)
      ↓
      Cast to BP_PressurePlate
        ├─ 성공 (압력판)
        │   └─ Set Material: 빨간색 ⭐
        │
        └─ 실패 (일반 플랫폼)
            └─ Set Material: 파란색
```

### 빨간색 Material 추가

```
MI_JetFuel 복제
  ↓
이름: MI_JetFuel_AbovePlate
  ↓
Color Override: 빨간색
```

## 🔍 Cast의 2가지 역할

### 1. 타입 확인

```
"너 압력판 맞아?"
  ├─ 맞으면: 성공
  └─ 아니면: 실패
```

### 2. 기능 접근

```
성공하면:
  └─ 압력판 전용 기능 사용 가능

예시:
  Cast to BP_PressurePlate
    └─ Does Un Press 변수 접근 가능
```

## 💡 왜 "Cast"라는 이름?

```
프로그래밍 용어:
  Type Casting = 타입 변환

하지만 Blueprint에서:
  ❌ 실제로 바꾸지 않음
  ✅ "이 타입 맞는지 확인"
```

---

## 🔑 핵심 정리

```
Cast to BP_PressurePlate:

❌ "압력판으로 바꿔!"
✅ "압력판 맞아? 맞으면 압력판 기능 쓸게"

성공 = 원래부터 압력판이었음
실패 = 처음부터 압력판 아니었음
```

---

## 📝 정확한 번역

```
Cast (영어) = 주조하다, 던지다
  └─ 프로그래밍: "타입 확인"

올바른 이해:
  └─ "타입 체크 + 접근 권한"
```

---

## 핵심

```
Cast 성공:
  └─ 맞은 게 그 타입이 맞을 때

Cast 실패:
  └─ 맞은 게 다른 타입일 때
```

## 🎯 완성된 시스템

### 작동 방식

```
제트 연료 배치/이동 시:
  ↓
Construction Script 실행
  ↓

  ↓
맞았나?
  ├─ No → 노란색 (허공)
```

```
제트 연료를 이동하면:
  1. Construction Script 자동 실행
  2. 현재 위치에서 Line Trace
  3. 맞은 오브젝트 확인
  4. 자동으로 색 변경 ✅

→ 수동 변경 불필요!
```

## 📊 핵심 노드 기능

### Line Trace by Channel

```
용도: 직선 레이캐스트
입력:
  ├─ Start: 시작점 (Vector)
  ├─ End: 끝점 (Vector)
  ├─ Trace Channel: 감지 채널
  └─ Actors to Ignore: 무시 목록

출력:
  ├─ Return Value: 맞았는지 (Boolean)
  └─ Out Hit: 충돌 정보 (Hit Result)

옵션:
  ├─ Trace Complex: 복잡한 충돌 사용
  ├─ Ignore Self: 자신 무시
  └─ Draw Debug Type: 디버그 표시
```

### Break Hit Result

```
용도: Hit Result 구조체 분해
입력: Hit Result
출력:
  ├─ Blocking Hit: 차단했는지
  ├─ Hit Actor: 맞은 액터 ⭐
  ├─ Hit Component: 맞은 컴포넌트
  ├─ Impact Point: 충돌 지점
  ├─ Impact Normal: 충돌 면의 방향
  ├─ Distance: 거리
  └─ 기타 정보들
```

### Set Material

```
용도: 메시 재질 변경
타겟: Primitive Component
입력:
  ├─ Element Index: 재질 슬롯 번호
  └─ Material: 새 재질
```

### Cast To

```
용도: 타입 확인 및 변환
형식: Cast to [클래스명]
출력:
  ├─ 성공 핀
  ├─ 실패 핀 (Cast Failed)
  └─ As [클래스]: 변환된 객체
```

## 🎓 Construction Script 활용

### 적합한 용도

```
✅ 초기 설정:
  ├─ 재질 변경
  ├─ 메시 크기 조정
  ├─ 컴포넌트 배치
  └─ 절차적 생성

✅ 환경 감지:
  ├─ 주변 확인
  ├─ 표면 감지
  └─ 다른 오브젝트 찾기

✅ 조건부 설정:
  ├─ 위치에 따라
  ├─ 주변 오브젝트에 따라
  └─ 파라미터에 따라

```

### 부적합한 용도

```
❌ 게임플레이 로직:
  └─ Play 중 실행 안 됨

❌ 반복 실행:
  └─ Tick처럼 계속 실행 불가

❌ 플레이어 입력:
  └─ 게임 중 작동 안 함
```

## ⚠️ 주의사항

### 1. 게임 중 실행 안 됨

```
❌ Play 중 Actor 이동해도
  → Construction Script 실행 안 됨

✅ 에디터에서 Actor 이동
  → Construction Script 실행 ✅

해결:
  └─ 게임 중 변경은 Event Graph 사용
```

### 2. 무한 루프 주의

```
❌ Construction Script에서
  → 자신의 위치 변경
  → 다시 Construction Script 실행
  → 무한 루프 ⚠️

✅ 읽기만 하고 변경 조심
```

### 3. 성능 고려

```
❌ 너무 복잡한 계산
  → 에디터 느려짐

✅ 간단한 설정만
  └─ 복잡한 건 Event Graph로
```

### 4. Material Instance 필요

```
❌ Material 직접 수정
  → 모든 곳에 영향

✅ Material Instance 생성
  └─ 개별 파라미터만 변경
```

```
  ✅ 초기 설정

  ✅ 반복 작업 제거
```
