# { 기본적인 통신 흐름과 역할 }

```jsx
클라이언트(Client):

		보통 우리가 사용하는 웹 브라우저입니다.

		클라이언트는 서버에 데이터를 요청하고, 서버는 이를 처리해서 클라이언트로 결과를 보냅니다.

웹 서버(Web Server):

		클라이언트와 가장 먼저 통신하는 서버입니다.

		웹 서버는 보통 Nginx, Apache 같은 소프트웨어를 사용해,

		클라이언트의 요청을 받아 WAS로 전달하는 역할을 합니다.

애플리케이션 서버(WAS, Web Application Server):

		웹 서버가 전달한 요청을 처리합니다. Java 기반의 Tomcat 같은 WAS는 프로그램 로직을 실행하여 필요한 데이터를 생성하고,

		이 데이터를 웹 서버를 통해 클라이언트로 반환합니다.
```

# { 클라이언트와 서버 간의 보안 통신 }

```jsx
클라이언트가 웹 서버와 통신할 때 SSL 인증서를 통해 안전하게 데이터를 주고받는 방식이 사용됩니다.
```

## SSL의 역할

```jsx
SSL(Secure Sockets Layer):

		서버와 클라이언트 간 통신을 암호화하여 중간에 누가 훔쳐봐도 데이터를 알아볼 수 없게 만듭니다.

HTTPS(HTTP + SSL):

		일반적인 HTTP 대신 HTTPS를 사용해 웹사이트가 신뢰할 수 있다는 것을 클라이언트에게 알려줍니다.
```

### 클라이언트와 웹 서버 간 통신 과정

```jsx
1. HTTPS 요청:

		클라이언트가 https://example.com과 같은 HTTPS URL로 접속을 시도합니다.

2. SSL 인증서 확인:

		웹 서버는 미리 설정해 둔 SSL 인증서를 클라이언트에게 제공합니다.

3. 암호화 통신:

		클라이언트가 인증서를 확인하고 신뢰할 수 있으면, 웹 서버와 암호화된 통신 채널이 형성됩니다.

		이후 데이터는 이 채널을 통해 안전하게 전송됩니다.
```

# { 웹 서버와 WAS 간의 SSL 프록시 설정 }

```jsx
웹 서버와 WAS가 서로 통신할 때도 SSL을 적용할 수 있습니다.

이때 웹 서버는 클라이언트 요청을 받아 적절히 처리한 뒤 WAS로 전달하는 프록시(Proxy) 역할을 합니다.
```

## 웹 서버와 WAS 간의 SSL 통신이 필요한 이유

```jsx
웹 서버와 WAS가 서로 다른 네트워크에 있거나,

외부 공격을 대비해 추가적인 보안이 필요한 경우에는 이 둘 간의 통신에도 SSL을 설정해 데이터를 암호화합니다.
```

## 프록시와 SSL 설정 예시

```jsx
웹 서버에 프록시 설정:

		웹 서버는 클라이언트 요청을 WAS로 프록시 처리합니다.

		이때 HTTP 대신 HTTPS를 사용하여 보안을 강화할 수 있습니다.

WAS에 SSL 설정:

		WAS도 웹 서버와의 SSL 통신을 위해 SSL 인증서를 설정해두어야 합니다.
```

```jsx
예를 들어, Nginx가 웹 서버이고 Tomcat이 WAS인 경우 Nginx에서 받은

HTTPS 요청을 다시 Tomcat에 HTTPS로 프록시할 수 있습니다.

( 아래는 아파치 예시 )
```

```jsx
<VirtualHost *:443>
    ServerName example.com

    # SSL 인증서와 키 파일 경로 설정
    SSLEngine on
    SSLCertificateFile /path/to/certificate.crt
    SSLCertificateKeyFile /path/to/private.key

    # 클라이언트 요청을 WAS 서버로 프록시
    ProxyPreserveHost On
    ProxyPass / https://was_server:8443/
    ProxyPassReverse / https://was_server:8443/

    # WAS와의 SSL 통신 설정
    SSLProxyEngine on
    SSLProxyVerify require
    SSLProxyVerifyDepth 2
    SSLProxyCACertificateFile /path/to/ca_certificate.pem
    SSLProxyMachineCertificateFile /path/to/client_certificate.crt
    SSLProxyMachineCertificateKeyFile /path/to/client_private.key
</VirtualHost>

```

# { 버츄얼 호스트 }

```jsx
<VirtualHost *:443>는 웹 서버가 특정 도메인(example.com)에서 오는 요청을 어떻게 처리할지 설정하는 부분입니다.

웹 서버(Apache 서버 등)에서 버츄얼 호스트는 하나의 서버에서 여러 사이트나 도메인에 대한 요청을 각각 다르게 처리하기 위한 개념입니다.

쉽게 설명하자면, 한 집에서 여러 우편함을 사용하는 것과 비슷합니다.

집 주소는 같지만, 각 우편함이 다른 이름이나 번호를 갖고 있어서,

우편이 도착하면 각 우편함으로 구분해 넣는 역할을 하죠. 이와 비슷하게, 서버는 하나이지만 여러 도메인을 운영하고,

각 도메인마다 다르게 처리할 수 있도록 설정하는 것이 버츄얼 호스트입니다.
```

## 버츄얼 호스트 설정 요소

```jsx
위의 예제에서 VirtualHost 블록에는 HTTPS(443 포트)를 사용하는 도메인(example.com)의 설정을 적어두었습니다. 주요 부분을 쉽게 설명하겠습니다.

ServerName:

		요청을 받을 도메인 이름입니다. 여기서는 example.com 도메인에 대한 요청을 처리합니다.

SSL 설정:

		SSLEngine:

				SSL을 활성화하는 설정입니다.

		SSLCertificateFile과 SSLCertificateKeyFile:

				SSL 인증서와 개인 키 파일의 경로입니다. 이 파일들로 클라이언트와의 암호화 통신을 보장합니다.

Proxy 설정:

		ProxyPass와 ProxyPassReverse:

				클라이언트의 요청을 내부에 있는 다른 서버(보통 WAS 서버)로 넘겨줍니다.

				이를 프록시라고 부르며, 클라이언트는 WAS 서버의 위치나 포트 정보는 모르고 오직 example.com에만 요청을 보냅니다.

		SSLProxyEngine:

				프록시 서버와 WAS 서버 간의 통신도 암호화(SSL)하도록 설정합니다.


이렇게 설정해두면 example.com에 HTTPS로 접속하는 사용자는 Apache 서버에 접속하지만,

Apache 서버는 그 요청을 내부의 다른 서버로 안전하게 넘겨 처리하게 됩니다.
```

# { 최종 통신 과정 }

```jsx
1. 클라이언트:

		클라이언트가 HTTPS로 웹 서버에 연결해 데이터를 요청합니다.

2. 웹 서버:

		클라이언트 요청을 받아 자체 처리하거나, WAS에 프록시하여 요청을 전달합니다.

3. WAS:

		웹 서버에서 전달한 요청을 받아 데이터를 처리하고, 결과를 웹 서버에 전달합니다.

4. 웹 서버:

		WAS로부터 받은 결과를 클라이언트로 보내 최종적으로 화면에 표시됩니다.
```

# { SSL과 프록시의 역할과 동작 방식 }

## SSL (Secure Sockets Layer)

```jsx
SSL은 인터넷을 통해 데이터를 암호화하여 보안을 강화하는 프로토콜입니다.

최신 버전의 SSL은 TLS(Transport Layer Security)로 불리며, HTTPS 통신에서 주로 사용됩니다.
```

```jsx
SSL 인증서:

		SSL 인증서에는 서버의 공개키와 도메인 정보, 발급기관 정보 등이 포함되어 있습니다.

		인증서를 통해 서버의 신원을 확인하고, 클라이언트와 서버 간에 안전한 연결을 설정합니다.

핸드셰이크 (Handshake): 클라이언트와 서버가 연결을 시도하면 SSL 핸드셰이크가 시작됩니다. 과정은 다음과 같습니다:

		1단계: 클라이언트가 서버에 연결 요청을 보내며 SSL 인증서 제공을 요청합니다.

		2단계: 서버는 자신의 SSL 인증서를 클라이언트에 전송합니다.

		3단계: 클라이언트는 서버 인증서를 확인하고, 일치한다면 대칭 키를 생성해 서버에 전달합니다.

		4단계: 서버는 클라이언트가 보낸 대칭 키로 암호화된 데이터를 주고받으며 안전한 통신을 이어갑니다.
```

## SSL이 필요한 이유

```jsx
데이터 보호: 민감한 정보(예: 로그인 정보, 금융 거래 등)가 유출되는 것을 방지합니다.

신뢰성 강화: 인증서를 통해 클라이언트는 서버의 신뢰성을 확인할 수 있습니다.

데이터 무결성: 데이터가 전송 중에 조작되거나 손상되지 않도록 보장합니다.
```

# { 프록시 (Proxy) }

```jsx
프록시는 중간 서버 역할을 하며 클라이언트의 요청을 받아 이를 목적지 서버(WAS 등)로 전달하고,

응답을 받아 다시 클라이언트로 전달합니다.

주로 웹 서버(Nginx, Apache 등)가 이 역할을 하며, SSL 프록시나 리버스 프록시 등으로 구분됩니다.
```

## 프록시의 역할과 종류

```jsx
리버스 프록시 (Reverse Proxy):

		외부에서 서버로의 요청을 받는 프록시로, 웹 서버 앞단에서 클라이언트 요청을 받아 WAS 서버로 전달합니다.

		예: Nginx, Apache

SSL 프록시:

		SSL을 사용하는 리버스 프록시로, 클라이언트와 프록시 서버 간, 프록시 서버와 WAS 간 각각의 SSL 연결을 설정합니다.

부하 분산 (Load Balancing):

		여러 WAS 서버가 있을 때 프록시 서버가 요청을 나눠서 전달해 서버의 부하를 줄이고 성능을 최적화합니다.

캐싱 (Caching):

		자주 요청되는 데이터를 프록시 서버가 캐싱하여 클라이언트에게 더 빠르게 제공합니다.
```

## 프록시의 이점

```jsx
보안 강화: 프록시 서버가 클라이언트와 서버 사이에 위치하여 직접 통신을 차단하고 SSL 인증서를 관리하므로 보안이 강화됩니다.

WAS 보호: 실제 서버의 IP가 외부에 노출되지 않으며, 클라이언트는 프록시 서버만 접근할 수 있습니다.

성능 최적화: 캐싱, 압축 등을 통해 서버 자원을 절약하고 응답 시간을 줄일 수 있습니다.
```

# { SSL 프록시 서버 통신 과정 예시 }

```jsx
클라이언트와 WAS 간에 SSL을 통해 안전하게 데이터를 주고받는 통신 과정은 다음과 같습니다.
```

```jsx
1. 클라이언트 → 프록시 서버:

		클라이언트는 프록시 서버(예: Apache, Nginx)와 HTTPS로 연결하여 SSL 핸드셰이크를 수행합니다.

		프록시 서버는 SSL 인증서를 이용해 클라이언트의 요청을 받습니다.

2. 프록시 서버 → WAS:

		프록시 서버는 클라이언트의 요청을 분석하고, 내부 WAS 서버로 이를 HTTPS를 통해 전달합니다.

		이때 프록시 서버와 WAS 간에도 SSL 인증서가 필요하며, 보안을 위해 이 역시 암호화됩니다.

3. WAS 응답 → 프록시 서버 → 클라이언트:

		WAS는 요청에 대한 응답을 프록시 서버에 보내고, 프록시 서버는 다시 클라이언트로 전달합니다.

		모든 데이터는 암호화되어 통신되므로 데이터 보호가 보장됩니다.
```
