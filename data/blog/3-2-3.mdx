```jsx

먼저 두 가지 라이브러리를 설치해야 합니다:

Socket.IO: 실시간 통신을 위한 라이브러리

Socket.IO-Redis Adapter: 여러 서버 간에 이벤트를 방송(broadcast)할 수 있게 해줌

redis: Redis 클라이언트 라이브러리Redis ( 클라이언트 라이브러리란, Redis라는 데이터베이스와 통신할 수 있게 해주는 도구를 의미 )

* "이벤트를 방송(broadcast)"한다고 말하는 것은,

	한 사용자가 서버에 보낸 메시지를 여러 사용자에게 동시에 전달할 수 있다는 의미입니다.

	예를 들어 채팅 애플리케이션에서, 한 사용자가 메시지를 보내면 그 메시지를 다른 모든 사용자에게 보여줘야 합니다.

	이때 Socket.IO-Redis 어댑터는 어느 서버에 있는 사용자든지 상관없이, 모든 사용자에게 그 메시지를 보낼 수 있도록 해줍니다.
```

## 소켓 서버 설정

```jsx
이 코드를 통해 여러 서버에서 연결된 클라이언트가 서로 통신할 수 있도록 구성됩니다.

Redis는 이를 돕기 위한 역할을 하며, 메시지를 다른 서버로 전달해 주는 역할을 합니다.

Server: httpServer와 연결된 Socket.IO 서버

createClient: Redis 서버와 연결할 클라이언트

adapter: Redis 어댑터를 적용해 소켓 간 이벤트를 여러 서버에서 브로드캐스트 가능하게 설정
```

```jsx
// Socket.IO 서버를 생성하는 비동기 함수
private async createSocketIO(httpServer: http.Server): Promise<Server> {   // 이 함수는 Promise를 반환합니다. Promise는 비동기 작업이 완료되었을 때 결과를 반환해주는 객체입니다. 여기서 이 Promise는 Server라는 타입을 반환합니다. 즉, 이 함수가 완료되면 Socket.IO 서버가 반환된다는 뜻입니다.

    // 1. Socket.IO 서버 생성
    // 기존 HTTP 서버를 사용하여 Socket.IO 서버를 만듭니다.
    // CORS 설정을 통해 특정 클라이언트 URL에서만 연결을 허용하고,
    // 허용할 HTTP 메서드를 설정할 수 있습니다.
    const io: Server = new Server(httpServer, {
        cors: {
            origin: config.CLIENT_URL,  // 허용할 클라이언트의 URL을 설정 (ex: 'http://localhost:3000')
            methods: ['GET', 'POST', 'PUT', 'DELETE', 'OPTIONS']  // 허용할 HTTP 메소드 설정
        }
    });

    // 2. Redis 클라이언트 생성
    // Socket.IO 서버 간에 데이터를 공유하려면 Redis 클라이언트를 사용해야 합니다.
    // Redis 클라이언트를 생성하는데, 이때 Redis 서버의 URL을 설정합니다.
    const publicClient = createClient({url: config.REDIS_HOST});  // Redis 서버와 통신하는 클라이언트

    // 3. Redis 클라이언트 복제
    // Redis는 "퍼블리셔"(publish)와 "구독자"(subscribe) 두 가지 역할을 나눠서 사용합니다.
    // 퍼블리셔는 메시지를 보내고, 구독자는 메시지를 받습니다.
    // publicClient를 복제하여 구독자 역할의 Redis 클라이언트를 생성합니다.
    const subClient = publicClient.duplicate();  // 구독 전용 클라이언트 생성

    // 4. Redis 클라이언트 연결
    // publicClient와 subClient 두 클라이언트를 모두 Redis 서버에 연결합니다.
    // `Promise.all`은 두 클라이언트의 연결이 모두 완료될 때까지 기다리게 해줍니다.
    await Promise.all([publicClient.connect(), subClient.connect()]);  // Redis 서버에 연결

    // 5. Redis 어댑터 설정
    // Socket.IO는 여러 서버 간의 실시간 통신을 지원하기 위해 Redis 어댑터를 사용합니다.
    // 생성한 두 개의 Redis 클라이언트를 Socket.IO 어댑터에 연결하여 서버 간 통신이 가능하게 만듭니다.
    io.adapter(createAdapter(publicClient, subClient));  // Redis 어댑터를 Socket.IO에 연결

    // 6. 완성된 Socket.IO 서버 반환
    // 설정이 끝난 Socket.IO 서버를 반환합니다.
    return io;
}

```

## **서버 시작 시 소켓 통합**

```jsx
startServer 함수는 애플리케이션(Express)을 기반으로 HTTP 서버와 Socket.IO 서버를 설정하고 시작하는 함수입니다.

먼저, http.Server 객체를 생성하여 HTTP 서버를 만들고,

그 서버를 바탕으로 Socket.IO 서버를 설정합니다.

서버가 모두 준비되면, HTTP 서버를 시작하고 Socket.IO 연결을 설정합니다.
```

```jsx
private async startServer(app: Application): Promise<void> {
    try {
        const httpServer: http.Server = new http.Server(app);
        // 1. HTTP 서버를 생성합니다. 여기서 'app'은 Express 애플리케이션입니다.
        // 이 서버는 웹 요청(HTTP 요청)을 처리하게 됩니다.

        const socketIO: Server = await this.createSocketIO(httpServer);
        // 2. 앞서 정의한 'createSocketIO' 함수를 호출해 HTTP 서버를 기반으로
        // Socket.IO 서버를 생성합니다. 이 과정에서 Redis와의 연결도 설정됩니다.
        // 비동기 작업이므로 'await'로 기다립니다.

        this.startHttpServer(httpServer);
        // 3. HTTP 서버를 시작합니다. 이 함수는 서버가 요청을 받을 준비가 되었는지
        // 확인한 후, 실제로 서버가 동작하게 만듭니다.

        this.socketIOConnections(socketIO);
        // 4. Socket.IO 서버와 클라이언트 간의 연결을 처리합니다.
        // 이 과정에서 이벤트 리스너 등을 설정해 실시간 통신이 가능하게 만듭니다.

    } catch (error) {
        console.log(error);
        // 5. 서버 시작 과정에서 발생할 수 있는 오류를 콘솔에 출력합니다.
        // 예외 처리 블록이므로 문제가 생겨도 서버가 중단되지 않고 로그로 남기게 됩니다.
    }
}

```

```jsx
export default (app: Application) => {
```

### 각 부분 설명

```jsx
import { Application } from "express";
```

## 1. 에러 인터페이스 정의

```jsx
먼저, 에러 핸들러에서 사용할 인터페이스를 정의합니다.

인터페이스는 TypeScript에서 객체의 형태를 정의하는 역할을 합니다.
```

```jsx
export interface IErrorResponse {
    message: string;  // 에러 메시지
    statusCode: number;  // HTTP 상태 코드
    status: string;  // 에러 상태

// 기본 에러 구조 인터페이스

    status: string;  // 에러 상태
}
```


## 2. 커스텀 에러 클래스

```jsx
다음으로, 우리가 만들 에러 핸들러의 기본 클래스를 정의합니다. 이 클래스는 모든 커스텀 에러의 부모 역할을 합니다.
```

```jsx
// 커스텀 에러 클래스
export abstract class CustomeError extends Error {
    abstract statusCode: number;  // 상태 코드 (하위 클래스에서 정의됨)
    abstract status: string;  // 상태 메시지 (하위 클래스에서 정의됨)

    constructor(message: string) {
        super(message);  // 부모 클래스인 Error의 생성자를 호출
    }

    // 에러 객체의 내용을 JSON 형태로 반환
    serializeErrors(): IError {
        return {
            message: this.message,  // 에러 메시지
            status: this.status,  // 에러 상태
            statusCode: this.statusCode  // HTTP 상태 코드
        };
    }
}

```

```jsx
CustomeError 클래스는 Error 클래스를 상속합니다.

이 클래스는 statusCode와 status라는 추상 필드를 가지고 있으며, 각각의 하위 클래스에서 반드시 정의해야 합니다.

serializeErrors() 함수는 에러 객체의 정보를 JSON 형식으로 반환하는 역할을 합니다.

* 추상 클래스는 직접 객체를 만들 수 없는 클래스입니다. 대신,

	다른 클래스들이 이 클래스를 상속받아 필요한 내용을 채워넣는 방식으로 사용됩니다.

	즉, 추상 클래스는 기본 구조나 공통 기능을 정의하고, 세부 구현은 하위 클래스에서 담당합니다.

	위 코드에서 CustomeError는 에러 처리의 기본 구조를 정의하지만, 실제 에러 메시지나 상태 코드는 하위 클래스가 결정하게 됩니다.
```

## 3. 다양한 커스텀 에러 클래스

```jsx

```

```jsx
// 요청 유효성 검사 실패 에러

        super(message);  // 부모 클래스 생성자 호출

    }

    status = 'error';  // 에러 상태
```

```jsx
각 클래스는 CustomeError를 상속받아 statusCode와 status를 설정합니다.

예를 들어, BadRequestError는 HTTP 400 상태 코드를 반환하며, 사용자가 잘못된 요청을 했을 때 사용됩니다.
```

```jsx
import HTTP_STATUS from "http-status-codes"; // HTTP 상태 코드를 쉽게 사용할 수 있게 해주는 라이브러리

// IErrorResponse: 에러 응답에 사용될 인터페이스로, 에러 메시지, 상태 코드, 상태를 정의하고
// 'serializeErrors' 메소드를 포함함. 이 메소드는 에러 객체를 반환함.
export interface IErrorResponse {
    message: string; // 에러 메시지 (예: "요청이 잘못되었습니다.")
    statusCode: number; // HTTP 상태 코드 (예: 400, 404 등)
    status: string; // 에러 상태 (예: "error" 또는 "fail")
    serializeErrors(): IErrorResponse; // 에러를 직렬화(serialize)하는 함수
}

// IError: 좀 더 단순한 에러 구조를 정의하는 인터페이스
export interface IError {
    message: string; // 에러 메시지
    statusCode: number; // HTTP 상태 코드
    status: string; // 에러 상태
}

// CustomError: 모든 사용자 정의 에러 클래스들이 상속받을 추상 클래스(abstract class).
// Error 클래스를 확장함으로써 기본적인 에러 처리를 하도록 함.
export abstract class CustomError extends Error {
    abstract statusCode: number; // HTTP 상태 코드 (각 에러 클래스에서 정의됨)
    abstract status: string; // 에러 상태 (각 에러 클래스에서 정의됨)

    // 부모 클래스의 생성자(constructor)를 호출하며, 에러 메시지를 받아옴.
    constructor(message: string) {
        super(message);
    }

    // 'serializeErrors' 메소드: 에러 정보를 직렬화해서 반환하는 메소드로, 에러 메시지와 상태 코드를 반환함.
    serializeErrors(): IError {
        return {
            message: this.message, // 에러 발생 시 전달된 메시지
            status: this.status, // 에러의 상태 (예: "error")
            statusCode: this.statusCode // 에러의 HTTP 상태 코드
        };
    }
}

// JoiRequestValidationError: Joi 유효성 검사 실패 시 발생하는 에러를 처리하는 클래스.
// 상태 코드는 400(Bad Request)로 설정됨.
export class JoiRequestValidationError extends CustomError {
    statusCode = HTTP_STATUS.BAD_REQUEST; // HTTP 상태 코드 400
    status = 'error'; // 에러 상태를 "error"로 설정

    // 부모 클래스인 CustomError의 생성자를 호출하고, 에러 메시지를 전달함.
    constructor(message: string) {
        super(message);
    }
}

// BadRequestError: 잘못된 요청이 들어왔을 때 발생하는 에러 클래스.
// 상태 코드는 400(Bad Request)로 설정됨.
export class BadRequestError extends CustomError {
    statusCode = HTTP_STATUS.BAD_REQUEST; // HTTP 상태 코드 400
    status = 'error'; // 에러 상태를 "error"로 설정

    // 부모 클래스의 생성자를 호출하고, 에러 메시지를 전달함.
    constructor(message: string) {
        super(message);
    }
}

// NotFoundError: 요청한 리소스가 존재하지 않을 때 발생하는 에러 클래스.
// 상태 코드는 404(Not Found)로 설정됨.
export class NotFoundError extends CustomError {
    statusCode = HTTP_STATUS.NOT_FOUND; // HTTP 상태 코드 404
    status = 'error'; // 에러 상태를 "error"로 설정

    constructor(message: string) {
        super(message);
    }
}

// NotAuthorizedError: 사용자가 인증되지 않았거나 권한이 없을 때 발생하는 에러 클래스.
// 상태 코드는 401(Unauthorized)로 설정됨.
export class NotAuthorizedError extends CustomError {
    statusCode = HTTP_STATUS.UNAUTHORIZED; // HTTP 상태 코드 401
    status = 'error'; // 에러 상태를 "error"로 설정

    constructor(message: string) {
        super(message);
    }
}

// FileTooLargeError: 파일 업로드 크기가 너무 클 때 발생하는 에러 클래스.
// 상태 코드는 413(Request Too Long)로 설정됨.
export class FileTooLargeError extends CustomError {
    statusCode = HTTP_STATUS.REQUEST_TOO_LONG; // HTTP 상태 코드 413
    status = 'error'; // 에러 상태를 "error"로 설정

    constructor(message: string) {
        super(message);
    }
}

// ServerError: 서버에서 내부적으로 문제가 발생했을 때 사용하는 에러 클래스.
// 상태 코드는 503(Service Unavailable)로 설정됨.
export class ServerError extends CustomError {
    statusCode = HTTP_STATUS.SERVICE_UNAVAILABLE; // HTTP 상태 코드 503
    status = 'error'; // 에러 상태를 "error"로 설정

    constructor(message: string) {
        super(message);
    }
}
```

## 4. 글로벌 에러 핸들러 설정

![image.png](https://res.cloudinary.com/du1acdhxq/image/upload/v1788381337/notion-blog/_/React_Node_/_3_-_2_-/image_5.png)

```jsx
이제 글로벌 에러 핸들러를 설정합니다.

이 핸들러는 모든 요청의 에러를 처리하며, 에러의 종류에 따라 클라이언트에게 적절한 응답을 반환합니다.
```

```jsx
// 글로벌 에러 핸들러 설정 함수
private globalErrorHandler(app: Application): void {
    // 1. 존재하지 않는 URL로 요청이 들어올 때 404 에러를 반환
    app.all('*', (req: Request, res: Response) => {
        // 요청한 URL이 없을 경우, 404 상태 코드와 함께 에러 메시지를 반환
        res.status(HTTP_STATUS.NOT_FOUND).json({message: `${req.originalUrl} not found`});
    });

    // 2. 커스텀 에러를 처리하는 미들웨어 (에러 처리 전용 함수)
    app.use((error: IErrorResponse, _req: Request, res: Response, next: NextFunction) => {
        console.log(error);  // 에러가 발생하면 콘솔에 에러 내용을 출력 (로그 기록)

        // 만약 에러가 'CustomeError' 클래스의 인스턴스라면 (커스텀 에러인 경우)
        if (error instanceof CustomeError) {
            // 에러의 상태 코드와 메시지를 JSON 형태로 클라이언트에 응답
            return res.status(error.statusCode).json(error.serializeErrors());
        }

        // 커스텀 에러가 아닐 경우, 다른 미들웨어로 넘겨서 처리 (next()를 호출하여 다음 미들웨어로 이동)
        next();
    });
}

```

```jsx
app.all('*')는 존재하지 않는 경로로 요청이 들어왔을 때 404 에러를 반환합니다.

app.use()는 커스텀 에러를 처리하는 미들웨어입니다.

만약 CustomeError 클래스의 인스턴스라면, 에러 정보를 JSON 형식으로 클라이언트에 응답합니다.

* 여기서 어떻게 없는 주소인줄 알게 되냐면 미들웨어에서 순서의 중요함으로 알 수 있다

	글로벌 핸들러 위에 라우터 미들웨어가 있는데 라우터에서 처리를 못하고 아래로 내려가면 app.all 같은 모든 경로를

	받아서 처리하는거다 ( 라우터에서 처리하지 못했다면 없는 경로니까 )
```

## 스크립트

```jsx
이 package.json의 scripts 부분은 개발자가 자주 사용하는 명령어를 간편하게 실행할 수 있도록 모아놓은 설정입니다.

"dev": "nodemon -r tsconfig-paths/register src/app.ts | bunyan"라는 스크립트를 살펴보면 다음과 같은 요소로 구성되어 있습니다:

nodemon:

		이 도구는 Node.js 애플리케이션을 실행하고, 파일에 변경이 있을 때 자동으로 서버를 재시작해줍니다.

		개발 중에 코드를 수정할 때마다 수동으로 서버를 다시 시작할 필요가 없어 편리합니다.

-r tsconfig-paths/register:

		이 옵션은 TypeScript 프로젝트에서 설정된 모듈 경로를 처리하기 위해 사용됩니다.

		tsconfig-paths/register는 TypeScript의 tsconfig.json 파일에 정의된 경로 별칭(alias)을 Node.js가 이해할 수 있게 해주는 역할을 합니다.

src/app.ts:

		이는 실행할 파일의 경로입니다. src 폴더에 있는 app.ts 파일을 실행한다는 의미입니다.

		보통 서버의 진입점(entry point) 역할을 하는 파일입니다.


| bunyan:

		파이프(|) 기호는 앞의 명령어 출력을 뒤의 명령어로 넘겨주는 역할을 합니다.
```

# { 절대 경로 설정의 문제 }

```jsx
프로젝트에서 상대 경로로 파일을 불러오는 경우, 많은 ../ 경로를 사용하게 되어 코드가 복잡해질 수 있습니다.

이 문제를 해결하기 위해, 상대 경로 대신 절대 경로를 설정하여 직관적이고 간단하게 파일을 불러오고자 합니다.
```

## 모듈 설치

```jsx
npm install ttypescript typescript-transform-paths
```

```jsx
ttypescript란?

ttypescript는 TypeScript 빌드를 도와주는 라이브러리입니다.

이 라이브러리는 **TypeScript 컴파일러(TSC)**를 확장하여, 추가적인 기능을 지원합니다.

기본적으로 TypeScript는 tsconfig.json 설정 파일을 이용해 코드를 컴파일하지만,

우리가 ttypescript를 사용하면 **플러그인(추가 기능)**을 쉽게 추가할 수 있게 도와줍니다.

쉽게 말해서, ttypescript는 TypeScript 컴파일러에 더 많은 기능을 추가할 수 있도록 확장해주는 도구입니다.

이걸 사용하면 우리가 필요한 특정 기능을 적용하여 더 복잡한 빌드를 할 수 있습니다

typescript-transform-paths란?

보통 개발할 때, 코드의 파일 경로를 지정할 때 상대 경로(예: ../../utils)를 많이 사용합니다.

하지만 상대 경로는 길어지고 복잡해질 수 있습니다.

그래서 절대 경로(예: @utils/helper)를 설정하면 훨씬 더 깔끔하게 코드를 작성할 수 있습니다.

문제는 TypeScript가 컴파일된 후의 자바스크립트 코드에서는 여전히 상대 경로를 사용해야 한다는 점입니다. 그래서 이 라이브러리는

개발 중에는 절대 경로로 파일을 편하게 import 할 수 있게 해줍니다.

예: @utils/helper

빌드 시(코드를 실제 배포하거나 실행할 때) 절대 경로를 상대 경로로 변환해줍니다.

예: ../../utils/helper
```

```jsx
쉽게 설명하면, 코드에서 절대 경로를 사용하여 모듈을 더 쉽게 불러올 수 있게 해주며, 빌드할 때는 상대 경로로 자동 변환해주는 설정입니다
```

```jsx

		TypeScript 컴파일러(TypeScript Compiler)를 실행하는 명령어입니다.
```

### 빌드 후 발생하는 경로 문제

```jsx
빌드를 실행한 후, 생성된 JavaScript 파일에서 여전히 절대 경로(@root/config)가 유지되어

경로 문제(Cannot find module '@root/setupServer')가 발생합니다.

이 문제는 TypeScript 빌드 시 절대 경로를 일반적인 상대 경로로 변환하지 않았기 때문에 발생한 것입니다.

해결 방법: ttypescript와 typescript-transform-paths 사용

이 문제를 해결하기 위해, TypeScript 트랜스파일러 대신 ttypescript와 typescript-transform-paths를 사용합니다.

ttypescript는 TypeScript 트랜스파일러의 확장 버전으로, 빌드 시 경로 변환을 지원합니다. ( 이전에 설치했던 라이브러리 )

typescript-transform-paths는 빌드 중에 경로를 올바르게 변환해주는 역할을 합니다.

* 스크립트를 ttsc -p . 로 변경하면 ttypescript를 사용 가능하다
```

## ttypescript 문제로 라이브러리 교체

```jsx
기존에 코드에서 상대 경로(../../..)를 사용하는 대신,

tsconfig 파일에서 설정한 경로 별칭(alias path)을 사용하여 가독성을 높였습니다.

하지만 TypeScript 빌드 시 TSC 명령어를 사용하면 경로 별칭이 그대로 유지되고,

실제로는 상대 경로로 바꿔야 배포 시 오류가 발생하지 않습니다.

이 문제를 해결하기 위해 ttypescript라는 라이브러리를 사용하여 경로 별칭을 상대 경로로 변환하는 방식을 사용했습니다.

그러나

ttypescript가 작동하지 않는 문제가 발생했습니다.

그래서 이를 대체할 새로운 라이브러리인 tsc-alias를 사용합니다.

```

```jsx
기존 라이브러리 ttypescript를 제거합니다:

npm uninstall ttypescript
```

```jsx
새로운 라이브러리 tsc-alias를 설치합니다

npm install tsc-alias --save-dev
```
