# { 🎮 Ping Pong Platform (왕복 플랫폼) 만들기 }

## 🎯 목표

게임 시작과 동시에 두 지점을 끊임없이 왕복하는 플랫폼 제작 + 부모 클래스 리팩토링

---

## 📋 전체 구조 개요

```
리팩토링 전
  BP_Interactive_Platform
    └─ BP_Floating_Platform (압력판으로 활성화)

리팩토링 후
  BP_Platform_Base (부모 클래스)
    ├─ Interp Location (공통)
    ├─ Interp Platform Location 함수 (공통)
    ├─ BP_Floating_Platform (압력판 활성화)
    └─ BP_Platform_PingPong (자동 왕복) ✨ 새로 추가
```

---

## 🏗️ 1단계: 부모 클래스 리팩토링

### 1-1. 문제 인식

**현재 상황**

```
BP_Floating_Platform
  ├─ Interp Location (자식에만 있음)
  └─ Update Platform Location (자식에만 있음)

문제점:
  └─ 새 플랫폼 만들 때마다 반복 작업 필요
```

**해결책**

```
공통 기능을 부모로 이동
  ├─ Interp Location → 부모
  └─ Update Platform Location → 부모
```

### 1-2. Interp Location을 부모로 이동

**작업**

```
BP_Interactive_Platform 열기
  ↓
Components 패널
  ↓
Add Component → Scene Component
  └─ 이름: Interp Location
```

**결과 확인**

```
BP_Floating_Platform 열기
  ↓
Components 패널
  └─ Interp Location 0 (자동 이름 변경됨)
      ├─ 기존: Interp Location
      └─ 새것: Interp Location (부모에서 상속)
```

💡 **왜 이름이 바뀌나?**

- 부모와 자식에 같은 이름의 컴포넌트가 생김
- 언리얼이 자동으로 "0"을 붙여서 구분
- 중복 방지를 위한 자동 처리

### 1-3. 참조 변경

**작업**

```
BP_Floating_Platform
  ↓
Update Platform Location 함수
  ↓
Get World Location 노드
  ├─ Target: Interp Location 0 ❌ (제거)
  └─ Target: Interp Location ✅ (부모 것으로 변경)
```

**Interp Location 0 삭제**

```
Components 패널
  └─ Interp Location 0 우클릭 → Delete
```

### 1-4. 레벨의 인스턴스 재설정

**문제**

```
부모 클래스에 컴포넌트 추가
  ↓
레벨에 있는 인스턴스들의 Interp Location 위치 초기화됨
  ↓
다시 설정 필요
```

**작업**

```
레벨의 각 BP_Floating_Platform 선택
  ↓
Interp Location 선택
  ↓
원하는 위치로 이동 (다시 설정)

```

💡 **왜 초기화되나?**

- 부모 클래스의 구조가 변경됨
- 자식 인스턴스들이 새 부모 구조를 반영
- Transform 값이 부모의 기본값으로 재설정

## 🔄 2단계: 함수를 부모로 이동

### 2-1. 함수 이름 변경 이유

**기존 이름**

```
Update Platform Location
  └─ 의미: 플랫폼 위치 업데이트
  └─ 모호함: "어떻게" 업데이트하는지 불명확
```

**새 이름**

```
Interp Platform Location
  └─ 의미: 플랫폼 위치를 보간(Lerp)해서 이동
  └─ 명확함: Interpolation(보간) 사용을 명시
```

💡 **Interp = Interpolation (보간)**

- 두 값 사이를 부드럽게 전환
- Lerp를 사용한다는 힌트

### 2-2. 부모 클래스에 함수 생성

**작업**

```
BP_Interactive_Platform (부모)
  ↓
Functions 패널 → + 버튼
  ├─ 이름: Interp Platform Location
  └─ 입력 추가
      ├─ 이름: Alpha
      └─ 타입: Float
```

**함수 내용**

```
BP_Floating_Platform의 Update Platform Location 복사
  ↓
BP_Interactive_Platform의 Interp Platform Location에 붙여넣기
  ↓
Alpha 입력 → Lerp의 Alpha에 연결
```

### 2-3. 자식에서 상속된 함수 호출

**작업**

```
BP_Floating_Platform
  ↓
Float Timeline → Update 핀
  ↓
Interp Platform Location 검색
  ├─ 함수 목록에 보이지 않음 (상속됨)
  └─ "Call Function" → Interp Platform Location 선택
```

**노드 연결**

```
Float Timeline
  ├─ Update → Interp Platform Location (상속 함수)
  └─ Float 출력 → Alpha 입력
```

**기존 함수 삭제**

```
Functions 패널
  └─ Update Platform Location 우클릭 → Delete
```

## 🔄 5단계: 왕복 시스템 구현

### 5-1. 왕복 로직 이해

**단순 재생 (작동 안 함)**

```
Begin Play → Timeline Play
  ↓
0초 → 2초 재생
  ↓
끝 (멈춤) ❌
```

**원하는 동작**

```
0초 → 2초 (Forward)
  ↓
2초 → 0초 (Reverse)
  ↓
0초 → 2초 (Forward)
  ↓
무한 반복 ♾️
```

### 5-2. Custom Events 생성

**Custom Event란?**

```
용도: 내가 만든 이벤트
특징:
  ├─ 다른 곳에서 호출 가능
  ├─ 함수처럼 사용
  └─ 이름으로 구분
```

**PingPong Forward 이벤트**

```
우클릭 → Add Custom Event
  ├─ 이름: PingPong Forward
  └─ 연결: PingPong → Play from Start
```

**PingPong Reverse 이벤트**

```
우클릭 → Add Custom Event
  ├─ 이름: PingPong Reverse
  └─ 연결: PingPong → Reverse from End
```

💡 **Play vs Play from Start**

- Play: 현재 위치에서 재생
- Play from Start: 항상 0초부터 재생

💡 **Reverse vs Reverse from End**

- Reverse: 현재 위치에서 역재생
- Reverse from End: 항상 끝(2초)부터 역재생

![image.png](https://res.cloudinary.com/du1acdhxq/image/upload/v1788380675/notion-blog/_/_/_5_/2/image_4.png)

### 5-3. Switch on Direction

**Switch 노드란?**

```
용도: Enum 값에 따라 다른 경로 실행
비유: if-else를 여러 개 나열한 것

Direction Enum:
  ├─ Forward → 정방향 완료
  └─ Backward → 역방향 완료
```

**노드 구조**

```
PingPong Timeline → Finished
  ↓
Switch on ETimelineDirection
  ├─ Selection: Direction
  ├─ Forward → PingPong Reverse 호출
  └─ Backward → PingPong Forward 호출
```

**작동 원리**

```
Step 1: Begin Play → PingPong Forward
  ↓
Step 2: Timeline 0→2초 재생 (Forward)
  ↓
Step 3: Finished 발동 + Direction = Forward
  ↓
Step 4: Switch → Forward 경로 선택
  ↓
Step 5: PingPong Reverse 호출
  ↓
Step 6: Timeline 2→0초 역재생 (Backward)
  ↓
Step 7: Finished 발동 + Direction = Backward
  ↓
Step 8: Switch → Backward 경로 선택
  ↓
Step 9: PingPong Forward 호출
  ↓
Step 10: Step 2로 돌아가서 무한 반복
```

### 5-4. Update 연결

**노드 구조**

```
PingPong Timeline → Update
  ↓
Interp Platform Location (상속 함수)
  ├─ Target: Self
  └─ Alpha: PingPong Alpha
```

### 5-5. Begin Play 연결

**노드 구조**

```
Event BeginPlay
  ↓
PingPong Forward (Custom Event 호출)
```

💡 **왜 PingPong Forward 호출?**

- 왕복 사이클 시작
- Forward → Reverse → Forward... 반복

## 👁️ 7단계: Billboard Component (시각화 개선)

### 7-1. 문제점

**현재 상황**

```
Interp Location = Scene Component
  ├─ 선택해야만 보임
  └─ 다른 오브젝트 선택 시 안 보임
```

**불편함**

```
플랫폼 여러 개 배치 시
  ├─ 어느 것이 어디로 가는지 모름
  └─ 일일이 선택해서 확인 필요
```

![image.png](https://res.cloudinary.com/du1acdhxq/image/upload/v1788380675/notion-blog/_/_/_5_/2/image_5.png)

### 7-2. Billboard Component란?

![image.png](https://res.cloudinary.com/du1acdhxq/image/upload/v1788380675/notion-blog/_/_/_5_/2/image_6.png)

**Billboard Component**

```
개념: 항상 카메라를 향하는 2D 이미지
용도:
  ├─ 에디터에서만 보임 (게임 중엔 안 보임)
  ├─ 위치 마커
  └─ 시각적 가이드

특징:
  ├─ Scene Component + 스프라이트
  └─ 선택 안 해도 항상 보임
```

**비유**

```
Scene Component = 투명한 마커
Billboard Component = 깃발이 꽂힌 마커
```

### 7-3. Scene을 Billboard로 교체

**단계 1: 기존 것 Deprecated 표시**

```
BP_Platform_Base
  ↓
Interp Location 선택
  ↓
이름 변경: Interp Location_dep
```

💡 **dep = deprecated (사용 중단)**

- 곧 삭제될 것을 표시
- 다른 곳에서 사용 중이므로 바로 삭제 불가
- 참조 변경 후 삭제

**단계 2: Billboard 추가**

```
Add Component → Billboard
  └─ 이름: Interp Location (새 것)
```

**단계 3: 스프라이트 변경**

```
Details 패널
  └─ Sprite
      ├─ Show Engine Content 체크 ✅
      └─ "target" 검색 → Target Icon 선택
```

**단계 4: 함수의 참조 변경**

```
Interp Platform Location 함수
  ↓
Get World Location
  ├─ Target: Interp Location_dep ❌
  └─ Target: Interp Location ✅
```

**단계 5: 기존 것 삭제**

```
Interp Location_dep 우클릭 → Delete
  ├─ 에러 없으면: 다른 곳에서 안 씀 ✅
  └─ 에러 있으면: 아직 어딘가 사용 중 ❌
```

### 7-4. 레벨 인스턴스 재설정

**작업**

```
레벨의 모든 플랫폼 인스턴스 선택
  ↓

  ↓
원하는 위치로 이동 (다시 설정)
```

**확인**


## 📊 핵심 개념 정리

### Custom Event

```
개념: 사용자 정의 이벤트
특징:
  ├─ 이름으로 다른 곳에서 호출
  ├─ 입력/출력 파라미터 가능
  └─ 재사용 가능

vs 함수:
  ├─ 함수: 값 반환 가능, 지역 변수 사용
  └─ Custom Event: 실행 흐름만, 네트워크 복제 가능
```

### Switch on Enum

```
용도: Enum 값에 따른 분기
구조:
  Switch
    ├─ Selection: Enum 변수
    ├─ 값1 경로
    ├─ 값2 경로
    └─ 값N 경로

vs Branch:
  ├─ Branch: True/False 두 갈래
  └─ Switch: 여러 값에 따라 여러 갈래
```

### Billboard Component

```
용도: 에디터 전용 시각 마커
특징:
  ├─ 항상 카메라 방향
  ├─ 게임 중엔 안 보임
  ├─ 성능 영향 없음
  └─ 레벨 디자인 도구

활용:
  ├─ 스폰 포인트
  ├─ 웨이포인트
  ├─ 목표 지점
  └─ 경로 표시
```


```
Custom Event 사용:
  ├─ 재귀 호출 필요
  ├─ 네트워크 복제 필요
```

```
  ├─ Branch 사용 가능

방향이 3개 이상이면:
  └─ Switch 사용 권장
```

### 5. Billboard 크기

```
너무 크면:
  └─ 화면 가림

너무 작으면:

  └─ Screen Size: 0.5~1.5
```

## 📋 핵심 개념

### Level Instance vs Packed Level Actor

```
Level Instance (레벨 인스턴스)
  ├─ 개념: 다른 레벨에 포함할 수 있는 서브 레벨
  ├─ 구성: 모든 종류의 액터 포함 가능
  ├─ 최적화: 없음
  └─ 용도: 복잡한 구조 재사용

Packed Level Actor (패킹된 레벨 액터)
  ├─ 개념: 최적화된 Blueprint 액터
  ├─ 구성: Static Mesh만 포함 가능 ⚠️
  ├─ 최적화: Instanced Static Mesh 사용 ✅
  └─ 용도: 반복되는 지오메트리 최적화
```

## 🎨 Instanced Static Mesh 원리

### Draw Call 최적화

```
Before (개별 메시)
━━━━━━━━━━━━━━━━━
Mesh A (10개)
  └─ Draw Call × 10 = 10

Mesh B (5개)
  └─ Draw Call × 5 = 5

총 Draw Call: 15

After (Instanced)
━━━━━━━━━━━━━━━━━
Mesh A Instances (10개)
  └─ Draw Call × 1 = 1 ✅

Mesh B Instances (5개)
  └─ Draw Call × 1 = 1 ✅

총 Draw Call: 2 (86% 감소!)
```

### 리소스 공유

```
같은 메시를 여러 번 사용할 때:

일반 방식:
  └─ 각 액터마다 메시 데이터 참조

Instanced 방식:
  ├─ 메시 데이터 1개만 메모리에 로드
  ├─ Transform(위치, 회전, 크기)만 개별 저장
  └─ GPU에서 한 번에 렌더링
```

💡 **비유**:

- 일반 = 같은 책을 10권 사기
- Instanced = 책 1권 사고 책갈피 10개 꽂기

## 🚀 7단계: Soft Class Reference (최적화)

### 7-1. 개념 이해

**Hard Reference vs Soft Reference**

```
Hard Reference (하드 레퍼런스)
  ├─ 즉시 로드
  ├─ 항상 메모리에 상주
  ├─ 크기: 큼 (의존성 포함)
  └─ 사용: 자주 필요한 것

Soft Reference (소프트 레퍼런스)
  ├─ 필요할 때만 로드
  ├─ 메모리 효율적
  ├─ 크기: 작음 (경로만 저장)
  └─ 사용: 가끔 필요한 것
```

**비유**

```
Hard Reference = 책을 항상 가방에 넣고 다님
Soft Reference = 도서관 카드만 가지고 필요할 때 빌림
```

### 7-2. 변수를 Soft Class Reference로 변경

**기존 방식**

```
Get All Actors of Class
  └─ Actor Class: BP_Kick (직접 선택)
      └─ 하드 레퍼런스 생성 ❌
```

**최적화 방식**

```
1. 변수로 승격
   Get All Actors of Class 핀
     ↓
   우클릭 → Promote to Variable
     └─ 이름: Kix Class

2. 타입 변경
   Variables 패널에서 Kix Class 선택
     ↓
   Details 패널 → Variable Type
     └─ Soft Class Reference 체크 ✅

3. 색상 변화
   ├─ Hard Reference: 보라색
   └─ Soft Reference: 분홍색 ✨
```

![image.png](https://res.cloudinary.com/du1acdhxq/image/upload/v1788380672/notion-blog/_/_/_5_/2/image_25.png)

### 7-3. Async Load Class Asset

**노드 구조**

```
Event Activate
  ↓
Async Load Class Asset
  ├─ Asset Class: Kix Class (Soft Reference)
  └─ Completed: 로딩 완료 시 실행
      ↓
      Class 출력: 로드된 클래스
```

**Async Load Class Asset**

```
용도: 클래스를 비동기로 로드
특징:
  ✅ 게임 멈춤 없음
  ✅ 백그라운드에서 로딩
  ✅ 완료되면 Completed 실행

입력:
  └─ Asset Class: Soft Class Reference

출력:
  ├─ Completed: 로딩 완료 핀
  └─ Class: 로드된 실제 클래스
```

**비동기(Async)란?**

```
동기(Sync):
  로딩 시작 → [멈춤] → 로딩 완료 → 진행

비동기(Async):
  로딩 시작 → 백그라운드 로딩
  게임 진행 → 완료되면 콜백
```

### 7-4. 최적화된 전체 구조

```
Event Activate
  ↓
Async Load Class Asset
  └─ Kix Class (Soft Reference)
      ↓
      Completed
        ↓
Get All Actors of Class
  └─ Class (로드된 클래스)
      ↓
Get [0]
  ↓
Branch (Is Valid Index?)
  ├─ True → Win Game
  └─ False → (무시)
```

## 💡 핵심 개념 정리

### Hard vs Soft Reference

```
언제 Hard 사용:
  ├─ 항상 필요한 것
  ├─ 자주 사용하는 것
  └─ 빠른 접근 필요

언제 Soft 사용:
  ├─ 가끔 필요한 것
  ├─ 조건부로 사용
  └─ 메모리 절약 중요
```

### Interface 활용

```
장점:
  ✅ 느슨한 결합
  ✅ 확장성
  ✅ 재사용성

Win/Lose 시스템:
  ├─ 다양한 트리거 가능
  ├─ 다양한 결과 처리
  └─ 쉬운 확장
```

### 비동기 로딩

```
필요성:
  ├─ 게임 멈춤 방지
  ├─ 부드러운 경험
  └─ 대용량 에셋 처리

주의:
  └─ Completed 전까지 사용 불가
```

## ⚠️ 주의사항

### 1. Soft Reference 설정

```
✅ Details 패널에서 직접 선택 가능
✅ None으로 두면 Is Valid Class가 False
❌ 런타임에 None이면 작동 안 함
```

### 2. 배열 접근

```
✅ 항상 Is Valid Index 확인
❌ 직접 Get 하면 크래시 위험
```

### 3. Interface 구현

```
✅ 구현 안 한 액터에 호출해도 에러 없음
✅ 조용히 무시됨
❌ 디버깅 어려울 수 있음
```

### 4. Async 로딩

```
✅ Completed 핀에서만 사용
❌ 로딩 중에 접근하면 null
```

## 🚀 7단계: BP_Kick에서 위젯 표시

### 7-1. 기본 구조 (Hard Reference)

```
Win Game / Lose Game 이벤트

Create Widget
  ├─ Class: WBP_End_Game
  └─ Owning Player: Get Player Controller
  ↓
Add to Viewport
  └─ 화면에 표시
```

**Create Widget**

```
용도: 위젯 인스턴스 생성
입력:
  ├─ Class: 위젯 클래스
  └─ Owning Player: 소유 플레이어
출력:
  └─ Return Value: 생성된 위젯
```

**Add to Viewport**

```
용도: 위젯을 화면에 표시
입력:
  └─ Target: 표시할 위젯
효과:
  └─ 화면에 위젯 렌더링
```

### 7-2. 최적화: Soft Class Reference

**문제점**

```
Hard Reference 사용 시
  ↓
WBP_End_Game 항상 메모리 로드
  ↓
게임 시작부터 불필요하게 메모리 차지
```

**해결책**

```
1. 변수로 승격
   Create Widget의 Class 핀
     → Promote to Variable
     → 이름: End Game Widget Class

2. Soft Reference로 변경
   Variables 패널
     → End Game Widget Class 선택
     → Variable Type: Soft Class Reference ✅

3. Async Load 사용
   Async Load Class Asset
     ├─ Asset Class: End Game Widget Class
     └─ Completed: 로딩 완료 시
```

**Async Load Class Asset**

```
기능: 클래스를 비동기로 로드
장점:
  ✅ 게임 멈춤 없음
  ✅ 필요할 때만 로드
  ✅ 메모리 효율

입력:
  └─ Asset Class: Soft Class Reference

출력:
  ├─ Completed: 로딩 완료 핀
  └─ Class: 로드된 클래스
```

### 7-3. 타입 특정화

**문제**

```
Create Widget 반환 타입 = User Widget (일반)
  ↓
Set Menu Text 함수 접근 불가
  (WBP_End_Game의 함수이므로)
```

**해결: 변수 타입 특정화**

```
End Game Widget Class 변수
  ↓
Variable Type 변경
  ├─ Class: WBP_End_Game (구체적)
  └─ Soft Class Reference: 체크 ✅
```

**효과**

```
Soft Reference 해결 시
  ↓
Create Widget 반환
  └─ WBP_End_Game (구체적 타입)
      ↓
  Set Menu Text 접근 가능 ✅

```

💡 **Casting 불필요**

- 변수 타입을 구체적으로 지정
- Create Widget이 그 타입으로 반환
- 자동으로 함수 접근 가능

## 📐 8단계: 화면 중앙 배치

### 8-1. 문제점

```
Add to Viewport만 하면
  ↓
화면 왼쪽 위 (0, 0)에 표시
  ↓
중앙이 아님 ❌
```

### 8-2. Set Position in Viewport

**노드 구조**

```
위젯 생성 후
  ↓
Set Position in Viewport
  ├─ Target: 위젯
  ├─ Position: Vector2D (위치)
  └─ Remove DPI Scale: false
```

**Position 계산**

```
목표: 화면 중앙에 위젯 중앙 배치

공식:
  위치 = (화면 크기 / 2) - (위젯 크기 / 2)
```

### 8-3. Get Viewport Size

```
Get Viewport Size
  ↓
Return Value (Vector2D)
  ├─ X: 화면 너비
  └─ Y: 화면 높이
  ↓
Split Struct Pin
  ↓
각각 / 2 (화면 중심)
```

### 8-4. Size Box 크기 가져오기

**Size Box를 변수로**

```
Designer 탭
  ↓
Size Box 선택
  ↓
Is Variable: 체크 ✅
  └─ 이름: Size Box Root
```

**크기 가져오기**

```
Size Box Root
  ↓
Get Desired Size (원하는 크기)
  ↓
Return Value (Vector2D)
  ├─ X: 위젯 너비
  └─ Y: 위젯 높이

```

❌ **잘못된 방법**: Get Desired Size
✅ **올바른 방법**: Get Width/Height Override

**문제점**

```
Desired Size:
  └─ 내부 콘텐츠가 원하는 크기
  └─ Override 값 반영 안 됨
```

**해결**

```
Size Box Root
  ├─ Get Width Override
  └─ Get Height Override
      ↓
  실제 설정한 크기 반환 ✅
```

![image.png](https://res.cloudinary.com/du1acdhxq/image/upload/v1788380674/notion-blog/_/_/_5_/2/image_36.png)

### 8-5. 최종 계산

```
Position X = (ViewportSize.X / 2) - (WidthOverride / 2)
Position Y = (ViewportSize.Y / 2) - (HeightOverride / 2)

Vector2D 노드로 조합
  ↓
Set Position in Viewport
```

### 8-6. 순수 함수로 정리

**Get Center for Size Box 함수**

```
입력:
  └─ End Game Widget (WBP_End_Game)

출력:
  └─ Return Value (Vector2D)

Pure Function: 체크 ✅
  └─ 실행 핀 없음, 값만 반환
```

**Pure Function이란?**

```
특징:
  ✅ 실행 핀 없음
  ✅ 값만 계산해서 반환
  ✅ 여러 곳에서 호출 가능
  ✅ 부작용 없음

vs 일반 함수:
  ├─ 일반: 실행 흐름 필요
  └─ Pure: 값만 필요할 때
```

## 🧹 9단계: 코드 정리 (Macro)

### 9-1. 중복 코드 문제

```
Win Game과 Lose Game
  ↓
거의 동일한 노드 구조
  ↓
차이점: 전달하는 텍스트만
```

### 9-2. Macro로 통합

**Macro란?**

```
개념: 재사용 가능한 노드 그룹
특징:
  ✅ Async 노드 포함 가능 (함수 불가)
  ✅ 입력/출력 정의 가능
  ✅ 여러 곳에서 재사용

vs Function:
  ├─ Function: Async 불가, 값 반환
  └─ Macro: Async 가능, 실행 흐름
```

**Macro 생성**

```
노드들 선택
  ↓
우클릭 → Collapse to Macro
  └─ 이름: Show End Game Widget

입력 추가:
  ├─ 이름: Menu Text
  └─ 타입: Text
```

### 9-3. 변수로 텍스트 관리

```
Win Game:
  Show End Game Widget
    └─ Menu Text: Win Text (변수)

Lose Game:
  Show End Game Widget
    └─ Menu Text: Lose Text (변수)

변수 설정:
  ├─ Win Text: "Won"
  └─ Lose Text: "Lost"
```
